# 项目蓝图规范

## 1. 文档职责

`.nova/PROJECT_BLUEPRINT.md` 是所有模块和开发会话共同读取的项目宪法，只保存需要长期共同遵守的稳定事实：项目结果、技术硬约束、代码落位、模块关系、跨模块契约、未完成工作索引和系统级资源边界。

以下内容不得在蓝图展开：

- 单个功能的页面、字段、局部流程、权限、失败分支和故事级验收；
- 具体函数、SQL、迁移步骤、运维命令和可从代码恢复的实现细节；
- 已完成工作、提交记录和历史过程说明。

功能目标进入 `.nova/design/*.md`；当前实现事实以代码、测试、迁移和配置为准。

## 2. 规范版本与一级结构

当前规范版本为 `3`。标题后必须包含：

```text
> 蓝图规范版本：3
```

以下七个一级章节名称和顺序固定，每章只承担一个职责：

1. 项目定位：对象、问题和成功结果；
2. 技术栈：当前事实或已确认硬约束；
3. 代码结构：物理目录、职责和代码落位规则；
4. 模块架构：业务模块职责、对外边界和依赖；
5. 跨模块契约：全局不变量、验证方式和唯一一份开发决策边界；
6. 待开发功能：仅保存尚未完成的工作包索引；
7. 系统架构：逻辑分层到代码目录的映射、数据与资源安全、运行与恢复。

版本缺失或不同即需要升级，不得根据标题相似度猜测兼容。

## 3. 必需结构

### 3.1 代码结构

使用“顶层目录”给出稳定目录树，再在“代码落位规则”使用下表：

```markdown
| 代码区域 | 职责 | 代码落位规则 |
|----------|------|--------------|
```

不罗列可从仓库直接恢复的完整文件树。

### 3.2 模块架构

模块职责使用：

```markdown
| 模块 | 职责 | 对外边界 |
|------|------|----------|
```

模块依赖、状态、流程或时序涉及三个以上节点时优先使用 Mermaid；字段、权限、失败责任和验收仍使用表格。

### 3.3 跨模块契约

“全局契约”使用：

```markdown
| 契约 | 适用范围 | 验证 |
|------|----------|------|
```

契约编号稳定且唯一。“开发决策边界”只在这里出现一次：

```markdown
| 边界 | 内容 |
|------|------|
| 本期必须实现 | ... |
| 明确不做 | ... |
| 后续候选 | ... |
| AI 可自行决定 | ... |
| 必须再次确认 | ... |
```

不得另设“非目标”“架构红线”或“项目级待确认事项”重复同一约束。

### 3.4 系统架构

“分层与代码映射”必须对应第 3 节的代码区域：

```markdown
| 层 | 职责 | 对应代码结构 | 允许依赖 |
|----|------|--------------|----------|
```

所有实现代码都必须映射到本表并服从依赖方向。模块自己的业务表结构、查询和 Repository 仍由模块所有，其接口与实现分别落入蓝图为相应职责规定的层和目录；蓝图可把 Repository 接口定义为端口或应用契约，并把持久化适配器映射到数据访问或基础设施实现区域。共享层只保存公共机制，不得绕过模块所有权吸收业务语义。分层、对应目录或允许依赖不足以容纳新能力时，先返回架构确认，不得由单个功能自行增加隐含层级。

数据与资源安全使用：

```markdown
| 适用范围 | 不变量 | 验证 |
|----------|--------|------|
```

例如 Parquet 内存安全属于本表；蓝图保留有界读取、资源所有权、原子发布和失败恢复等稳定不变量，具体类名、方法名、脚本名和逐步操作由代码、测试或专项设计承载。

运行与恢复使用：

```markdown
| 资源或失败点 | 所有者 | 恢复与清理 |
|--------------|--------|------------|
```

## 4. 待开发功能表

```markdown
| 编号 | 优先级 | 来源 | 功能 | 设计依据 | 前置依赖 | 完成定义 | 需求引用 |
|------|--------|------|------|----------|----------|----------|----------|
```

“来源”只允许：

- `用户提出`；
- `Review-Defer`；
- `问题诊断`；
- `历史迁移`。

其余约束：

- 编号必须稳定且唯一；
- 已确认设计必须引用 `.nova/design/YYYY-MM-DD_具体名称.md` 中一个真实、未完成工作包的显式锚点；
- 多个待办可以引用同一设计文档的不同工作包；
- 未完成澄清时“设计依据”写“待澄清”，不得创建空文档或虚构链接；
- 前置依赖只允许当前表内编号、`无` 或 `待澄清`，不得自依赖或重复；
- 完成定义只写外部可执行结果，不复制详细验收；
- 需求引用只允许 `REQ-<UUIDv7>@vN` 或 `无`，只在活动工作明确来自一个需求块时填写；
- 工作包实现并通过验收后删除该行，设计文档继续保留。

引用示例：

```markdown
[借用审批 WP-02](design/2026-08-25_设备借用闭环.md#wp-02-approval)
```

## 5. 内容分流与事实来源

满足任一条件的结论才进入蓝图：多个模块共同遵守、改变模块职责或依赖、改变全局权限/安全/数据生命周期、改变公共外部契约或项目级非功能要求、所有后续相关功能都必须遵守。

| 信息 | 唯一事实来源 |
|------|--------------|
| 项目级边界、跨模块契约和全局不变量 | `.nova/PROJECT_BLUEPRINT.md` |
| 待开发目标和工作包行为 | `.nova/design/*.md` |
| 当前实现、接口和数据结构 | 代码、测试、迁移和配置 |
| 操作、备份和回滚步骤 | 运维手册 |
| 完成历史 | 版本控制和发布记录 |

## 6. 完成检查

- 版本为 `3`，七个一级章节精确且有序；
- 代码目录、模块职责、分层到目录映射明确；
- 同一规则只写一次，没有独立“非目标”“架构红线”或“项目级待确认事项”；
- 五类开发边界完整；
- 待办表头、来源、编号、依赖和设计链接合法；
- 已完成工作不在待办表中，设计文档仍保留；
- 功能细节和可恢复实现信息没有进入蓝图。
