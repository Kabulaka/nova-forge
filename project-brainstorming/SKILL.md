# 项目头脑风暴与设计收敛

默认用户不是产品或技术专业人员。让用户按自己的思路描述，AI 在后台维护需求关系、证据和影响范围，前台只展示当前结论和一个最小问题。

## 核心规则

1. 每轮最多提出一个问题，且只确认一个信息维度；用户应能用一个短语或一句话直接回答。
2. 能从代码、配置、测试、运行契约或用户指定参考源查明的事实先研究，不要求用户代替检索。
3. 将结论标记为“已确认”“证据推断”或“待确认”，不得把推断写成正式要求。
4. 蓝图只保存所有模块都需要理解并长期遵守的项目级事实；具体功能设计进入 `docs/design/*.md`。
5. 一个史诗可以包含多个相互依赖的工作包；多个待办可以引用同一设计文档的不同稳定章节。
6. 现有蓝图不得直接套模板覆盖。格式不符合当前规范时，必须先报告迁移范围和未关联设计的待办，再取得用户选择。
7. 结构升级不得改变旧待办的名称、优先级、完成定义或隐含业务语义；未知内容显式保留为“待澄清”。
8. 前台不得出现推理草稿、自检标签、代理身份、工具过程、孤立人名或无上下文英文短句。
9. 有多个实质方案时提供 2–3 个互斥选择，用用户可感知结果解释取舍并明确推荐。
10. 架构讨论必须来自已确认场景、失败语义和非功能要求，不得用技术选型反向替用户决定需求。

## 文档分层

### `PROJECT_BLUEPRINT.md`

蓝图是项目宪法和开发入口，只记录：

- 项目定位、模块地图和依赖方向；
- 跨模块契约、全局不变量和架构红线；
- 共享的安全、资源和非功能要求；
- 项目级开发边界；
- 尚未完成的工作包索引及其设计依据。

蓝图不得展开单个功能的页面、字段、局部流程、局部状态机、异常分支或故事级验收。

### `docs/design/<epic>.md`

设计文档记录一个史诗的公共上下文以及一个或多个相关工作包，包括局部业务规则、权限、失败恢复、依赖和验收。开发某个工作包时，只读取蓝图、设计文档公共章节、当前工作包章节及其直接依赖，不默认加载整份史诗。

### 代码、测试、迁移与配置

它们是当前实现细节的唯一事实来源。设计文档可以记录不可从代码安全反推的取舍和契约，但不得复制会快速漂移的函数、SQL 或逐步操作说明。

## 项目级与功能级分流

讨论结论满足任一条件时，提炼后进入蓝图：

- 改变多个模块共同遵守的契约；
- 改变模块职责或依赖方向；
- 改变全局权限、安全、数据生命周期或状态不变量；
- 改变公共外部契约、项目级非功能指标或架构红线；
- 后续所有相关功能都必须遵守。

只影响一个史诗或工作包的交互、流程、局部状态、异常恢复和验收时，只进入设计文档。若局部讨论产生全局规则，蓝图只保存抽象后的公共约束，设计文档引用该约束并保留功能上下文，不在两处复制全文。

## 工作流

### 1. 确定项目上下文

- 判断是新项目、已有代码库、继续澄清已有工作包，还是升级现有蓝图。
- 读取项目级指令、现有 `PROJECT_BLUEPRINT.md`、与当前主题直接相关的代码和已引用设计章节。
- 未指定路径时，已有仓库默认使用根目录 `PROJECT_BLUEPRINT.md`，设计文档默认位于 `docs/design/`。
- 在首次提问前完整读取 [references/conversation-sop.md](references/conversation-sop.md)。

### 2. 检查现有蓝图

现有蓝图存在时，完整读取 [references/blueprint-migration-sop.md](references/blueprint-migration-sop.md)：

- 以明确的蓝图规范版本判断是否需要升级，不凭标题相似度猜测；
- 统计现有待办以及缺少有效设计章节引用的待办；
- 判断哪些待办共享目标、模型、不变量、状态链、依赖或组合验收，才可建议共同澄清；
- 用户不选择澄清时直接无损升级，未确认字段写“待澄清”，不继续劝说；
- 用户以后可以按待办编号重新发起同一套需求澄清流程。

### 3. 研究可验证事实

已有代码库时，按当前主线检查入口、模块边界、直接调用关系、权限、存储、失败恢复和测试。代码、测试和有效配置优先于陈旧说明，冲突标为待确认。

用户指定外部产品、开源项目或 GitHub 仓库时，在提出结论前完整读取 [references/reference-research-sop.md](references/reference-research-sop.md)：

- 范围过宽时先问一个缩小范围的问题；
- 范围明确且支持子代理时，启动一个或多个只读探索子代理；
- 主代理综合为参考事实、适配建议、不建议照搬和一个确认问题；
- 未经用户接受的参考行为只属于证据推断。

### 4. 自然对话与局部闭环

沿用户当前语境选择影响最大、证据最不足的一个差量。用户谈 A 时涉及 B，只有 B 会改变 A 的当前含义才立即追问，否则暂存，稍后只问剩余差量。

围绕当前功能簇逐步收敛：

- 为什么需要、谁使用、何时触发；
- 正常结果、状态变化和权限；
- 关键边界、失败及恢复；
- 明确不做什么；
- 如何证明实现正确。

一次共同澄清可以覆盖多个关联待办，但每轮仍只能询问一个差量。共同澄清表示共享史诗上下文，不表示把多个问题合并在一轮。

### 5. 形成史诗和工作包

需要功能设计时，完整读取 [references/design-document-standard.md](references/design-document-standard.md)，并以 [assets/DESIGN.template.md](assets/DESIGN.template.md) 为起点：

- 将共享目标、模型、不变量和依赖放入公共章节；
- 为每个可独立开发和验收的故事建立稳定工作包 ID 与显式锚点；
- 每个工作包独立定义范围、行为、权限、失败恢复和验收；
- 没有真实共享语义的待办必须拆成不同设计文档；
- 用户确认开始澄清后，可以保存“澄清中”设计文档，但规范性内容只写已确认事实，推断和未决事项必须分区。

工作包完成澄清后，才将蓝图待办的“设计依据”更新为该设计章节链接。中途停止时保留“澄清中”设计文档，蓝图待办仍标记“待澄清”。

### 6. 冻结开发边界

对当前工作包确认五类边界；存在未决项时继续遵守单问题规则：

1. 本期必须实现；
2. 明确不做；
3. 后续候选；
4. AI 可自行决定；
5. 必须再次确认。

边界外工作不得因“顺手”或“最佳实践”自动获得授权。

### 7. 确认并写入

写文件前展示自然语言摘要，说明哪些结论更新蓝图、哪些进入设计文档、会新增或更新哪些待办引用。只有用户明确确认或修正完毕后才写入正式要求。

- 起草蓝图前完整读取 [references/blueprint-standard.md](references/blueprint-standard.md)，新文件使用 [assets/PROJECT_BLUEPRINT.template.md](assets/PROJECT_BLUEPRINT.template.md)。
- 起草或更新设计文档时遵守设计状态和工作包生命周期，不覆盖其他工作包已确认内容。
- 已完成工作包从蓝图待开发表删除；设计文档继续保留，供仍未完成的工作包和后续维护追溯。
- 全部工作包完成后将设计文档标记为“已实现”；被新设计取代时标记为“已废弃”并指出替代来源。

### 8. 校验与交付

生成后运行：

```bash
python3 scripts/validate_blueprint.py /absolute/path/to/PROJECT_BLUEPRINT.md
python3 scripts/validate_blueprint.py --design /absolute/path/to/docs/design/example.md
```

蓝图校验必须检查规范版本、必需语义、待办编号、设计文件及章节锚点。设计文档校验必须检查状态、公共章节、工作包锚点和验收。处理全部错误后，再执行项目要求的测试、Review 和提交。

## 资源

- `references/conversation-sop.md`：自然访谈、差量追问、分支管理和输出净化；首次提问前完整读取。
- `references/blueprint-migration-sop.md`：现有蓝图检测、待办归组、用户选择和无损升级；现有蓝图存在时完整读取。
- `references/reference-research-sop.md`：外部参考范围、子代理探索、证据和 clean-room 边界；用户指定参考对象时完整读取。
- `references/blueprint-standard.md`：项目级蓝图职责、版本、结构和待办引用；起草或升级蓝图前完整读取。
- `references/design-document-standard.md`：史诗、公共章节、工作包、状态和生命周期；处理功能设计时完整读取。
- `assets/PROJECT_BLUEPRINT.template.md`：蓝图规范版本 2 模板。
- `assets/DESIGN.template.md`：支持多个工作包的史诗设计模板。
- `scripts/validate_blueprint.py`：蓝图和设计文档校验器。
