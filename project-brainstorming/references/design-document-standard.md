# 史诗设计文档规范

## 1. 文档职责

`docs/design/YYYY-MM-DD_<具体名称>.md` 保存一个史诗的共享契约和一个或多个相互关联的工作包。日期是文档首次创建当天的项目本地日期，必须是真实日历日期，后续修改不得改变；具体名称必须非空且能区分本次设计。

设计定义待开发目标，不充当当前代码说明书，也不复制蓝图全局规则。

当前实现事实仍以代码、测试、迁移和配置为准。

## 2. 元数据与状态

标题后必须包含：

```text
> 设计规范版本：3
> 设计状态：澄清中
> 演进来源：无
> 工作包：WP-01、WP-02
```

“演进来源”必须为 `无`，或指向同目录中一份已实现/已废弃设计的 Markdown 链接。新需求改变已完成设计所覆盖的原功能时必须填写链接；不得自引用、断链或指向尚未终态的设计。

设计状态只允许：

- `澄清中`：至少一个工作包为“待澄清”或“澄清中”；
- `已确认`：全部工作包已确认，但至少一个尚未完成；
- `已实现`：全部工作包均为“已完成”或“已废弃”，且至少一个已完成；
- `已废弃`：所有工作包均已废弃，并提供 `> 替代来源：[新设计](replacement.md)`。

工作包状态只在工作包地图维护一次，允许 `待澄清`、`澄清中`、`已确认`、`开发中`、`已完成`、`已废弃`。

## 3. 共享约束

共享章节使用稳定锚点：

```html
<a id="shared-context"></a>
## 1. 共享约束
```

问题与结果：

```markdown
| 问题 | 成功结果 |
|------|----------|
```

只记录全部工作包共同需要的契约：

```markdown
| 契约 | 已确认约束 |
|------|------------|
```

共享契约编号使用 `S-<编号>`。若工作包不共享目标、模型、不变量、依赖或组合验收，应拆成不同设计文档。

业务关系、业务流程、业务状态或时序确有三个以上节点时可以增加 Mermaid；不得重复工作包地图中的状态、交付和依赖，也不得为了填模板创建空图。

## 4. 工作包地图

```markdown
| 工作包 | 状态 | 交付结果 | 前置依赖 | 设计章节 |
|--------|------|----------|----------|----------|
```

- 工作包 ID 必须稳定且唯一；
- 前置依赖只允许当前地图内工作包、`无` 或 `待澄清`；
- 设计章节必须链接到同一文件的显式工作包锚点；
- 地图是工作包状态、交付和依赖的唯一事实来源。

## 5. 工作包契约

每个工作包使用稳定锚点：

```html
<a id="wp-01-example"></a>
## WP-01 示例工作包
```

契约表：

```markdown
| 契约 | 维度 | 已确认约束 |
|------|------|------------|
```

每个工作包必须且只能覆盖以下六个维度：

1. `交付边界`：本期结果及明确不做；
2. `参与者与权限`；
3. `触发与输入`；
4. `结果、状态与不变量`；
5. `失败与恢复`；
6. `AI 决策边界`：可自行决定和必须再次确认的范围。

契约编号使用 `<工作包 ID>-C<编号>`，例如 `WP-01-C01`。

业务流程、业务状态或时序复杂时可在契约表后增加 `### 行为图`，使用 Mermaid 表达；工作包依赖仍只保存在地图，简单行为不创建该章节。

验收表：

```markdown
| 覆盖契约 | 场景 | 预期结果 |
|----------|------|----------|
```

每个工作包契约必须至少被一个验收场景覆盖。组合场景在承担最终结果的工作包中同时引用多个工作包或共享契约编号，不再复制一份“组合验收关系”。

## 6. 澄清暂存

只有设计状态为“澄清中”时才保留：

```markdown
## 3. 澄清暂存

| 类型 | 内容 | 来源 |
|------|------|------|
| 待确认 | ... | 用户尚未决定 |
```

类型只允许 `证据推断` 或 `待确认`，且至少有一条“待确认”。已确认要求必须进入共享或工作包契约；文档进入“已确认”“已实现”或“已废弃”后删除整个暂存章节，不保留“无”的空章节。

## 7. 锚点、读取与生命周期

- 蓝图只引用显式 HTML 锚点，不引用行号；完成后锚点仍保持稳定；
- 设计文件名始终保留首次创建日期，修改正文、状态或工作包不得重命名为修改日期；
- 开发某个工作包时读取蓝图、设计元数据、共享约束、当前工作包及直接依赖；是否读取其他章节由代码影响分析决定，不在每份设计文档重复声明；
- 工作包确认后，蓝图待办才链接其锚点；中途停止时蓝图仍写“待澄清”；
- 工作包实现并验收后从蓝图删除，设计地图状态改为“已完成”；
- 全部工作包进入“已完成”或“已废弃”且至少一个已完成后，设计状态改为“已实现”；全部工作包废弃时改为“已废弃”；
- `已实现`和`已废弃`是终态历史快照，不得为后续需求追加工作包、修改已确认契约或改回非终态；后续需求必须新建日期文件，并以“演进来源”链接旧设计；
- 尚未终态的同一史诗只有在共享目标、模型或不变量仍成立时才可追加工作包；否则新建设计；
- 尚未实现的设计被取代时保留旧文档，标记“已废弃”并链接替代来源。

### 7.1 旧式文件名迁移

版本 3 项目的当前待办、当前设计或校验结果出现无创建日期的旧式设计文件名时，只迁移设计路径及其引用，不升级蓝图七章结构：

1. 先列出旧路径、新路径、日期证据和全部已知引用，取得用户确认后再写文件；
2. 日期优先取文档中可验证的首次创建记录；没有记录时，取当前文件连续版本控制谱系的首次加入日期，并转换为项目本地日期；
3. 文件曾删除后重建时，只有历史和内容能证明仍是同一设计谱系才沿用原日期；无法证明、没有版本历史或不同证据冲突时停止迁移，只询问首次创建日期，不得使用迁移当天日期；
4. 重命名时保留标题、契约和稳定锚点，只补充当前规范必需的元数据，并在同一变更中更新蓝图、设计及项目内已知引用；
5. 任一引用无法安全更新、源文件在迁移中变化或迁移后校验失败时停止，不形成部分迁移结果。

## 8. 完成检查

- 设计规范版本为 `3`，文档状态与工作包地图一致；
- 文件名符合 `YYYY-MM-DD_具体名称.md`，日期有效且具体名称非空；
- 演进来源为“无”或指向同目录终态设计；新需求没有复用终态文档；
- 共享契约和工作包契约编号唯一；
- 每个工作包只有一处状态和依赖；
- 六类工作包契约齐全，验收逐条覆盖；
- 锚点、地图链接和蓝图引用可解析；
- 非澄清状态没有证据推断、待确认或空占位章节；
- 没有复制蓝图全局规则或代码可恢复细节。
