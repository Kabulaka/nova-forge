# 现有蓝图受控迁移 SOP

## 1. 适用条件

只有目标项目已存在 `PROJECT_BLUEPRINT.md`，且版本标记缺失、明确不是 `3`，或用户明确要求迁移审计时，才完整读取并执行本 SOP。不存在蓝图的新项目不属于迁移。版本 `3` 的正常澄清与只读分析不得加载本 SOP；显式迁移审计是唯一例外。

入口必须先按技能主流程取得稳定的完整蓝图快照，再依据其中的版本分流；不得为分流跳过首次全文读取。迁移只升级结构和追溯契约，不重新解释旧需求。

## 2. 检测与迁移报告

1. 读取项目指令、完整蓝图及当前任务已引用的设计章节。
2. 检查 `> 蓝图规范版本：3`；缺失或不同即判定需要升级。
3. 记录原待办的顺序、编号、优先级、名称、有效设计链接、可转换依赖和完成定义。
4. 统计待办总数及没有有效 `docs/design/*.md#anchor` 引用的数量。
5. 列出新版七字段待办表之外的所有附加列，例如“类别”“状态”“关联功能”。
6. 逐节扫描蓝图正文，识别不得继续默认加载的页面、字段、局部流程、局部权限、失败/恢复分支和故事验收；每项记录原标题或可定位的原文摘要，不能仅凭章节标题判断“无”。
7. 发现蓝图与代码冲突时标为待确认，不静默选择一方。

迁移前向用户一次说明：为什么升级；新版七章各自负责“项目定位、技术栈、代码结构、模块架构、跨模块契约、待开发功能、系统架构”；待办与缺失设计数量；将删除的附加列；每段需归档局部内容的原标题或摘要；可共同澄清的待办归组。七章不得合并成“补齐新版结构”等概括句，局部内容清单不得用“暂无”替代逐节扫描结果。不得先写文件再补充说明。

附加列在用户确认升级后直接从新表删除，不迁入设计文档，不根据其值推断新字段。仍在正文中的局部功能细节若没有正式设计，迁移前逐字归档到 `docs/archive/PROJECT_BLUEPRINT.pre-v3.<唯一标识>.md`；归档不参与默认读取，也不是设计依据。文件名冲突、归档内容校验不一致或迁移期间源文件变化时停止，不覆盖原文件。

## 3. 判断能否共同澄清

多个待办至少满足一项才可放入同一史诗：

- 共享用户目标和端到端结果；
- 共享领域模型、权限或状态不变量；
- 存在必须按顺序交付的数据或状态依赖；
- 必须组合验收才能证明整体行为正确。

同模块、同优先级、名称相似或同期开发不构成合并依据。

## 4. 只询问一个迁移决定

迁移报告后只询问一个选择，并把删除范围写进选项：

1. 按推荐归组先澄清，完成后升级并删除迁移报告中已披露的附加列；
2. 现在升级并删除已披露的附加列，缺失设计依据继续写“待澄清”；
3. 暂不升级，保持文件不变。

用户明确选择 1 时执行第 5 节，选择 2 时执行第 6 节，选择 3 时停止且不写文件。答复不明确时只澄清这个迁移选择，不得把“不想澄清”推断为删除授权。

## 5. 用户选择澄清

1. 按推荐归组建立“澄清中”设计文档；没有共享语义的待办分开建文档。
2. 已确认内容写入共享或工作包契约；证据推断和未决差量只写入“澄清暂存”。
3. 每个待办建立独立工作包 ID 和显式锚点。
4. 旧蓝图尚未升级时，映射只保存在设计地图中，不向不存在的列提前写值。
5. 全部待办完成本轮澄清后一次升级蓝图；已闭环工作包写真实链接，未闭环仍写“待澄清”。
6. 澄清中断时保留设计文档，旧蓝图不变；恢复后只继续剩余差量。

共同澄清只共享上下文，每轮仍只确认一个信息维度。

## 6. 用户明确选择立即升级

立即升级：

- 保留原待办顺序、稳定编号、优先级、名称、有效设计链接、可转换依赖和完成定义；
- 缺少编号时按顺序生成 `PEND-001`、`PEND-002`，不带业务推断；
- 来源统一写 `历史迁移`；
- 没有已确认设计时写“待澄清”；
- 旧“前置条件”不是当前待办编号时不得伪装成依赖，写“待澄清”；
- 删除迁移报告中已披露的附加列；
- 不创建空设计，不补写原文没有确认的验收、权限、失败或架构要求。

无法保持名称、优先级、完成定义或有效设计链接时停止迁移并报告冲突。

## 7. 后续重新发起澄清

用户以后指定待办编号时：

1. 读取蓝图行和已有相关设计；
2. 复述已确认内容；
3. 只询问剩余的一个差量；
4. 判断加入现有史诗还是新建设计；
5. 工作包确认后更新蓝图设计链接；
6. 不重新询问蓝图中的项目级公共契约。
