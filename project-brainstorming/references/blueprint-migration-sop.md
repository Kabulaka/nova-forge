# 现有蓝图无损迁移 SOP

## 1. 适用条件

只要目标项目已经存在 `PROJECT_BLUEPRINT.md`，在继续需求澄清或写文件前完整执行本 SOP。迁移的目标是升级文档结构和追溯能力，不是重新解释旧需求。

## 2. 检测与保护

1. 读取项目指令、完整蓝图及其引用的当前设计章节。
2. 检查 `> 蓝图规范版本：2`；缺失或不同即判定需要升级。
3. 记录原待办的顺序、编号、优先级、名称和完成定义。
4. 统计没有有效 `docs/design/*.md#anchor` 引用的待办。
5. 识别新版蓝图不得继续承载的旧功能细节，包括局部字段、流程、权限、异常和验收。
6. 发现文档与代码冲突时标为待确认，不静默选择一方。

旧功能细节不能直接删除。若它们尚未形成已确认设计，重写蓝图前必须把原蓝图逐字保存到不参与默认读取的 `docs/archive/PROJECT_BLUEPRINT.pre-v2.<唯一标识>.md`，并验证归档内容与重写前原文一致。该归档只保存迁移证据，不是规范性设计依据；不得用它替代澄清，也不得把蓝图待办链接到归档。文件名冲突时停止，不覆盖既有归档。

如果旧内容已能无歧义地归属到现有设计章节，保留原文来源并按设计文档规范迁移；存在归属、状态或语义歧义时仍进入归档，蓝图“设计依据”保持“待澄清”。

向用户说明：为什么需要升级、哪些结构会变化、哪些旧内容原样保留、待办总数和缺少设计依据的数量。不得先写文件再补充说明。

## 3. 判断能否共同澄清

多个待办至少满足一项实质条件，才可以建议放入同一史诗共同澄清：

- 共享同一个用户目标和端到端结果；
- 共享领域模型、权限或关键状态不变量；
- 存在必须按顺序交付的状态链或数据依赖；
- 需要组合验收才能证明整体行为正确。

仅仅属于同一模块、同一优先级、名称相似或计划同期开发，不足以合并。没有共同语义时必须分别澄清并使用不同设计文档。

## 4. 向用户提出一个迁移选择

先展示推荐归组和依据，然后只询问一个决定，例如：

> 当前有 4 个待办缺少设计依据，其中“要求提取”和“审核与版本管理”共享需求模型、版本状态和组合验收，适合作为一个史诗共同澄清；另外两个应独立处理。
>
> 是否按上述归组先澄清全部 4 个待办，再升级蓝图？

这一个选择必须覆盖所有缺少设计依据的待办，不提供“只澄清一部分后再升级”的迁移分支。用户不选择全部澄清时直接执行第 6 节，不继续询问功能规则。用户确认后，后续仍按每轮一个信息维度逐步对话。

## 5. 用户选择澄清

1. 按第 3 节的推荐归组分别建立状态为“澄清中”的设计文档；没有共同语义的待办各自使用独立设计文档。
2. 只将已经确认的内容写入规范性章节；证据推断和待确认差量分区保存。
3. 为各待办建立独立工作包 ID 和显式锚点。
4. 蓝图尚未升级时，不向可能不存在的“设计依据”列写值；已确认的待办到工作包映射分别保存在各自设计文档的工作包地图中。
5. 全部缺少设计依据的待办处理完后执行一次蓝图结构升级，并在新表格中一次写入已闭环工作包链接；尚未闭环的行写“待澄清”。
6. 澄清中途停止时保留设计文档和其中的映射，旧蓝图保持原样；恢复后重新读取二者，只继续剩余差量。

共同澄清只是共享上下文，不能把多个答复任务合并到一个问题中。

## 6. 用户不选择澄清

立即执行无损结构升级，不继续劝说或逐个追问：

- 保留原待办名称、优先级、顺序和完成定义；
- 保留已有稳定编号；缺少编号时按原顺序增加不带业务推断的 `PEND-001`、`PEND-002`；
- 没有已确认设计依据时填写“待澄清”；
- 未知前置依赖填写“待澄清”，不得从名称或排序推断；
- 不创建空壳设计文档；
- 不补写原文没有确认的验收、权限、失败或架构要求。

若旧蓝图包含新版禁止展开的功能细节，先按第 2 节完成逐字归档及一致性验证，再从新蓝图中移出；升级报告必须给出归档路径。归档不改变待办的“待澄清”状态，用户后续确认后再把有效内容收敛进正式设计文档。

如果迁移无法保留原语义或遇到并发修改，停止写入并报告冲突。

## 7. 后续重新发起澄清

用户以后指定待办编号时：

1. 读取蓝图行及已有相关设计文档；
2. 复述已经确认的内容；
3. 只询问剩余差量；
4. 判断应加入现有史诗还是新建设计文档；
5. 工作包确认后更新设计章节链接；
6. 不重新询问蓝图中的项目级公共约束。
