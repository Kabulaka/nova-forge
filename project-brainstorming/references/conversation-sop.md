# 非专业用户蓝图访谈 SOP

本 SOP 只在目标项目的新会话首次提问前完整读取一次。同一会话、同一项目且蓝图指纹未变化时复用，不重复加载。

## 1. 后台关系记录

用户按自己的思路描述，AI 在后台维护最小关系记录，不向前台倾倒表格。

| 字段 | 最小内容 |
|------|----------|
| 话题 | 稳定名称、用户原话、当前理解 |
| 事实 | 已确认、证据推断、参考来源 |
| 关系 | 上游目标、关联话题、影响范围 |
| 边界 | 隐含排除、待确认差量 |
| 状态 | 当前、相邻、暂存、闭环、冲突 |

保持追溯：`目标 → 用户场景 → 功能簇 → 行为契约 → 验收标准`。缺少上游目标的功能应被质疑，缺少验收的关键契约不能闭环。

- **当前**：正在讨论的唯一主线。
- **相邻**：会改变当前含义，可能需要立即确认。
- **暂存**：已经记录，但现在展开会打断思路。
- **闭环**：体验、边界、失败和验收已确认；只有新信息影响时重开。
- **冲突**：前后表达不能同时成立，必须由用户选择。

## 2. 选择一个差量

依次考虑认知连续性、影响范围、不确定性、不可逆性和可回答性。能由代码研究解决、影响小、可逆或纯内部实现的问题不占用提问预算。

每轮最多一个问题，只对应一个待确认差量。两个答案需要组合时也必须分轮，先问更不可逆、影响范围更大的一项。未问差量会改变当前理解时放入相邻分支，否则暂存。

### 单问题闸门

发送前必须全部满足：

1. 可先用一句陈述解释为何需要答案，但陈述本身不要求作答。
2. 只有一个需要用户回答的句子，最多一个问号。
3. 只收集一个信息维度，不含“谁使用并如何完成”“分别说明”“同时确认”等复合任务。
4. 示例只解释当前维度，不形成第二个问题或流程清单。
5. 2–3 个互斥选项只要求一次选择，用用户可感知结果解释取舍并明确推荐，不同时追问理由或下一项决定。
6. 用户若必须串联多个答案才能作答，继续拆分，只发优先级最高的一问。

错误：

> 你的主要用户是谁，他们会怎样完成一次典型协作？

正确：

> 我先确认服务对象，因为这会影响后续协作和权限。
>
> 这个平台第一批主要给哪一类人使用？

## 3. 输出净化闸门

所有用户可见回复，包括摘要和交付说明，在发送前执行：

1. 只保留理解结论或回答当前问题所需的内容。
2. 子代理、工具和后台记录只作事实来源，必须重新组织，不能拼接原始输出。
3. 删除推理草稿、候选问题、规则自检、内部等级、代理名称/状态、工具过程和面向 AI 的提示。
4. 删除孤立人名、无上下文英文、调试标记和 `[one question]` 等流程标签。
5. 用户要求分析内部原文时才可展示，并明确标为被分析内容。
6. 无法判断内容是否面向用户时不发送；净化后为空就停止，不用内部状态补位。

错误：

```text
管理驾驶舱是否需要导出 Excel 报表？ [one question]
Larsen.
Could ask export, user. good.
```

正确：

```text
管理驾驶舱是否需要导出 Excel 报表？
```

## 4. 分支、闭环与冲突

用户谈 A 时涉及 B：先记录 B；B 会改变 A 当前含义时只问一个最小差量，再回到 A；否则暂存。回到 B 时复述已知结论，只问剩余差量，不从头询问。

围绕当前功能簇逐轮覆盖：为什么需要、谁使用、何时触发、正常结果、状态变化、权限、关键边界、失败与恢复、明确不做、验收证据。分类只在后台使用，不按章节审问用户。

闭环时可用短摘要确认，但同一轮不要再开启下一话题：

> 到这里我理解的是：……，并且明确不做……。这段理解准确吗？

发现冲突时指出两种行为产生差异的具体场景，只问用户最终希望哪一种。新决定覆盖旧推断后，沿关系检查功能、权限、数据、架构和验收。

## 5. 外部参考

用户指定外部项目时，按 `reference-research-sop.md` 研究。后台将来源事实记为“证据推断”，将适配建议记为“待确认”；只有用户接受后才转为“已确认”。不得把参考项目全部功能自动纳入范围。

## 6. 架构与开发边界

需求基本收敛后，必须澄清代码结构、系统分层及其目录映射；其他架构决策先解释用户可感知的成本、离线/多设备、隐私位置、故障恢复和扩展边界，不让用户在未知后果下选择框架、数据库或协议。

最终冻结五类边界：

| 边界 | 判定 |
|------|------|
| 本期必须实现 | 缺少即无法完成核心场景或验收 |
| 明确不做 | 容易被顺手扩展但未获授权 |
| 后续候选 | 当前不实施，只保留已确认兼容空间 |
| AI 可自行决定 | 不改变体验、外部契约、安全或数据语义的内部实现 |
| 必须再次确认 | 范围扩大、安全或外部契约变化、不可逆数据操作、新依赖/基础设施或显著成本 |

边界总结使用用户理解的能力名称，不用类名、表名或目录代替。仍有未决项时继续遵守单问题闸门。

## 7. 禁止行为

- 按蓝图章节逐项审问，或在一轮合并多个答复任务。
- 为了完整询问可从代码查明的事实。
- 用户体验未确认就锁定技术方案。
- 遗忘暂存分支，或重新询问已确认内容。
- 只记录正常功能，不记录排除、失败恢复和验收。
- 只读 README 或产品首页就声称完成参考研究。
- 把参考行为直接写成本项目要求。
- 向用户转发代理输出、工具日志或内部自检。
