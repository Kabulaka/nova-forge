# 非专业用户蓝图访谈 SOP

## 1. 目标

允许用户用碎片化、跳跃和非专业语言描述项目。AI 在后台建立结构，前台保持认知连续性，最终得到完整且可追溯的蓝图要求。

核心原则：用户按自己的思维说，AI 负责在后台结构化；讨论沿当前语境推进，蓝图按专业结构输出。

## 2. 后台需求关系记录

为每个想法或功能簇维护以下信息。除非需要确认，不向用户展示完整记录。

| 字段 | 内容 |
|------|------|
| 标识 | 稳定的话题名称或内部编号 |
| 用户原话 | 保留用户表达，避免专业改写造成偏移 |
| 当前理解 | AI 对意图的简短解释 |
| 关联话题 | 被该想法触发或影响的其他话题 |
| 已确认 | 用户明确认可的要求 |
| 证据推断 | 来自代码、测试、配置或上下文的推断 |
| 参考来源 | 外部项目、版本、文件或官方资料及证据强度 |
| 适配建议 | 从参考事实推导、尚未得到用户确认的本项目建议 |
| 隐含边界 | 用户表达已经排除的能力或行为 |
| 待确认差量 | 仍会改变结果的最小问题 |
| 影响范围 | 受影响的功能、数据、权限、架构或验收 |
| 状态 | 活跃、相邻、暂存、已闭环、冲突 |

同时维护追溯关系：

```text
目标 → 用户场景 → 功能簇 → 行为契约 → 验收标准
```

没有上游目标或场景的功能应被质疑；没有验收的关键契约不能视为闭环。

## 3. 话题状态

- **当前主线**：用户正在思考的中心，只保留一条。
- **相邻分支**：会影响当前理解，可能需要立即澄清。
- **暂存分支**：已记录但现在展开会打断思路。
- **已闭环**：已确认体验、边界、失败和验收；只有新信息影响它时才重开。
- **冲突**：用户不同时间的表达无法同时成立，必须回到用户确认。

暂存不是遗忘。每次自然转场前检查相邻和暂存分支，优先选择与刚闭环话题依赖最近的分支。

## 4. 选择下一问

按以下优先级选择一个问题：

1. **认知连续性**：紧接用户刚才的表达，不迫使切换上下文。
2. **影响范围**：答案会改变多个功能或边界。
3. **不确定性**：当前存在两种以上合理解释。
4. **不可逆性**：涉及安全、外部契约、数据或高成本架构。
5. **可回答性**：用户能用体验和结果回答，而不需要技术知识。

能由代码研究解决、影响小、可逆或纯内部实现的问题不占用用户提问预算。

每轮最多问一个问题。该问题只能对应一个待确认差量，用户应能用一个短语或一句话作答。即使两个答案需要组合才能形成完整决定，也必须分轮询问；先问更不可逆、影响范围更大的一项。未询问差量会改变当前理解时进入相邻分支，否则进入暂存分支。

发送前执行单问闸门：

1. 用一句简短陈述说明为什么当前需要答案；该陈述不得要求用户作答。
2. 本轮只有一个需要用户作答的句子，且最多出现一个问号。
3. 问题短、具体，只收集一个信息维度，不包含“谁使用并如何完成”“分别说明”“同时确认”等复合要求。
4. 示例只帮助理解当前问题，不要求用户补充第二类信息；若示例本身形成流程清单，删除示例或缩成一个动作。
5. 2–3 个互斥选项只对应一次选择；不得同时追问选择理由或另一项决定。
6. 若用户需要串联多个答案才能完整作答，说明问题仍是复合问题，必须拆分后只发送优先级最高的一问。

### 输出净化闸门

所有用户可见回复在发送前执行以下检查，包含没有提问的摘要、方案和交付说明：

1. 只保留用户理解当前结论或回答当前问题所需的内容。
2. 子代理、工具和后台记录只能作为事实来源；先提取事实再重新组织，禁止拼接或转发原始输出。
3. 删除推理草稿、候选问题、规则自检、内部需求分级、代理名称/状态、工具调用过程和面向 AI 的操作提示。
4. 删除孤立人名、无上下文英文短句、调试标记和括号式流程标签；Excel、PDF、API 等与用户内容直接相关的术语必须保留。
5. 用户明确要求引用或分析某段内部片段时可以展示该片段，并清楚标明它是被分析的原文。
6. 无法判断某段是否面向用户时不发送该段，改用已确认事实重新生成完整回复；净化后为空则停止输出，不用内部状态补位。

错误输出：

```text
已确认……。
管理驾驶舱是否需要导出 Excel 报表？ [one question]
Larsen.
Could ask export, user. good.
hard requirement.
```

正确输出：

```text
已确认……。

管理驾驶舱是否需要导出 Excel 报表？
```

## 5. A 涉及 B 的处理

用户谈 A 时提到 B：

1. 将 B 记录为关联话题。
2. 判断“不知道 B 是否会改变 A 的当前含义”。
3. 会改变：提出一个最小澄清问题，再回到 A。
4. 不会改变：把 B 放入暂存分支，不立即展开。
5. 回到 B 时复述所有已知内容，只问剩余差量。

禁止把 B 遗忘后在后续章节从零询问。禁止为了坚持固定顺序要求用户“稍后再说”。

## 6. 外部参考结果进入对话

外部参考研究完成后，前台输出完整遵循 `reference-research-sop.md` 的“综合与确认”，本文件不重复定义展示格式。后台将参考事实记录为“证据推断”，将适配建议记录为“待确认差量”；只有用户明确接受后才能转为“已确认”。不得因用户说“参考某项目”就把该项目的全部功能纳入范围。

## 7. 功能簇局部闭环

围绕一个功能簇自然覆盖以下内容，不必向用户展示分类名：

- 用户为什么需要，谁使用，何时触发；
- 用户看见什么结果，系统状态如何变化；
- 谁能做、谁不能做；
- 边界情况、失败时看到什么、如何恢复；
- 哪些相似能力明确不需要；
- 如何用场景证明实现正确。

缺少会改变结果的内容时继续追问；只是内部代码选择时留给开发探索。

闭环时使用短摘要。当前轮若询问摘要是否准确，就不要同时开启下一话题：

> 到这里我理解的是：……。其中明确不做……。这段理解准确吗？

用户确认后，下一轮再提出下一个话题的一问。

## 8. 重访与冲突

重访旧话题时使用差量格式：

> 你之前已经确认 A、B，并排除了 C。现在的新想法会影响 D；还需要确认的是……

发现冲突时不要指责用户，也不要自行选择：

> 前面你希望……，刚才又提到……。这两种行为在……情况下会产生不同结果。你更希望用户最终看到哪一种？

用户修改决定后，沿关联关系检查功能、权限、数据、架构和验收的连带变化。

## 9. 覆盖扫描的用户化问法

后台检查专业维度，前台转换成场景问题：

| 后台维度 | 用户化问题示例 |
|----------|----------------|
| 权限 | “哪类人可以修改它？” |
| 幂等 | “连续点两次，是算一次还是两次？” |
| 并发 | “两个人同时修改时，谁的结果应该保留？” |
| 超时 | “等待太久时，用户应该继续等、重试还是先退出？” |
| 回滚 | “做到一半失败，已经完成的部分保留还是全部撤销？” |
| 数据保留 | “用户删除后，历史记录还需要保留吗？” |
| 可用性 | “外部服务暂时不可用时，哪些功能仍必须能用？” |
| 性能 | “在你预计的用户量下，多长时间内看到结果才可以接受？” |

## 10. 架构讨论

需求基本收敛后才提出架构。先解释用户可感知差异，再说明技术名称：

- 使用和维护成本；
- 离线或多设备能力；
- 隐私和数据位置；
- 故障影响和恢复难度；
- 当前规模与未来扩展边界。

不要让用户在不了解结果的情况下选择框架、数据库、认证协议或部署拓扑。

## 11. 开发边界冻结

最终逐项确认：

### 本期必须实现

缺少即无法完成核心场景或验收的能力。

### 明确不做

容易被 AI 顺手扩展、但用户没有授权的能力。

### 后续候选

有价值但当前不实施，只保留经确认的兼容空间。

### AI 可自行决定

不改变用户体验、外部契约、安全或数据语义的内部实现细节。

### 必须再次确认

产品范围扩大、安全策略改变、外部契约变化、不可逆数据操作、新依赖、新基础设施或显著成本变化。

边界总结必须使用用户能理解的能力名称，不用文件、类或数据库术语代替。

## 12. 反模式

- 按蓝图章节逐项审问用户。
- 同一功能的“要做”和“不做”相隔多轮重新询问。
- 用户刚提到旁支就连续展开所有相关问题。
- 把用户原话过早翻译成技术方案并要求确认。
- 为了完整而询问可从代码直接查明的事实。
- 在未确认用户体验前讨论框架和数据库。
- 只记录功能，不记录隐含排除、失败和验收。
- 总结过于频繁或一次展示整张需求表，增加认知负担。
- 在同一轮询问“主要用户是谁”和“他们如何完成完整流程”。
- 用一个问号包裹多个由“并且、以及、分别、同时”连接的答复任务。
- 只阅读外部项目 README 或产品首页就声称已经完成参考研究。
- 把外部项目的既有功能直接写成本项目要求，跳过适配确认。
- 把 `[one question]`、候选问题、内部分类或代理名称附在用户回复后面。
- 将子代理或工具输出直接拼接到前台消息，混入调试文本和过程状态。

## 13. 登录示例

用户说：“我想做排行榜，大家最好能登录。”

不要立即讨论认证协议。记录“排行榜”和“身份”两个关联话题，然后问：

> 登录主要是为了在排行榜中认出是谁，还是还要保存个人进度？这两种范围差别比较大。

如果用户回答“只要认人，游客也能看，不需要保存进度”，记录这些已确认内容和隐含排除。后续只问剩余差量：

> 你前面已经确认游客可以查看、登录只用于认人，也不保存进度。现在还差一个决定：游客产生的成绩是否进入排行榜？

不要在权限阶段重新问“登录哪些不用做”。

## 14. 新项目首问示例

用户说：“我想开发一个类似 Jira 的项目管理平台。”

不要同时询问主要用户和完整协作流程。先只问一个基础差量：

> 我先确认服务对象，因为这会影响后续优先梳理的协作流程和权限。

> 这个平台第一批主要给哪一类人使用？

用户回答后，下一轮再从其答案出发询问最常完成的一件事。完整流程、角色差异和验收结果分别留到后续轮次。
