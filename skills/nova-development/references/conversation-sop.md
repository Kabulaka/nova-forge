# Nova 共享澄清 SOP

Requirements 在用户明确要求需求澄清或创建、修改内容不足时使用本文件；Architecture 与 Development 在出现真实歧义时使用。它只约束共同的提问、选项、委托、确认、中断和恢复方式，不替代各技能对当前阶段结果的定义，也不创建流程状态、审计、编号或持久化记录。请求已经明确且证据足以推进时直接推进，不为形式完整强制访谈。

## 1. 先研究，再决定是否提问

1. 先从当前阶段允许使用的证据恢复事实；能由这些来源查明的问题不得让用户代替检索。
2. Requirements 只使用用户当前表达和用户明确提供的材料，研究会改变参与者、业务流程、状态、规则、边界或业务结果的差量；不得为澄清而自行扫描蓝图、设计、代码或测试。
3. Architecture 从目标项目规则、蓝图、蓝图精确链接及必要实现证据中，研究会改变技术栈、运行形态、模块职责、依赖方向、数据所有权、公共 API、事件、安全或恢复边界的差量。
4. Development 从目标项目规则、蓝图导航、代码、配置和测试中，研究会改变本次用户可见行为、交付范围、数据语义、接口契约、安全边界、失败语义或验收结果的差量。
5. 可逆的内部实现选择、命名、代码组织和已有约定能够唯一决定的事项，由 AI 直接选择并在需要时说明，不占用提问轮次。
6. 分开标明：
   - **用户已确认**：用户明确表达或确认的目标与边界；
   - **证据已查明**：可定位到项目或可靠外部来源的事实；
   - **AI 候选建议**：基于事实形成、仍可由用户修正的选择；
   - **待确认差量**：不同答案会实质改变本阶段交付且无法由证据消解的事项。
7. 当前阶段允许使用的证据与用户已确认内容冲突时，展示具体冲突和影响，不得把冲突静默改写成 AI 决定。

## 2. 选择一个最关键差量

依次考虑影响范围、不可逆性、风险、不确定性和对当前阶段结果的阻塞程度。每轮最多提出一个问题，只收集一个信息维度。

一个问题只有同时满足以下条件才应提出：

- 属于当前请求，而非未来功能或相邻改进；
- 不同答案会改变行为、范围、数据、公共契约、架构或验收；
- 会实质阻塞当前阶段结果、首次编辑或不可逆决定；Requirements 的阶段结果由其技能定义为能够自洽说明系统如何运转的业务大纲，Development 中只要答案会改变用户可见行为、范围、数据语义、接口、安全、失败语义或验收，就视为阻塞首次编辑，即使仍可先写脚手架、局部代码或测试；
- 无法从当前阶段允许使用的证据、已确认内容或用户委托中可靠消解。

后续功能、可选优化和不影响当前阶段结果的事项只作为遗留风险或候选说明，不进入当前问题队列。用户指出跑偏或要求先完成当前任务时，立即移除越界问题并返回当前下一动作，不再追问是否返回或是否继续。

### 单问题闸门

发送前必须全部满足：

1. 可先用一句陈述解释为何需要答案及它会影响什么，但陈述本身不要求作答。
2. 只有一个需要用户回答的句子，最多一个问号。
3. 不含“谁使用并如何完成”“分别说明”“同时确认”等复合任务。
4. 示例只解释当前维度，不形成第二个问题。
5. 存在 2–3 个真实、互斥选项时，说明每项的用户可感知取舍并把推荐项排第一；不同时追问理由或下一项。
6. 用户必须串联多个独立答案才能作答时继续拆分，只问优先级最高的一项。

错误：

> 你的主要用户是谁，他们会怎样完成一次典型协作？

正确：

> 我先确认首批服务对象，因为这会改变权限和默认流程。
>
> 这个平台第一批主要给哪一类人使用？

## 3. 方案、委托与确认

1. 形成候选方案时，先说明依据和证据强度，再给出具体建议、用户可感知影响和明确不采用的内容。
2. 只有多个边界共同构成一个不可分的行为选择时才可合并确认；可独立改变或取舍不同的决定仍须分轮。
3. 用户明确把某个范围委托给 AI 时，可免除该范围内低风险内部参数的逐项提问，但委托不得外推到其他阶段、业务目标、公共契约、显著成本或高风险边界。
4. 委托只能免除形式性问题，不能免除必要研究、具体选择披露和用户修正机会。
5. 用户修正候选时只重开目标边界和直接依赖；无冲突的既有事实、决定和证据继续有效。
6. 明确开发请求在没有阻塞差量时直接实施，不要求额外确认整份摘要。
7. 用户主动要求形成或修改需求、架构、设计或计划时，在写入前展示覆盖本次变更的整体摘要和目标文件；只有用户明确确认后才写入。用户已经提供完整内容、精确目标和明确写入指令时不重复索要形式性确认；普通“继续”、沉默、空答案、取消或对其他问题的回答不算确认。

## 4. 交互载体

1. 当前差量存在 2–3 个真实互斥方案，且宿主当前交互通道已确认支持原生结构化提问工具时优先使用；推荐项排第一。
2. Codex 使用当前可用的 `request_user_input`，Claude Code 使用当前可用的 `AskUserQuestion`；工具名称出现在本轮列表中不等于当前交互通道可用。`codex exec`、批处理或其他无法在工具调用中接收用户回答的非交互通道必须直接使用普通文本，不得尝试结构化提问。
3. 不得为了显示选项自行切换 Plan mode、修改宿主配置或调用额外流程工具。
4. 开放式事实问题、无法形成诚实互斥选项或原生工具不可用时，使用普通文本提出一个问题。
5. 原生工具只承载问题和选项；普通回复不得重复已经成功呈现的问题。工具返回后按“中断、空答案与恢复”中的可观察结果判断是否成功呈现，不能确认成功时执行其中的文本降级。

## 5. 答案后的统一推进

文本答案与结构化工具答案使用同一语义：

1. 把有效答案并入当前理解；最新明确补充覆盖默认含义，存在冲突时只保留一个冲突差量。
2. 每次合并后重新计算当前范围内的待确认差量和研究任务，不沿用回答前预判的“下一问”或“已收敛”。
3. 有当前阶段允许使用的证据可查时先研究；本轮能查明就继续推进，不能查明才说明“证据不足”和具体原因，不得借研究扩大该技能的证据范围。
4. 仍有阻塞差量时立即提出优先级最高的一问；没有阻塞差量时直接执行下一可执行动作，不只报告“建议下一步”或要求用户再次说“继续”。
5. 用户询问“还有要讨论的吗”时先重新计算：有差量就直接研究或提问，没有就明确说明并继续既定动作。

## 6. 中断、空答案与恢复

1. 结构化工具明确报告超时、取消或未提交，并同时确认问题已成功呈现时，视为当前问题未回答：不合并、不推进、不在当前轮重复，也不把空答案当确认。
2. 只返回空答案或 `0/1 answered`、没有成功呈现标记时，无法区分用户取消与宿主能力失败；必须在当前轮立即改用普通文本，完整呈现同一问题、原选项及其影响，不得称为“用户未回答”或“未收到选择”。
3. 工具明确返回 `unsupported`、`not supported`、`unavailable` 或其他能力错误时，同样视为问题没有成功呈现并执行当前轮文本降级。
4. 已确认成功呈现但未回答的问题，只在用户明确继续时原样重放问题、选项顺序、标签和说明；届时工具不可用则用普通文本完整列出原选项。
5. 用户直接回复完整选项标签时可接受；缺少上下文的 A/B/C 不得猜测。
6. 用户中断、纠偏或切换目标时，保留已确认且无冲突的事实；只丢弃被覆盖的候选和问题。
7. 上下文压缩或恢复后先从摘要和当前阶段允许使用的证据恢复已回答内容，只处理具体缺口，不从头重放访谈。

## 7. 输出净化

所有用户可见回复在发送前：

1. 只保留理解结论、选择影响、当前问题或交付结果所需内容。
2. 工具和后台分析只作事实来源，必须重新组织，不拼接原始输出。
3. 删除推理草稿、候选问题、规则自检、内部等级、代理名称或状态、工具过程和 `[one question]` 等流程标签。
4. 不用流程术语冒充业务结论，不把 AI 候选表述为用户已经确认。
5. 无法判断内容是否面向用户时不发送；净化后为空就停止，不用内部状态补位。

## 8. 分支、闭环与冲突

用户谈 A 时涉及 B：B 会改变 A 当前含义且阻塞当前动作时只问一个最小差量，再回到 A；否则把 B 留作相邻或后续事项。回到 B 时复述已知结论，只问剩余差量，不从头询问。

各技能只按自身定义的阶段结果和证据边界检查是否闭环；共享 SOP 不提供固定覆盖矩阵，也不要求按目标、角色、状态、权限或其他栏目逐项得出结论。已经由证据、委托或明确不适用消解的差量不再提问。

发现冲突时指出两种表达在具体场景中会产生什么不同结果，只问用户最终希望哪一种。新决定覆盖旧推断后，只在对应技能定义的阶段结果和证据边界内检查直接影响；Requirements 只检查会改变参与者、责任转移、主流程、关键业务规则或业务结果的影响，Architecture 与 Development 按各自技能边界检查。无冲突部分保持有效。

架构或设计需要整体确认时，最终摘要冻结五类边界：

| 边界 | 判定 |
|------|------|
| 本次必须实现 | 缺少即无法完成核心场景或验收 |
| 明确不做 | 容易被顺手扩展但未获授权 |
| 后续候选 | 当前不实施，只保留兼容空间 |
| AI 可自行决定 | 不改变体验、外部契约、安全或数据语义的内部实现 |
| 必须再次确认 | 范围扩大、安全或公共契约变化、不可逆数据操作、新依赖/基础设施或显著成本 |

边界总结使用用户理解的能力名称，不用类名、表名或目录代替。仍有未决项时继续遵守单问题闸门。

## 9. 外部参考边界

Requirements 只有在用户明确要求参考研究时才取得外部证据；仅提到产品名称或当前业务涉及高风险事项，不构成自动扩大来源的授权。Architecture 与 Development 在用户显式引用成熟平台、标准、最佳实践、产品或仓库，或方案涉及安全、身份、公共契约等高风险边界时，先取得与当前差量直接相关的可靠证据。外部事实标为“证据已查明”，适配到本项目的选择仍标为“AI 候选建议”；产品名仅作为证据源或例子时不得固化为产品专属依赖。

## 10. 禁止行为

- 按蓝图章节逐项审问，或在一轮合并多个答复任务；
- 为了流程完整询问可从当前阶段允许使用的证据查明的事实；
- 用户体验或公共边界未确认就锁定技术方案；
- 遗忘相邻事项，或重新询问已回答内容；
- 明知排除、失败恢复或验收会改变当前阶段结果，却只考虑正常路径；
- 只读 README 或产品首页就声称完成参考研究；
- 把参考产品行为直接写成本项目要求；
- 向用户转发代理输出、工具日志、推理草稿或内部自检。
