# Nova 实施与交付 SOP

本文件承接 Architecture 之外的开发实施约束。默认流程是“固定差异与验收 → 编码 → 测试 → 本地 commit”；不自动 Review，也不维护流程数据。

## 1. 准入、范围与任务差异基线

1. 当前实现事实以代码、测试、迁移和配置为准；项目级公共约束和架构导航以 `.nova/PROJECT_BLUEPRINT.md` 为准。只沿蓝图中与当前任务相关的精确链接读取详细架构或设计，不扫描 `.nova/design/`。
2. 根据用户明确目标、蓝图公共约束、相关设计和项目证据固定本次范围、验收矩阵与未验证事项。任务必须有完整结果和验收；多个步骤只有共同完成才有交付价值时视为同一内聚任务，不按阶段、文件、模块、代理或提交批次拆分。
3. 编码前记录仓库根、Git/SVN 状态、任务路径或模块，以及范围内既有修改和未跟踪文件。相关路径已有修改时，必须有足以区分同一文件新旧行块的基线；只有文件名或哈希不够。
4. “当前任务差异”只含相对任务开始基线由本任务新增、修改或删除的路径与行块。历史未提交内容不得因出现在 diff 或未跟踪列表中自动纳入。
5. 无法可靠分离时停止编辑，请用户选择独立 worktree/checkout、明确扩围或先处理既有变更。不得覆盖、回退、暂存或提交用户已有修改。
6. 上下文压缩、自检、Review 或续接不得重建任务基线。用户明确扩围时，在新增范围首次编辑前补充基线和验收。
7. 编码前应把会改变行为、契约、安全或数据语义的歧义清空。实施中发现此类阻塞时按共享澄清 SOP 处理；真实共享架构冲突必须停止并返回 Architecture，不得在实现中静默修改公共架构。

## 2. 编码前契约

编码前必须在内部固定与本次风险相称的变更说明；非必要时不单独发送一轮流程汇报：

1. **接口契约**：输入、输出、错误语义、兼容性、状态变化，以及跨调用边界的权威定义；
2. **核心不变量**：必须始终成立的数据、状态、权限、资源或顺序约束；
3. **变更闭包**：修改点、直接调用方、消费者和受影响模块；
4. **失败语义**：关键失败点、恢复、重试、回滚、清理和错误传播责任；
5. **资源生命周期**：所有权、并发、取消、超时、释放和重复执行语义；
6. **验收标准**：每条关键契约和不变量对应的可执行验证；
7. **分层落位**：新增或移动的入口符合蓝图目录、职责与依赖方向。

纯文档、格式或无运行时语义的机械维护只须固定目标、精确范围和最低验收，不为其虚构不适用的运行时契约。缺少代码落位，或需要新增技术栈、层、共享依赖、数据所有权或公共契约时停止并返回 Architecture。

## 3. 编码约束

- 正常路径和失败路径同时实现，不得先完成 happy path 再让测试替代异常语义；
- 在输入、接口和资源边界主动保证契约，不依赖调用方自觉传入合法值；
- 同一业务契约在前端、API、服务、任务和持久化边界保持允许输入、状态转换和错误语义一致；
- 上游校验只用于提前反馈，不能替代权威执行层的独立校验；
- 每个副作用都定义失败后的状态、补偿、清理和错误传播；
- 修改接口、状态或资源边界时同步检查直接调用方、消费者及恢复路径；
- 不得通过放宽校验、吞错、静默替换默认值或空值、改变既有语义或削弱断言来迁就实现；
- 测试不得反向修改已确认方案；发现设计缺陷时先补全契约与失败语义；
- 模块业务数据和 Repository 由模块所有；共享层只承载已确认的公共机制，不得吸收业务语义形成万能层；
- 存在 `.nova/SHARED_CAPABILITIES.md` 时先把它作为复用路由，再定向验证相关代码和测试；用户已确认且本轮完成的共享能力通过最低验收后按需登记，候选和未完成入口不得登记，最后一项退役时删除目录文件；
- 新依赖必须使用项目既有权威依赖清单和管理器，不得私自绕过；
- 同一失败连续修复三次仍未解决时停止，报告证据、尝试和阻断点。

## 4. 测试与证据复用

1. 测试逐条覆盖固定验收的正常路径、失败路径和关键边界。同一业务契约在多个调用边界存在时，使用共享用例或等价断言确认语义一致。
2. 测试发现设计未覆盖的缺陷时，先回溯补全契约和失败语义，再修复实现；不得在测试阶段临时发明业务规则。
3. 首次测试后保留：命令和工作目录、覆盖的验收项、相关代码/测试/配置/依赖与环境状态、结果和未验证事项。
4. 只有相关内容或环境变化、覆盖不足、结果失败或不完整，或用户明确要求重跑时，证据才失效。压缩、续接、自检、Review、阶段变化及无关文件变化不使结果失效。
5. 证据有效时后续自检、Review 和完成核对必须复用。失效时只重跑受影响测试；仅当影响无法可靠限定或验收要求全量时才运行全量测试。
6. 测试通过不等于 Review PASS；用户没有明确发起 Review 时不得使用 Review 结论措辞。

## 5. 高效执行

1. 普通开发不使用 Task、待办或进度工具记录模型内部步骤；只有用户明确要求规划、沉淀待办，或存在多个跨回合独立交付物时才使用。
2. 没有依赖关系的文件读取、检索和状态检查在同一模型回合并发发出。只有后续动作必须依据当前结果重新决策时才增加一次模型—工具往返。
3. 同一内聚改动集中完成；只有验证失败或新证据改变实现时才补充调查和编辑。
4. 编辑完成后使用一个失败即停的组合命令运行相关测试、静态检查、`git diff --check`、任务范围 diff 和状态核对。
5. 验证通过后使用一个组合命令精确暂存、核对 staged diff、提交并检查最终状态；不得暂存范围外改动。
6. 没有代码、配置、测试、用户范围或 Git 状态变化时，不重复读取同一文件或重复执行相同状态查询。
7. 进度更新只在提供新事实、风险或决定时发送，不为“仍在执行”制造额外模型调用。

## 6. 提交

1. 一个内聚任务默认只创建一个完整、可验证的 Conventional Commit，不按文件、编辑批次、测试轮次或代理拆提交。
2. 最低验收通过且无阻断后提交精确任务差异，不夹带历史修改，不提交未通过测试的代码。
3. 提交前检查完整 staged diff、未跟踪文件和 commit message；主题应准确描述结果，不添加 Nova 编号、trailers、Review 状态或审计元数据。
4. 尚未共享的本地提交需要同范围修正时，可在安全且符合用户意图时 amend；已经共享或无法安全改写时追加普通修正提交。
5. 默认不启动 Review。用户明确要求时才加载 `nova-review`；Review 修复是否提交服从 Review SOP。
6. 全局规则代表精确范围本地 commit 的持续授权；用户明确“不提交”只撤回当次授权。push、远程配置、发布和 SVN commit 始终需要独立授权。
7. 用户明确要求设计或待办时，验收完成后在同一任务删除蓝图中的对应待开发条目；设计文件保留，不写 Review 状态。

## 7. Plan mode 追加约束

Plan mode 只由用户启用：

- 走 Research → Create Plan → Obtain Approval → Execute → Verify；方案未经用户审批不得编码；
- Research 先读相关代码、测试和配置，再读蓝图公共约束及其精确架构链接；存在当前设计链接时只读取对应设计和直接依赖；
- Open Questions 只保留会改变实现且无法由证据消解的真实差量，不为满足格式强行制造问题；
- 计划列出范围、接口与数据边界、失败恢复、依赖、验收和明确不做；
- 涉及持久化时从项目最终生效配置解析存储位置，不写死默认路径；
- Execute 仍按默认流程测试和提交；Plan mode 不自动启动 Review；
- Verify 只读核对固定范围、验收矩阵、有效测试证据、工作副本和本地提交，不重跑未失效测试、不重新研究已确认问题、不扩大范围。

## 8. 完成报告

完成报告不是过程日志：

1. 首段直接说明实际完成了什么可观察结果；
2. 随后明确刻意没有修改的范围；
3. 列出关键文件及各自作用；
4. 列出测试命令、工作目录、结果、覆盖验收、复用证据和未验证项；
5. 列出本地 commit hash 与主题、精确提交范围，以及 push、发布或 SVN 是否执行；
6. 列出遗留风险和具体下一步；没有则明确写无。

缺陷恢复必须说明修复前的可复现偏离和修复后结果；主动局部调整应说明行为边界；维护应说明产品行为是否保持不变。报告只受本提示约束，不创建候选报告文件，不调用文本模板或 Schema 校验器。
