# Nova 功能开发

让用户按自己的思路描述。AI 先研究项目事实；请求明确时直接开发，只有会实质改变当前交付且阻塞实现的歧义才澄清。

## 自动路由与有限加载

1. 先从用户明确路径、当前请求指向的仓库或可信会话状态确定目标项目；不得只因当前目录存在蓝图就假定它是目标项目。
2. 读取项目规则和 `.nova/PROJECT_BLUEPRINT.md`。蓝图不存在时转入 `nova-architecture` 初始化，完成后回到本技能。
3. 从蓝图取得技术栈、代码落位、模块职责、公共约束和架构导航，只沿与本次改动直接相关的精确链接读取详细架构。
4. 禁止扫描、枚举、通配匹配或索引 `.nova/design/`。只有蓝图“待开发工作”对当前任务给出精确设计链接时才读取对应设计章节及其直接依赖。
5. 围绕当前主题定向研究代码入口、直接调用方、权限、存储、失败恢复、配置和测试；实现事实以代码、测试、迁移和配置为准。
6. 现有架构不足，或目标要求改变技术栈、模块职责、依赖方向、共享数据所有权、公共 API、事件、基础设施或运行边界时停止实现；只有用户主动调用或明确授权修改共享架构后，才转入 `nova-architecture`。
7. 不以“核对需求”为由运行例行需求访谈、扫描需求文档或扩大范围。

## 不可违反

1. 能从代码、配置、测试、蓝图或指定参考源查明的事实先研究，不让用户代替检索。
2. 区分用户已确认、证据已查明、AI 候选建议和待确认差量；未经用户接受的候选不得写成正式要求。
3. 每轮最多一个问题，只确认一个会改变当前实现的信息维度；已有明确请求且证据足够时不得形式性提问。
4. 蓝图只保存长期共享的项目和架构事实；用户主动要求的局部设计进入 `.nova/design/*.md`；当前实现仍以代码和测试为准。
5. 用户可见回复必须移除推理草稿、规则自检、代理身份、工具过程、孤立人名和无上下文英文。
6. 取得有效答案后重新计算当前范围的差量；无阻塞差量时直接执行下一动作，不只报告“下一步”或再次要求用户说“继续”。
7. 不创建需求块、工作项编号、交付台账、审计、检查点、迁移状态、Review 状态或 Nova commit trailers。

## 研究与澄清

只有出现真实歧义时完整读取 [共享澄清 SOP](references/conversation-sop.md)。Architecture 与 Development 必须使用这一套提问、选项、委托、确认、中断和恢复语义，不得在本技能另造简化版。

开发阶段只询问同时满足以下条件的差量：属于当前请求，会改变用户可见行为、范围、数据语义、接口、安全、失败语义或验收，直接阻塞下一可执行动作，且无法由项目证据或用户委托消解。后续工作、可选优化和不阻塞当前动作的问题不得提前提问。

发现可能复用的能力时，先读取存在时的 `.nova/SHARED_CAPABILITIES.md`，再定向检查相关代码和测试；目录缺失或未命中不能直接断言不存在。已有能力说明复用入口和边界。用户已确认且本轮实现的共享能力通过最低验收后，按需创建或更新该目录；候选和未完成入口不得登记，最后一项退役时删除文件。新增共享技术栈、层、依赖、数据所有权或公共契约必须返回 Architecture；普通辅助代码、一次性布局和业务专属规则不得因想象中的复用而扩大范围。

用户显式引用成熟平台、标准、最佳实践、产品或仓库，或把安全、身份、公共契约等高风险事项委托给 AI 时，完整读取 [外部参考研究 SOP](references/reference-research-sop.md)。参考事实与本项目建议分开呈现；产品名只是例子时不形成产品专属依赖。

## 设计与待开发工作

普通开发不创建设计文档或待办。只有用户明确要求“设计”“规划”或“沉淀待办”时：

1. 完整读取 [设计文档规范](references/design-document-standard.md)，新建时使用 [设计模板](assets/DESIGN.template.md)。
2. 设计文件命名为 `.nova/design/YYYY-MM-DD_<具体名称>.md`，只记录目标、范围、契约、失败恢复、复用点和可执行验收，不记录开发流水。
3. 写入前按共享澄清 SOP 展示整份设计摘要、目标文件和蓝图引用变化，并取得用户明确确认。
4. 在蓝图“待开发工作”用可读名称精确链接对应设计章节，不生成专有编号，不记录 Review 状态。
5. 实现完成并满足验收后删除蓝图中的对应条目；设计文件保留。完成动作不依赖 Review，也不扫描其他设计。

## 实施与交付

编码前完整读取 [实施与交付 SOP](references/implementation-sop.md)。本技能负责固定任务差异和验收、实现正常与失败路径、运行风险相称的验证、保护既有工作树、精确本地提交和完成报告。

### 高效执行

- 普通开发不使用宿主 Task、待办或进度跟踪工具记录内部步骤；只有用户明确要求规划、沉淀待办，或任务包含多个需要跨回合跟踪的独立交付物时才使用。
- 只有后续动作必须依据当前结果重新决策时才增加模型—工具往返。没有依赖关系的只读操作在同一模型回合并发发出，不为进度汇报、重复确认或扩大扫描单独调用工具。
- 同一内聚改动一次完成；只有验证失败或新证据改变实现时才补充调查和编辑。
- 完成编辑后用一个失败即停的组合命令运行相关测试、静态检查、`git diff --check`、任务范围 diff 和状态核对；验证通过后，再用一个组合命令精确暂存、检查、提交和核对最终状态。
- 没有代码、配置、测试结果、用户范围或 Git 状态变化时，不重复读取相同文件，也不重复执行相同的 `status`、`diff` 或 `log`。

默认不启动 Review。只有用户明确要求时才转交 `nova-review`。不得自动 push、发布、修改远程或提交 SVN。

## 完成报告

首段直接说明实际完成的行为结果，随后明确刻意没有改什么，再列关键文件、测试命令与覆盖、未验证项、本地提交 hash 与主题、精确提交范围、远程操作状态、遗留风险和下一步。报告不是过程日志，不生成或校验临时报告，不把自检和测试称为 Review。
