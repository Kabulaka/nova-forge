# Nova 功能开发

让用户按自己的思路描述。AI 先研究项目事实；请求明确时直接开发，只有会实质改变当前交付且阻塞实现的歧义才澄清。所有实现结果在用户明确发起 Commit 前保持未提交。

## 路由与有限加载

1. 从用户明确路径、当前请求指向的仓库或可信会话状态确定目标项目；不得只因当前目录存在蓝图就假定它是目标项目。
2. 在同一准备批次读取项目规则和 `.nova/PROJECT_BLUEPRINT.md`，并检查固定旧入口 `.nova/SHARED_CAPABILITIES.md`。蓝图不存在时转入 `nova-architecture` 初始化；蓝图缺少“开发导航”或旧入口仍存在时停止，说明迁移需求，只有用户显式调用 Architecture 后才迁移。
3. 从蓝图取得技术栈、代码落位、模块职责和公共约束，再用第六章“开发导航”的触发条件筛选当前请求；只沿命中条目的精确入口读取详细契约、代码和测试。
4. 禁止扫描、枚举、通配匹配或索引 `.nova/design/`。只有蓝图“待开发工作”为当前任务给出精确设计链接时才读取对应设计章节及其直接依赖。
5. 围绕当前主题定向研究代码入口、直接调用方、权限、存储、失败恢复、配置和测试；实现事实以代码、测试、迁移和配置为准。涉及持久化时从最终生效配置解析存储位置，不写死默认路径。
6. 现有架构下没有明确合规实现，或目标必然新增、删除项目级模块或技能，改变项目级模块或技能的对外暴露集合、技术栈、模块职责、依赖方向、共享数据所有权、公共 API、事件、基础设施或运行边界时属于硬冲突，必须停止实现；即使变化较小或可逆，也不得由 Development 自行修改蓝图或共享架构。单一模块内新增普通用户功能且不改变共享边界时仍由 Development 直接实现。硬冲突只可让用户选择显式调用 `nova-architecture`，或修改、放弃冲突需求，冲突解除前不得编码。
7. 不以“核对需求”为由运行例行需求访谈、扫描需求文档或扩大范围。

## 研究与澄清

能从代码、配置、测试、蓝图或指定参考源查明的事实先研究，不让用户代替检索。区分用户确认、证据查明、AI 候选和待确认差量，未经接受的候选不得写成正式要求。

只有出现真实歧义时完整读取 [共享澄清 SOP](references/conversation-sop.md)。Architecture 与 Development 必须使用同一套提问、选项、委托、确认、中断和恢复语义，不得在本技能另造简化版。

开发阶段先完成定向研究，再在首次编辑前重新计算待确认差量。只询问同时满足以下条件的差量：属于当前请求，会改变用户可见行为、范围、数据语义、接口、安全、失败语义或验收，且无法由项目证据或用户委托消解。符合这些条件的差量一律阻塞首次编辑，不得以仍可先写脚手架、局部代码或测试为由继续。硬冲突，或轻量架构闸门认定的“命中”“未知”，同样阻塞首次编辑。每轮最多一个问题；请求和证据足够时不得形式性提问。得到有效答案后重新计算差量，无阻塞时直接继续，不只报告下一步或要求用户再说“继续”。

已有共享能力只沿蓝图命中入口复用；导航无命中不能断言能力不存在。Development 不修改蓝图架构事实或开发导航，也不自动调用 Architecture；发现缺失、过时、冲突或架构收益时按下述闸门中断，由用户显式决定是否调用 Architecture。

## 轻量架构闸门

首次编辑前，使用已经读取的蓝图和本次定向研究结果完成一次架构判断；不得为此新增目录扫描、MCP、外部研究或独立技能调用。依次检查模块职责与依赖、公共 API/事件、数据所有权与一致性、共享安全机制、运行基础设施、跨模块能力以及失败恢复。每项只可判定为“命中 / 不命中 / 未知”，未知不得降级为不命中。

只有以下条件全部取得正向证据时才可判定“不命中”并直接开发：当前能力由单一模块所有；不改变公共接口、事件、数据所有权、依赖、基础设施、安全或恢复；以后抽取只需移动私有代码和调整内部导入；从项目定位、现有模块和当前需求无法推导其他现实复用场景；该选择不需要其他独立开发者共同遵守。不得以“当前没有第二个消费者”“以后再说”“可能不会复用”或“只是猜测”替代证据。

当前需求违反既有架构，或实现必然改变共享边界时，按前述硬冲突处理，不得提供“保持现有架构开发”这一不可执行选项。只有已经找到明确的现有架构合规实现时，才继续判断架构收益：存在现实复用场景且延后决定可能导致数据迁移、公共契约兼容、模块所有权调整、依赖倒转、多个调用方修改或安全/恢复语义重做时判定“命中”；证据不足以排除这些风险时判定“未知”。命中或未知都必须在编码前中断，一次说明该合规实现及其具体成本、候选架构调整、现实或潜在复用场景、延后后的返工、收益和成本，只让用户决定“显式调用 Architecture 调整”或“保持现有架构合规实现”。用户选择保持后冻结当前任务决定，除非新证据改变共享边界，不得重复询问。

架构判断必须并入原本的首次开发更新，不新增一次模型往返：不触发时用一行覆盖单一所有权、无公共边界变化、局部可逆、无项目事实可推导的其他复用场景，以及无需独立开发者共同遵守这五项正向证据；触发或未知时按上一段中断。用户明确选择调整架构才构成 Architecture 的执行授权；Development 不得自行修改架构后继续。

用户显式引用成熟平台、标准、最佳实践、产品或仓库，或把安全、身份、公共契约等高风险事项委托给 AI 时，完整读取 [外部参考研究 SOP](references/reference-research-sop.md)。参考事实与项目建议分开呈现；产品名只是例子时不形成产品专属依赖。

## 设计与待开发工作

普通开发不创建设计文档或待办。只有用户明确要求“设计”“规划”或“沉淀待办”时：

1. 完整读取 [设计文档规范](references/design-document-standard.md)，新建时使用 [设计模板](assets/DESIGN.template.md)。
2. 设计文件命名为 `.nova/design/YYYY-MM-DD_<具体名称>.md`，只记录目标、范围、契约、失败恢复、复用点和可执行验收，不记录开发流水。
3. 写入前按共享澄清 SOP 展示整份设计摘要、目标文件和蓝图引用变化，并取得用户明确确认。
4. 在蓝图“待开发工作”按 `开发触发条件 | 待开发内容 | 交付结果 | 设计入口` 增加一行，设计入口精确链接对应章节；不增加状态、负责人、优先级、排期、进度、Review 或审计字段。
5. 实现完成并满足验收后删除蓝图中的对应条目，设计文件保留；完成动作不依赖 Review，也不扫描其他设计。

## 任务范围与基线

1. 根据用户目标、蓝图公共约束、相关设计和项目证据固定本次范围、验收矩阵与未验证事项。任务必须有完整结果和验收；多个步骤只有共同完成才有价值时视为同一内聚任务，不按阶段、文件、模块、代理或工具批次拆分。
2. 首次编辑前记录仓库根、Git/SVN 状态、任务路径或模块，以及范围内既有修改和未跟踪文件。相关路径已有修改时，基线必须足以区分同一文件的新旧行块；只有文件名或哈希不够。
3. 当前任务差异只含相对任务开始基线由本任务新增、修改或删除的路径与行块。历史未提交内容不得因出现在 diff 或未跟踪列表中自动纳入。
4. 无法可靠分离时停止编辑，请用户选择独立 worktree/checkout、明确扩围或先处理既有变更。不得覆盖、回退、暂存或提交用户已有修改。
5. 上下文压缩、自检、Review 或续接不得重建基线。用户明确扩围时，在新增范围首次编辑前补充基线和验收。
6. 编码前清空会改变行为、契约、安全或数据语义的歧义；真实共享架构冲突必须停止并返回 Architecture，不得静默修改公共架构。

## 编码前契约

在模型内部固定与风险相称的变更说明，不为复述流程单独增加一轮：

1. **接口契约**：输入、输出、错误语义、兼容性、状态变化和跨调用边界的权威定义；
2. **核心不变量**：必须始终成立的数据、状态、权限、资源或顺序约束；
3. **变更闭包**：修改点、直接调用方、消费者和受影响模块；
4. **失败语义**：关键失败点、恢复、重试、回滚、清理和错误传播责任；
5. **资源生命周期**：所有权、并发、取消、超时、释放和重复执行语义；
6. **验收标准**：每条关键契约和不变量对应的可执行验证；
7. **分层落位**：新增或移动入口符合蓝图目录、职责与依赖方向。

纯文档、格式或无运行时语义的机械维护只固定目标、精确范围和最低验收，不虚构运行时契约。缺少代码落位，或需要新增技术栈、层、共享依赖、数据所有权或公共契约时停止并返回 Architecture。

## 编码约束

- 正常路径和失败路径同时实现，不让测试替代异常语义；
- 在输入、接口和资源边界主动保证契约，不依赖调用方自觉传入合法值；
- 同一业务契约在前端、API、服务、任务和持久化边界保持允许输入、状态转换和错误语义一致；
- 上游校验只用于提前反馈，不能替代权威执行层的独立校验；
- 每个副作用都定义失败后的状态、补偿、清理和错误传播；
- 修改接口、状态或资源边界时同步检查直接调用方、消费者及恢复路径；
- 不得通过放宽校验、吞错、静默替换默认值或空值、改变既有语义或削弱断言迁就实现；
- 测试不得反向修改已确认方案；发现设计缺陷时先补全契约与失败语义；
- 模块业务数据和 Repository 由模块所有；共享层只承载已确认的公共机制，不得形成万能层；
- 新依赖必须使用项目既有权威依赖清单和管理器，不得私自绕过；
- 同一失败重复且没有新证据或新方案时停止，报告证据、尝试和阻断点。

## 测试与证据复用

1. 测试逐条覆盖固定验收的正常路径、失败路径和关键边界。同一业务契约存在多个调用边界时，使用共享用例或等价断言确认语义一致。
2. 测试发现设计未覆盖的缺陷时，先补全契约和失败语义，再修复实现；不得临时发明业务规则。
3. 首次测试后保留命令和工作目录、覆盖的验收项、相关内容与环境状态、结果和未验证事项。
4. 只有相关内容或环境变化、覆盖不足、结果失败或不完整，或用户明确要求重跑时，证据才失效。压缩、续接、自检、Review、阶段变化和无关文件变化不使结果失效。
5. 证据有效时后续自检、Review 和完成核对必须复用；失效时只重跑受影响测试，仅当影响无法限定或验收要求全量时才运行全量测试。
6. 测试通过不等于 Review PASS；用户没有明确发起 Review 时不得使用 Review 结论措辞。

## 高效执行

1. 优先用一个准备批次读取本技能、蓝图精确链接、Git/SVN 基线、目标代码、直接调用方和相关测试；宿主没有批量工具时，在同一模型回合并发读取。不得先扫描整个仓库或设计目录。
2. 从准备结果在模型内部固定契约、变更闭包和验收，不输出内部计划或等待形式性确认；只有真实歧义、架构冲突、范围不可分离或用户要求的流程分支才能中断。
3. 同一内聚改动集中完成正常路径、失败路径和相关测试；只有验证失败或新证据改变实现时才补充调查和编辑。
4. 编辑后使用一个失败即停的验证批次运行风险相称的测试、静态检查、`git diff --check`、任务范围 diff、未跟踪文件和状态核对。每项保留独立退出状态；失败时只处理实际失败项，不重复未失效证据。
5. 不用 Task、待办、进度工具或子代理记录内部步骤；事实和状态未变化时不重复查询，只在有新事实、风险或决定时更新进度。
6. 验证完成后保留精确任务差异，不暂存、不提交，也不自动启动 Review 或 Commit。

## 完成报告

报告先说明实际行为结果和刻意未改范围，再列关键文件、测试命令与覆盖、未验证项、遗留风险和下一步。缺陷恢复说明修复前偏离和修复后结果；主动调整说明行为边界；维护说明产品行为是否保持不变。报告不是过程日志，不生成或校验临时报告，不把自检和测试称为 Review。

简单示例：

```text
完成：新增订单取消能力，并覆盖重复取消和非法状态。
验证：npm test，18/18 通过。
改动：src/order.ts、test/order.test.ts
状态：改动未提交；未启动 Review。
```
