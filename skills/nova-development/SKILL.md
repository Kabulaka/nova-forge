# Nova 功能开发

让用户按自己的思路描述。AI 在后台维护关系、证据和影响范围，前台只呈现当前结论和一个最小问题。

## 自动路由与有限加载

技能名称不决定用户意图。首次只读用户表达、`.nova/PRODUCT_REQUIREMENTS.md` 的需求索引、`.nova/PROJECT_BLUEPRINT.md` 的技术/模块摘要及活动工作索引；不得为了判断路由扫描需求块、设计正文、共享能力目录或代码树。

- 无需求文档、无代码且无蓝图：转入 `nova-requirements`，需求确认后再进入 `nova-architecture`，不得直接生成开发设计。
- 已有代码和蓝图但无需求文档：只询问是否补建需求层；用户拒绝时继续普通功能/FIX，不把缺少需求文档当阻断。
- 新增或改变业务目标、角色、流程、权限、状态、业务规则或范围：转入 `nova-requirements`。需求确认后由用户选择是否进入本技能澄清具体实现。
- 技术栈、共享数据所有权、公共 API、事件、基础设施或跨需求并行契约未定或将改变：转入 `nova-architecture`。
- 用户已指明需求块或索引能唯一定位：只读取索引和目标需求块，再读取目标蓝图约束；功能设计记录 `Requirement-Ref: REQ-...@vN`。
- 既有契约内的局部缺陷：直接分类为 FIX，不读取需求正文。无法判断是否改变业务契约时只问一个路由问题。

进入本技能后，不以“核对需求”为由扩大 Review 或实现范围。发现共享架构契约不足时停止功能设计并返回 `nova-architecture`，不得由单个功能静默修改 `.nova/architecture/`。

## 不可违反

1. 每轮最多一个问题，只确认一个信息维度；用户应能用短语或一句话回答。
2. 能从代码、配置、测试、运行契约或指定参考源查明的事实先研究，不让用户代替检索。
3. 区分“已确认”“证据推断”“待确认”，未经用户接受的推断不得写成正式要求。
4. 蓝图只保存所有模块长期共用的事实；史诗与工作包设计进入 `.nova/design/*.md`；当前实现以代码、测试、迁移和配置为准。
5. 一个史诗可含多个相关工作包，蓝图待办可引用同一设计的不同稳定章节；没有共享语义时拆分设计。
6. 用户可见回复必须移除推理草稿、规则自检、代理身份、工具过程、孤立人名和无上下文英文；写正式要求或扩大范围前必须取得确认。
7. 每次取得有效答案后重新计算待确认差量和研究任务；任一未清空时不得宣称话题收敛，已确定下一动作时不得只报告“下一步”而不执行。文本与原生提问工具适用同一状态语义。
8. AI 只能形成候选收敛；用户明确确认整份最终摘要后才可标记已确认。讨论过、要求开发、普通“继续”、空答案、取消或部分答案均不得代替确认。
## 1. 先定位项目，再加载上下文

先从用户明确路径、当前请求指向的仓库或已确认会话状态确定目标项目。只因当前目录存在蓝图，不得把它当成目标项目。未能安全确定且不同路径会改变结果时，只问项目位置。项目治理蓝图固定为 `.nova/PROJECT_BLUEPRINT.md`。

若检测到根目录 `PROJECT_BLUEPRINT.md`、`PRODUCT_REQUIREMENTS.md` 或 `docs/design/`、`docs/audit/`、`docs/requirements/`、`docs/architecture/` 等旧布局，完整读取“布局迁移”小节并先执行 `scripts/migrate_nova_layout.py --repo <根目录>` dry-run。展示精确移动、引用改写、冲突和 `Plan-SHA256` 后必须再次取得用户明确批准，才能执行 `--apply --plan-sha256 <已批准摘要>`；不得覆盖、保留重复实体或把布局迁移与内容模板升级混为同一步骤。

会话内维护：目标根目录绝对路径、蓝图绝对路径、规范版本、蓝图 SHA-256、已加载的项目指令、访谈 SOP SHA-256，以及本路由已加载的项目文档和技能文档资源状态。资源状态按目标项目绝对路径、资源绝对路径和 SHA-256 隔离。用户无需管理这些状态。

### 实施请求前置路由

用户明确要求实施某个编号时，此路由优先于下述首次进入和蓝图版本路由。先读取目标项目指令并检查精确蓝图路径，再以编号或稳定锚点定向读取目标条目；不得在确认交接资格前把蓝图全文展开到模型上下文。条目具有已确认设计依据和可执行验收标准，且版本 `5` 设计具有与当前语义一致的收敛确认时，再定向读取所引工作包、直接依赖和本任务实际涉及的公共约束，并按“已确认工作包的实施交接”执行。目标条目无法定位、仍为“待澄清”、设计依据缺失、验收不可执行、版本 `5` 收敛确认缺失或失配、或契约冲突时，退出实施路由并转入单问题澄清；只有无法通过定向读取判断阻断原因时，才按首次进入和版本路由补读必要范围。既有版本 `4` 设计保持交接兼容，但任何语义修改必须升级到版本 `5` 并重新确认整份设计。

### 首次进入或状态失效

未命中实施请求前置路由且发生任一情况时，先读取目标项目指令并检查精确蓝图路径是否存在。蓝图不存在时记录“无蓝图”，不得对不存在的文件计算 SHA-256 或要求全文；蓝图存在时，从同一份稳定快照取得全文、版本与 SHA-256：

- 新会话首次进入目标项目；
- 切换项目或蓝图路径；
- 没有可信的会话内理解；
- 当前 SHA-256 与记录不同。

对已存在蓝图，在读取前后分别计算 SHA-256；两次不一致时丢弃正文并重新读取，连续变化无法取得稳定快照时停止并报告，不绑定旧理解与新哈希。首次向用户提问前，完整读取一次 [访谈 SOP](references/conversation-sop.md) 并记录其 SHA-256。除已保存实施交接且其列明的失效条件均未发生外，上下文丢失时按首次进入处理，不猜测旧状态。

### 同一会话续问

每次继续访谈前，先用不向模型上下文展开正文的方式计算当前蓝图与访谈 SOP SHA-256。项目、路径、蓝图指纹和 SOP 指纹均未变化时，复用已有理解，只读取尚未加载或指纹变化的当前待办、相关蓝图章节、设计元数据、当前工作包及其直接依赖；不要重读完整蓝图或访谈 SOP。代码影响分析表明范围扩大时，再补读受影响部分。

蓝图指纹变化时立即废弃旧理解并完整重读；SOP 指纹未记录或发生变化时只完整重读访谈 SOP，保留已确认的项目理解。任一文件读取前后指纹不一致时重新读取，连续变化则停止并报告。本路由加载的项目文档和技能文档资源在同一项目的路径和 SHA-256 未变化时复用，变化时只失效受影响资源；一次完整读取是一个逻辑任务，不得先 `wc` 再按固定行数串行重读，只有工具明确截断时才从未返回位置补读，不得读取超过已知文件末尾的空区间。无法可靠判断目标路径、文档存在性、设计有效性或资源指纹时，不得按“不存在”处理、加载示例或写入缓存；先用路径、链接和头部元数据缩小候选，仍会改变设计语义时停止并只确认一个差量。不得跨会话或跨项目复用缓存，也不得为读取资源修改插件、hook 或宿主 UI。

## 2. 按蓝图版本路由

未命中实施请求前置路由时，首次进入或缓存失效必须先完成上一节的文件存在性检查；蓝图存在时再完成稳定快照全文读取并按已读版本分流，不得用单独读取版本标记替代首次完整读取。同会话缓存有效时使用已记录版本：

- 不存在蓝图：若属于绿地项目先转入 `nova-requirements`；已确认需求且正在建立架构时转入 `nova-architecture`；普通遗留项目功能开发可继续，不加载蓝图版本迁移 SOP。
- 明确为版本 3：正常澄清和只读分析不加载迁移 SOP；用户明确要求迁移审计时例外。当前待办、当前设计或校验结果出现旧式设计文件名时，只读取设计规范并执行其中的“旧式文件名迁移”，不进入七章蓝图迁移决策门。
- 已存在蓝图但版本标记缺失、版本不是 3，或用户明确要求迁移审计：完整读取 [迁移 SOP](references/blueprint-migration-sop.md)，进入迁移决策门。

旧版蓝图不得套模板覆盖。迁移决策门必须先完成迁移报告：逐项列明新版七章职责，并按原标题或摘要列出每段待归档局部内容，不得用概括句替代证据清单；然后只询问“先澄清后升级、立即升级、暂不升级”这个三选一决定。用户明确选择前，禁止追问待办功能、加载蓝图规范、创建或修改文档、运行校验器；不得替用户决定“本轮不迁移”。选择后的处理严格按迁移 SOP，且每轮仍只询问一个差量。

## 3. 研究与澄清

已有代码库时，围绕当前主题研究入口、模块边界、直接调用关系、权限、存储、失败恢复和测试；冲突标为待确认。

开发阶段按统一 SOP 生成 `stageProjection`：`inheritedContracts` 只引用进入本阶段前已正式确认且与当前工作包相关的需求和已就绪架构契约，并保留其需求或架构来源阶段；`stageEvidence` 只保存本阶段从代码、配置、测试和运行契约查明的事实；`stageDecisions` 只保存本阶段新增且已披露的功能实现候选。不得把上游内容冒充开发澄清；代码证据与继承契约冲突时，暂停设计或实施，按 `inheritedContracts` 来源返回需求或架构阶段重新确认，无冲突项保持有效。

### 共享能力发现与决定

澄清当前功能时，先查 `.nova/SHARED_CAPABILITIES.md`，再定向研究相关共享目录、代码和测试；目录缺失或没有命中不证明能力不存在。发现已有能力时说明复用入口和边界，不重复建设。发现边界清晰、可能跨页面或模块复用，或统一实现能显著降低复杂度、安全或一致性风险的候选时，向用户说明当前需要、可能复用场景、收益、本次成本与影响并给出建议，只确认“本次共享建设 / 当前局部实现 / 局部实现但保留抽象边界”一个决定；普通辅助函数、一次性布局和纯业务语义不升级为共享候选。

用户确认共享建设后才把抽象范围、分层落位和验收写入当前设计。现有蓝图已定义共享代码区域、系统分层和允许依赖时可在当前工作项实现；需要新增技术栈、层、共享依赖、数据所有权或公共契约时停止功能设计并返回 `nova-architecture`。目录只登记已实现且通过最低验收的能力，候选和计划留在设计中。

用户显式引用成熟平台、标准、最佳实践、产品或仓库，或把安全、身份、公共契约等高风险事项委托给 AI 时，完整读取 [参考研究 SOP](references/reference-research-sop.md)。范围明确且支持子代理时，启动一个或多个只读探索子代理；主代理分离参考事实与本项目候选决定，并披露具体决定、依据、影响、不采用内容和证据缺口。宽泛的“类似某产品”先问一个范围问题；产品名仅作为研究例子时不得形成产品专属规则。

AI 结合已确认上下文发现候选做法时，只有准备把它作为已验证的成熟/最佳实践，才进入同一研究 SOP；普通低风险内部取舍只标为可修正的 AI 候选，是否包含多个直接依赖边界本身不触发研究，也不得声称为已验证实践。

开发阶段只询问属于当前交付切片、会改变功能行为、外部契约、安全边界或数据语义、直接阻塞下一可执行动作且无法由证据和委托消解的差量。当前交付切片由活动工作项、验收范围和下一可执行动作限定；`PEND-*` 还绑定正式工作包及已有里程碑，`FIX-*`/`MAINT-*` 不创建工作包或里程碑。技术子步骤完成不使切片闭环。后续工作项、后续里程碑和只影响未来实现的差量一律暂存，不得进入当前问题队列。

用户委托范围内的普通低风险内部实现由 AI 决定并在整份摘要中披露，不逐项提问；“按行业通用做法处理”等委托只覆盖当前被问差量和当前交付切片，不授权打开后续阶段。委托不能授权单功能静默修改共享架构，也不能代替用户最终确认。用户指出跑偏、要求先完成当前阶段或按既定顺序推进时，视为范围纠偏中断：立即移出越界差量并继续当前下一可执行动作，不再询问是否返回、是否继续或是否重新确认当前范围。

沿当前语境选择影响最大且证据不足的一个差量。用户谈 A 时涉及 B，只有 B 会改变 A 的当前含义才立即问，否则暂存。逐轮闭环目标、参与者、触发、结果、权限、状态、边界、失败恢复、明确不做和验收证据；不要按文档章节审问用户。

架构讨论来自已确认场景、失败语义和非功能要求。必须澄清代码结构、系统分层、目录映射和依赖方向；模块自己的业务表结构、查询和 Repository 仍由模块所有，但其代码位置及依赖必须服从蓝图分层。内部实现细节可由开发时分析，不用提前写成长说明。

### 已确认工作包的实施交接

任何 `PEND-*`、`FIX-*` 或 `MAINT-*` 实施开始前，完整读取 [实施与交付 SOP](references/implementation-sop.md)。本节只定义与需求/设计状态衔接的增量规则，不替代其中的任务差异基线、编码契约、测试证据、提交、plan mode 或完成报告约束。

用户明确要求实施某个编号，且蓝图条目具有已确认设计依据和可执行验收标准，并满足目标设计版本对应的收敛确认门禁时，进入实施交接，不重新运行需求访谈。只读取该条目、所引工作包、直接依赖和本任务实际涉及的公共约束；复用当前可信的项目、路径和指纹状态，不重读完整蓝图、访谈 SOP 或已闭环关系。本技能负责固定最小上下文、快速实现、最低验收和待 Review 交接；用户明确启动 Review 时再转交 `nova-review`。

本轮从需求澄清新建正式 `PEND-*` 时，只要用户未把任务限定为仅头脑风暴、澄清、规划、蓝图、设计或文档，当前不处于尚待方案批准的 Plan mode，且用户已明确确认整份最终摘要、工作包已确认、蓝图引用与可执行验收完整、版本 `5` 收敛确认有效、蓝图和设计校验通过，就自动进入同一实施交接；不要求用户在原始请求中再次说“实施”或报出新编号。不得以仅交付文档的回复结束当前执行周期，也不得再次询问是否开始编码；立即完整读取实施 SOP、固定任务差异基线并按默认实施流程推进。用户明确暂停或取消、上述范围限制、待确认差量、研究证据不足、收敛确认缺失或失配、文档校验失败、契约冲突或无法安全隔离既有工作副本变化时停止；Plan mode 继续服从其方案审批门禁。

交接时固定任务编号、范围、设计依据、验收标准、设计语义指纹、未验证事项及 `activeDeliverySlice`；切片至少记录活动工作项、工作包、里程碑、验收范围、下一可执行动作和暂存范围，字段来源如下，不得为补齐切片而创建或虚构治理实体：

| 类别 | `workPackage` | `milestone` | 验收范围与下一动作来源 |
|------|---------------|-------------|------------------------|
| `PEND-*` | `Design-Ref` 指向的正式工作包 | 蓝图或设计已明确的里程碑；没有则 `none` | 已确认设计、工作包验收与实施计划 |
| `FIX-*` | `none` | `none` | 任务差异基线、固定验收矩阵与当前修复计划 |
| `MAINT-*` | `none` | `none` | 任务差异基线、最低验收与当前维护计划 |

上下文压缩、自检、显式 Review 或继续修改不使交接失效；技术子步骤完成也不使交接失效。每个子步骤完成后直接执行同一切片的下一可执行动作，不回到总体收敛矩阵，也不询问是否继续或是否进入后续工作项。只有目标路径、蓝图或排除状态字段后的设计语义指纹变化，用户明确扩围，或实现证据暴露契约冲突时，才重读受影响部分并重新计算当前切片内的差量。当前工作项按既定完成门禁闭环且下一工作项经明确路由后，暂存的后续范围才可成为新的当前切片。条目仍为“待澄清”、设计依据缺失、验收不可执行、版本 `5` 收敛确认无效或契约相互冲突时，不得实施；退出交接并按单问题规则只确认一个差量。

创建新工作项时，先按提交契约确定分类，再调用 `nova-review/scripts/nova_review.py new-id --class <分类>` 生成一次 UUIDv7 编号；既有数字编号只在原工作项未归档时继续沿用。编号一经进入蓝图或提交即固定，原范围开发、测试和 Review 修复不得重新生成或替换；可信审计归档后编号永久封存，后续缺陷使用新 FIX，能力或公共契约变化使用新 PEND，纯维护使用新 MAINT。

默认实施流程是编码、最低验收、记录有效测试证据和本地 Git commit。只有 `PEND-*` 的设计工作包在最低验收后更新为 `待Review`；`FIX-*`、`MAINT-*` 不创建蓝图条目或工作包。`Review-Policy: required` 的提交进入待审集合，合法 exempt 的 `MAINT-*` 以客观豁免证据直接完成。全局治理中的持续授权使精确范围本地 commit 无需逐次询问，用户明确要求不提交时只撤回当次授权。不得自动启动 Review。正式 `PEND-*` 在 Review PASS 前继续保留于蓝图，提交使用 `Change-Class: designed`、相同 `Work-Item` 和设计引用；用户测试后要求继续修改时，只有修正仍服务于原设计和验收才沿用同一编号。明确源于已归档 PEND 的新 FIX 必须写 `Related-Work-Item` 并用仓库感知校验确认该来源可信；新 PEND 以“演进来源”链接终态设计。push 和 SVN commit 必须另行授权。

用户明确要求 Review 时才加载 `nova-review`。Review 中断则保留 `待Review` 并返回调试；PASS 后由 `nova-review` 完成蓝图删除、设计终态和审计归档。Review-Defer、新增待办及无关蓝图变化不自动进入当前范围，也不得复用当前工作项；待审选择发现已归档编号承载新 commit 时必须在 Reviewer 启动前失败。

## 4. 形成文档

讨论结论满足任一条件时，提炼后写入蓝图：影响多个模块、模块职责或依赖方向、全局权限/安全/数据生命周期、公共外部契约、项目级非功能指标，或所有后续功能必须遵守。其余局部交互、流程、状态、失败恢复和验收只进入设计。

创建或升级蓝图前读取 [蓝图规范](references/blueprint-standard.md)，新建时使用 [蓝图模板](assets/PROJECT_BLUEPRINT.template.md)；只有目标项目不存在 `.nova/PROJECT_BLUEPRINT.md` 且正在首次创建蓝图时，才读取 [完整蓝图示例](references/examples/equipment-borrowing/.nova/PROJECT_BLUEPRINT.md)。创建或更新设计前读取 [设计规范](references/design-document-standard.md)，新建时使用 [设计模板](assets/DESIGN.template.md)，文件必须命名为 `YYYY-MM-DD_具体名称.md`；只有目标项目 `.nova/design/` 不存在有效设计且正在首次创建设计时，才读取 [关联设计示例](references/examples/equipment-borrowing/.nova/design/2026-08-25_设备借用闭环.md)。已有对应文档体系时只读取规范、模板和当前项目相关文档，模板不替代必要示例。

从需求块进入时，设计元数据必须保存该需求的稳定版本引用；不关联需求层的遗留功能或 FIX 写 `Requirement-Ref: 无`。`PEND-*` 与 `REQ-*` 分别表示交付和长期需求，不得互换或从 Key 推导工作项编号。

`已实现`、`已废弃`设计是终态历史快照。新需求即使基于原功能，也不得向终态文档追加工作包或改回非终态；必须用创建当天日期新建设计，并通过“演进来源”链接旧设计。候选来源先由当前需求、蓝图引用和已确认关系锁定，只读取其标题、规范版本、状态、演进来源和工作包等头部元数据；只有元数据不足以确认覆盖关系或存在契约冲突时，才定向读取相关共享契约、工作包和直接依赖，不读取仅主题相邻的旁支设计。只有同一史诗尚未终态时，关联工作包才可继续共用原文档。

一个工作包只有完成澄清并取得整份设计明确确认后才能成为蓝图中的有效设计链接。正常访谈在最终确认前不写设计；用户暂停或准备跨会话时，只在其同意保存后保留“澄清中”、收敛确认“待确认”的草稿，蓝图仍写“待澄清”。最终整设计确认问题必须同时展示自然语言摘要、目标文件和待办引用变化，并明确该次确认同时授权写入；用户确认后，新设计使用版本 `5` 并把确认绑定到语义指纹，直接写入并自动进入实施，不得再提出写入或开发确认。
设计要求先按同一对象和主题归集为唯一权威契约；六个维度只作覆盖检查，同一维度允许多个原子契约。无法唯一归一的相似、强弱、目标/上限或例外关系必须按单问题规则确认。工作包按完整功能能力而非技术层划分；多工作包设计必须包含唯一收口工作包及跨包组合验收。

`PEND-*` 工作包完成最低验收后标记为 `待Review`，正式待办继续留在蓝图；`FIX-*`、`MAINT-*` 不创建工作包。只有 `nova-review` 记录有效 PASS 后才从蓝图删除对应条目并把工作包标记为“已完成”；设计文档和稳定锚点始终保留。全部工作包完成或废弃且至少一个完成时，设计标记“已实现”；全部废弃或被整体替代时标记“已废弃”并链接替代来源。

## 5. 校验触发

以下操作完成后运行对应校验器：创建、修改或迁移蓝图/设计；新增、修改或删除共享能力目录；改变待办引用、工作包状态或文档生命周期；交付本轮已变更文档前。

```bash
python3 scripts/validate_blueprint.py /absolute/path/to/.nova/PROJECT_BLUEPRINT.md
python3 scripts/validate_blueprint.py --design /absolute/path/to/.nova/design/2026-08-26_example.md
python3 ../nova-architecture/scripts/validate_shared_capabilities.py --if-present /absolute/path/to/.nova/SHARED_CAPABILITIES.md
```

纯头脑风暴、继续提问、解释规则、读取项目和只读分析不运行校验器。校验不代替项目要求的测试、显式 Review 或提交门禁。

### 布局迁移

`scripts/migrate_nova_layout.py` 只迁移路径，不升级文档内容：

```text

PRODUCT_REQUIREMENTS.md -> .nova/PRODUCT_REQUIREMENTS.md
docs/requirements/      -> .nova/requirements/
docs/architecture/      -> .nova/architecture/
docs/design/            -> .nova/design/
docs/audit/             -> .nova/audit/
```

默认 dry-run 必须零写入。`--apply` 必须同时提供用户已批准的 `Plan-SHA256`；摘要覆盖移动实体与改写文件的路径、类型、模式、内容树及改写后字节，任一差异都拒绝执行。匹配后才使用 `git mv`，同步当前源码、配置与活动治理文档中的已知引用；版本 5 活动设计的路径变化同时确定性刷新收敛指纹，可信历史审计和终态设计正文保持原字节。改写先在同目录完整写入临时文件并原子替换，写入、替换或后置校验失败均恢复原字节、模式、Git 状态和本次目录；符号链接不作为文本跟随，回滚失败必须报告实际残留。
