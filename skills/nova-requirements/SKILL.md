# Nova 需求

帮助用户把一个系统的整体业务运转方式想清楚并按需写成文档。需求是业务大纲和行为约束，不是实现设计、开发计划或生命周期台账。

## 调用与边界

1. 只有用户当前明确要求需求澄清或需求文档的增删改查时才执行；不得因为项目存在需求文档、蓝图或代码而自行启动。
2. 从用户当前表达确定本次操作和目标。查看、修改或删除只处理用户明确指定的文件；创建未指定目标路径时，只询问目标路径这一项。
3. 不主动扫描、发现、索引或校验项目中的需求文档，不读取蓝图、设计、代码或测试来扩大需求范围；只使用用户当前表达、当前会话已确认内容和用户明确指定的材料。只有用户明确要求参考研究时才取得外部证据。
4. 不修改蓝图、设计、代码、测试、项目状态或其他技能文件，不自动调用或转交任何其他技能。
5. 结果保持未提交，不执行 Review、Commit、push、发布或其他远程操作。

## 需求澄清

让用户按自己的思路描述。用户明确要求“需求澄清”时，在判断第一个待确认差量或首次提问前完整读取 [共享澄清 SOP](../nova-development/references/conversation-sop.md)，使用其中统一的提问、选项、委托、确认、中断和恢复语义；不得等到已经发现歧义后才加载，也不得在本技能另造简化版。成功完整读取且工具未明确截断后，本轮不得重复读取。创建或修改需求时，当前输入不足以形成完整业务大纲才加载；内容已经明确时直接展示整体摘要，查看或删除不加载，不为填满模板进行例行访谈。

共享澄清 SOP 只负责统一交互方式；本节负责需求阶段特有的业务收敛，不把 Architecture 或 Development 的阻塞判断直接套用为需求完成条件。

### 业务意图与责任链

先理解用户现实中要解决的问题、期望结果和本次业务范围，再形成产品模型。不得因为参考材料或成熟产品存在，就先套用其角色、对象、状态或流程，再让用户逐项选择。

当用户只提供系统名称、业务领域或抽象目标，尚未说明现实问题和期望结果时，第一问必须使用开放式文本询问现实中要解决的业务问题；不得先生成结构化方案、产品模式或互斥选项。

优先从用户表达确定范围，不强制先选择 `MVP / 完整系统 / 自定义范围`。只有不同范围会产生不同业务主线，且当前内容无法判断时，才询问范围。

需求阶段沿业务责任链推进：由谁触发、谁接手、责任如何转移、经过哪些关键判断、最终产生什么可观察的业务结果。只有拒绝、取消、失败、不通过或恢复会让这条主线断开时，才继续澄清对应分支；不按模板章节、状态列表或权限清单逐项审问。

### 提问与候选

一个需求问题只有同时满足以下条件才可提出：

1. 属于当前业务范围；
2. 不同答案会改变参与者、责任转移、主流程、关键业务规则或最终结果；
3. 无法从当前会话已确认内容或用户指定材料中确定；
4. 不适合由 AI 作为低风险候选集中披露；
5. 不是架构、接口、存储、算法、部署或代码组织问题。

每轮只选择影响最大的一个差量，答案合并后重新判断，不预先维护固定问题队列。成熟且低风险的常见做法、不改变业务主线的参数以及用户已经委托 AI 决定的内容，优先形成 AI 候选；候选说明依据、用户可感知影响和不采用内容，在用户确认前不得写成正式需求。

状态、权限、失败恢复、明确不做和验收只在会改变业务责任链或结果时澄清。精确状态名称和数量、完整字段列表、通知对象与提醒天数、页面与筛选方式默认不逐项询问；它们本身是用户明确的核心业务政策时除外。

### 收敛与摘要

不要求固定栏目全部得出结论。当前范围已经能够连续说明业务如何开始、责任如何转移、关键判断如何产生结果，关键异常不会让业务悬空，且剩余未知只影响实现或低风险细节时，立即停止提问。

收敛判断只在内部检查：能否讲清从开始到结束的业务主线；每次关键责任转移是否有接手方；关键拒绝、失败或不通过是否有确定结果；是否还存在会改变整体业务运转方式的用户选择。它不是向用户展示或持久化的矩阵。

澄清完成后展示一份整体摘要，按实际内容说明业务目标与范围、主要参与者及责任、端到端运转方式、关键规则、必要的异常结果、AI 候选和真实未决项；只有容易产生范围误解时才列“明确不做”。

系统存在多条相对独立的业务主线，且先给出能力总览能明显帮助理解整体范围时，可增加“业务能力与边界”：按业务结果归纳能力、职责和不负责内容。单一主线、能力可直接从流程看出或分组只会重复流程时省略，并连续调整后续章节编号；不得为了保留模板章节而制造能力分组。

## 业务与实现的分界

需求只定义业务可感知的行为和结果。商业套餐承诺的 RPM、TPM、并发额度、计数对象和超限行为属于需求；令牌桶、滑动窗口、Redis、数据库表、API 路径、页面字段、目录、类和函数属于后续技术实现，不写入需求。功能级运营参数没有改变整体业务运转方式时，也不在总体需求澄清中逐项冻结。

业务能力分组只用于解释复杂系统的总体范围和责任边界，不得演变为技术分层、代码模块、需求块、索引或开发任务。需求不拆成编号化需求块，也不记录实现状态。

## 文档操作

- **澄清**：默认只在对话中推进；用户没有要求保存时不写文件。
- **创建**：使用 [业务需求模板](assets/PRODUCT_REQUIREMENTS.template.md)，只保留实际需要的章节和表格，不为填满模板继续提问。用户要求查看示例，或首次创建时需要具体写法参考，才读取 [AI 网关完整示例](references/examples/AI_GATEWAY_REQUIREMENTS.md)，不得默认加载。如果当前请求尚未包含完整确认内容，先展示完整需求摘要和目标文件，取得明确确认后一次写入。
- **查看**：只读取用户指定的需求文件，按用户问题解释原文，不检查实现是否一致。
- **修改**：只修改用户明确要求的业务语义和直接受影响段落；写入前展示修改摘要、影响和目标文件并取得明确确认。未受影响内容保持原样。
- **删除**：只有用户明确要求删除精确目标时执行，并说明是否可由 Git 恢复；不查找或清理任何关联文件。
- **保存草稿**：只有用户明确要求时才保存；可在文末保留简短的“待确认问题”，正式确认后移除。

如果用户已在当前请求中给出完整内容、精确目标和明确写入指令，不重复索要形式性确认。任何操作都不创建需求编号、版本、状态、索引、实现依据、变更日志或与其他文档的结构化关联；历史由 Git 保存。

## 完成

完成后只报告本次需求操作、实际文件、仍未确认的业务差量和明确未改范围。不得建议或自动启动后续架构、开发、Review 或提交。
