# Nova 需求文档规范

## 1. 职责与事实来源

`.nova/PRODUCT_REQUIREMENTS.md` 只保存总体业务主线、业务模块、范围和需求索引；`.nova/requirements/*.md` 保存一个独立交付需求块的完整业务定义。技术架构进入 `.nova/PROJECT_BLUEPRINT.md` 与 `.nova/architecture/`，实现细节进入 `.nova/design/` 和代码。

两个文档必须严格使用对应模板的一级/二级章节、元数据和表头，不增加同义章节。需求文档不写语言、框架、目录、API、表、缓存、MQ、类名或任务拆分。

## 2. Requirement Key 与版本

- Key 为小写规范 UUIDv7：`REQ-xxxxxxxx-xxxx-7xxx-[89ab]xxx-xxxxxxxxxxxx`，创建后永久不变。
- 文件名为 `REQ-<uuidv7>_具体名称.md`；名称可调整但索引链接必须同步，禁止日期副本。
- 需求版本为 `v1` 起递增整数。修改时把此前确认内容与新结论合并成完整当前定义，不保留原子差量或变更日志。
- 功能设计引用 `Requirement-Ref: REQ-...@vN`；工作项身份仍使用独立 `PEND-*`。

## 3. 状态

| 状态 | 唯一含义 | 索引约束 |
|------|----------|----------|
| 待实现 | 当前需求已有确认检查点，但尚未形成完整 delivery-plan 检查点 | 已实现版本和实现依据均为“无” |
| 开发中 | 当前版本完整交付计划已持久化，仍有有效切片未完成；本机制自身可在 bootstrap 首片 PASS 后临时进入 | 已实现版本和实现依据同时为“无”，或同时严格绑定早于当前版本的上一完整实现；不得指向当前未完成版本 |
| 已实现 | 当前版本已有 Review PASS 实现 | 已实现版本等于当前版本；实现依据必须列出全部有效任务的 `PEND-*`，每项都可由 `nova-review` 严格重建，且被审设计的 `Requirement-Ref` 精确绑定该 `REQ@版本` |
| 已更新 | 既有实现之后需求定义已升级 | 已实现版本小于当前版本，并保留严格绑定上一实现版本的可信 PEND 依据 |

状态只在总体需求索引维护，需求块正文不重复保存。需求访谈只在已实现需求语义改变时把状态置为已更新；未实现需求修改后仍为待实现。正常需求仅在完整 delivery-plan 检查点成功后进入开发中；Review 不读取需求块正文，只从活动交付台账和蓝图元数据聚合状态。若 Review 版本低于当前版本，状态保持已更新。

## 4. 独立交付

需求块按业务能力而非前端、后端、数据库、接口或测试分层。一个需求块必须能交给一名全栈工程师独立完成，并同时拥有完整业务输入、结果、异常、边界和验收。

需求之间默认无硬依赖。共享数据、API、事件或 Mock 属于架构前置；需求阶段记录需要的业务输入输出，架构阶段冻结技术契约。只有业务顺序本身不可消除时才记录硬依赖，并说明串行原因。

需求块较大时允许在开发阶段拆成多个 PEND，但每项必须是独立、内聚、可控的交付单元：拥有完整结果与验收，并能独立排期、暂停、恢复、Review 或取消。需求、架构、编码、测试等流程阶段及文件、模块、技能、代理、提交批次不能作为拆项依据；只有共同完成才有交付价值的步骤必须保留为一个 PEND 的内部里程碑。

## 5. 总体文档更新边界

新增需求块通常只在需求索引增加一行。只有产品定位、端到端流程、业务模块职责或总体范围发生变化时，才更新总体章节和产品版本，避免总体文档随每个功能膨胀。

## 6. 校验

- 总体文档与需求块结构、元数据、表头和必填单元格精确，业务模块名称唯一且索引只能引用已定义模块；
- Key、文件名、索引、版本、状态、已实现版本和实现依据一致；
- `开发中 / 已实现 / 已更新` 的历史实现依据可以是以顿号分隔的一个或多个唯一 PEND，不接受最小伪造审计或无关 PASS；每项都必须通过确定性索引、完整 Review 记录、被审提交及设计中的 `Requirement-Ref` 联合证明；
- 索引链接存在且只指向 `.nova/requirements/`；
- 需求块包含六个必要章节，无技术实现细节或未完成占位；
- 业务规则 ID 非空且唯一；验收按完整 ID token 精确引用，每条规则至少有一个验收场景覆盖且不得引用未知规则。
