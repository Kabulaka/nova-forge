# Nova 架构

维护所有任务进入项目时都必须知道的轻量系统骨架，使开发者能够直接判断代码放在哪里、可以依赖谁、运行在哪里，以及权威状态由什么介质承担。架构不是“重要设计”的集合，也不因功能跨模块、有版本或可能不兼容而扩大。

`.nova/PROJECT_BLUEPRINT.md` 是一次读取的项目入口，同时保存系统骨架、已实现可复用能力和待开发工作；只有系统骨架属于 Architecture。Architecture 不创建 ADR、索引、审计、状态机或新的 `.nova/architecture/<topic>.md` 详细架构文档。

## 准入与加载

1. 先确定目标仓库并读取项目规则，直接检查固定路径 `.nova/PROJECT_BLUEPRINT.md`，不得用忽略隐藏目录的文件枚举代替。
2. 蓝图不存在时由本技能初始化。蓝图存在后，只有用户本次主动调用本技能，或明确要求改变系统骨架时才修改；普通功能开发只读取并遵守。
3. 蓝图存在时一次读取完整文件，不按章节制造多次调用。读取时同时兼容第六章旧标题“开发导航”和新标题“已实现可复用能力”；普通任务不得因旧标题中断或强制迁移。
4. 用户明确要求升级、迁移或整体精简时，才检查固定旧入口 `.nova/SHARED_CAPABILITIES.md`。不枚举 `.nova`、源码、测试或设计目录，不主动发现或读取需求文档，不为补全蓝图扫描仓库。
5. 普通架构修改只研究本次骨架差量及其直接影响位置；证据足以确定技术栈、运行体、目录、模块、依赖或基础设施边界后立即停止。
6. 既有蓝图已经完整约束目标且用户没有要求修改时，只说明复用的骨架依据，不制造形式性变更。

## 系统骨架准入

只有下列封闭集合中的项目级决定属于 Architecture：

- 语言、框架、运行环境和构建形态；
- 单体、模块化单体、微服务、进程和部署拓扑；
- 数据库、缓存、消息队列、文件、日志等基础设施的选型和系统职责；
- 系统分层、层间允许依赖和顶层代码落位；
- 稳定服务及项目级模块的新增、删除、拆分、合并；
- 服务/模块的唯一职责、所有权、对外角色和允许依赖方向；
- 全系统共同遵守的鉴权、隔离、密钥、配置、部署和资源边界。

内容还必须同时满足：脱离当前功能后仍然成立；任一普通开发任务不能在局部实现中自行改变；删除后会使开发者在代码落位、依赖方向、运行形态或基础设施职责上形成不同系统骨架。

以下内容默认属于 Development，即使跨多个模块、有多个消费者、存在版本或兼容风险也不提升为架构：

- 业务 API、OpenAPI 业务字段、DTO、schema 和数据库表；
- 业务事件及其载荷；
- 页面、端到端工作流、状态机、事务、算法和参数；
- 功能级重试、补偿、恢复、清理、性能目标和验收；
- 一个业务对象如何被资料、目录、正文或其他步骤消费；
- 单个功能使用多个模块、数据库、缓存、并发或外部服务。

“跨模块”“公共”“共享”“版本化”“两个以上参与方”“可能不兼容”都不能单独构成架构准入。业务 API 或 schema 的精确契约保存在代码、正式契约或用户明确要求的设计中；Architecture 最多记录承载它的服务/模块职责、允许依赖和系统级通信方式。

如果请求同时含骨架变化和具体功能，只处理最小骨架差量；功能本身保持 Development。不存在骨架差量时立即返回 Development，不继续架构访谈或把端到端功能改称“架构契约”。

## 存储介质边界

蓝图不能只写“业务状态进数据库、临时状态进缓存”。项目实际使用某种介质时，Architecture 必须写清允许保存、禁止作为和失效恢复边界：

- **数据库**：保存用户提交或确认的权威事实、当前有效结果、重启后必须恢复的任务状态、稳定关系和资源元数据；不默认保存函数执行流水、调试轨迹、可重算中间值、每次 AI 临时输出或无明确业务用途的历史尝试。
- **缓存**：只保存可从权威来源重建且允许过期的查询加速、会话、锁、租约、幂等和限流数据；缓存丢失、过期或清空不得改变业务结果、丢失已确认内容或让成功任务回退。
- **文件介质**：保存上传原件、模板、需要长期引用的转换产物和交付文件；数据库保存稳定文件标识、归属、版本、状态和受控位置。
- **日志与指标**：用于诊断和可观测性，不成为业务真相，也不因“以后可能有用”自动形成业务流水表。

具体业务对象、字段、表、缓存键和保存时机仍由 Development 决定，但不得违反蓝图已经确定的介质职责。

## 蓝图结构与维护权

新建时使用 [蓝图模板](assets/PROJECT_BLUEPRINT.template.md)。一级章节名称和顺序固定：

1. 项目定位；
2. 技术栈与系统形态；
3. 代码结构；
4. 服务与模块骨架；
5. 系统基础边界；
6. 已实现可复用能力；
7. 待开发工作。

Architecture 维护第一至第五章。第六章由 Development 根据已经交付并验证的通用组件维护；第七章由 Architecture、Development 和 Review 按各自授权维护。三类内容同处蓝图只是为了让任务一次读取，不得相互改名或搬运以绕过准入。

系统骨架必须短小：技术栈写实际选择，代码结构只列稳定区域，服务/模块必须映射到精确目录或运行体，依赖方向写真实允许关系。不得复制文件树、函数、SQL、业务字段、迁移步骤、运维命令、功能流程或测试清单。

## 已实现可复用能力

本章只保存已落地通用组件的轻量入口，表格使用 `复用时机 | 能力 | 实现入口 | 复用边界 | 验证入口`。能力必须已经实现、具备稳定入口和独立验证，并且离开当前单一业务工作流后仍能被无关功能直接复用；两个现有无关消费者，或明确的项目级基础组件，才构成复用证据。

潜在复用、单一业务工作流、业务 API/schema/事件、内部辅助代码和未完成候选不得登记。Architecture 初始化时写“无”，迁移时只保留旧入口已经明确登记且从现有精确路径即可确认符合准入的能力；不扫描仓库发现或补齐能力。后续新增、删除、移动或改变复用边界由对应 Development 任务同步更新，不需要再次调用 Architecture。

旧蓝图标题“开发导航”在读取时保持兼容；只有用户显式要求升级、迁移或整体精简时才改名。旧“详细共享契约”不迁入本章：属于系统骨架的一句话边界压缩进第一至第五章，属于业务契约或设计的内容从蓝图能力入口移除，源文件不主动删除或扫描。

## 待开发工作

本章使用 `何时处理 | 待开发工作 | 交付结果 | 设计入口`，只保存大块开发需求和需要独立处理的真实技术债务：

- 设计入口为“无”表示尚未沉淀设计；精确链接表示设计已经确认。
- 没有设计链接不强制普通 Development 先创建设计；用户直接要求实现时仍只澄清真实差量。
- Architecture 只登记用户明确要求分解、保存或随本次骨架决定产生的大块开发需求，不把解释示例、相邻改进和 AI 推导候选自动登记。
- Architecture 不创建设计文档；用户明确要求设计时交由 Development 按其授权处理，不自动调用或制造额外技能往返。
- 同义工作更新原行，完成后删除；不记录状态、来源、负责人、优先级、排期、进度、Review 或审计信息。

## 升级、迁移与精简

显式升级时在内存中完成一次语义映射，再一次性写回：

1. 第一至第五章只保留通过系统骨架准入的内容；业务 schema、工作流、恢复矩阵和功能验收移出骨架，不自动创建设计。
2. 旧第六章只迁移已经明确登记、可从精确入口确认且符合复用准入的已实现能力；旧标题改为“已实现可复用能力”。
3. 旧“详细共享契约”按前述规则压缩为骨架边界或移出能力入口，不创建新的详细架构文档。
4. 旧待开发工作原样保留；有设计链接和“无”都合法，不补状态字段。
5. 固定旧入口 `.nova/SHARED_CAPABILITIES.md` 只有在新蓝图完整、条目与链接验证成功后才移除；任一步失败都保留原文件并停止，不留下部分迁移结果。

迁移不重新证明蓝图中没有失真迹象的普通骨架事实。只有本次修改、疑似过期或会直接造成系统骨架错误的技术栈、运行体、基础设施职责、目录、模块和依赖做有界核对；不读取需求文档或扫描仓库寻找更多内容。

## 澄清、写入与完成

只有不同选择会改变上述系统骨架时，才完整读取 [共享澄清 SOP](../nova-development/references/conversation-sop.md)。业务设计差量不由 Architecture 澄清。没有真实骨架差量时直接说明复用依据。

写入前展示本次骨架摘要、取舍、影响、目标文件，以及不属于架构而保持 Development 的内容，并取得用户明确确认。用户已经批准覆盖同一范围的具体方案时不重复确认。

写入后只验证：

- 七章结构和顺序正确；
- 第一至第五章只含系统骨架，存储介质职责明确；
- 服务/模块映射到精确目录或运行体，依赖方向清楚；
- 第六章没有业务流程、schema、详细设计或潜在复用候选；
- 第七章设计入口语义正确且没有流程状态字段；
- 没有新建详细架构文档、索引、台账或审计数据；
- 链接、格式和任务 diff 通过项目验证。

结果保持未提交，不自动启动 Review、Commit、push 或发布。完成报告只说明骨架结果、蓝图其他两类内容的必要同步、验证和未提交状态。
