# Nova 架构

维护多人长期并行开发共同遵守的主体技术架构，使互不依赖实时沟通的开发者仍能产出兼容实现。蓝图是架构权威；普通开发不得静默改变架构，唯一开发导航也只保存在蓝图中。不生成独立索引、选型报告、ADR 或过程数据。

## 准入与加载

1. 先确定目标仓库并读取项目规则，直接检查固定路径 `.nova/PROJECT_BLUEPRINT.md`。蓝图不存在时负责初始化，不把空白项目直接交给 Development。
2. 蓝图存在后，只有用户本次主动调用本技能或明确要求修改共享架构时才修改；普通开发只读取、复用和遵循现有架构。
3. 蓝图存在时一次读取七章，不按章节制造多次调用。旧蓝图缺少“开发导航”，或仍存在 `.nova/SHARED_CAPABILITIES.md` 时，先在内存中生成完整迁移候选：旧第六章“待开发工作”原样移到新第七章；旧第七章架构链接和经代码、测试确认的旧目录能力合并为新第六章“开发导航”；其余章节保持原有语义。只有新七章顺序、旧待办的数量与内容、链接和导航全部验证通过后，才一次性写回蓝图并移除旧目录；任一步失败都保留原蓝图和 `.nova/SHARED_CAPABILITIES.md`，停止并报告，不得留下部分迁移结果，也不得把无导航解释为无架构或无能力。
4. 先按架构决定映射确定受影响的权威章节，再只沿命中导航的精确入口定向研究代表性代码、配置、部署和测试；能批量读取时使用一个准备批次，不扫描整个 `.nova/architecture/` 或 `.nova/design/`。
5. 如果不同选择会使独立开发者产出不兼容实现，或改变技术栈、运行形态、模块职责、依赖方向、数据所有权、公共接口、安全、失败恢复或部署边界，就属于架构决定；可局部替换且不改变共享边界的内部实现不属于架构。
6. 既有蓝图和代码已完整约束目标且用户没有要求修改时，只报告复用依据并交回 Development，不创建形式性变更。

## 澄清与决策

出现真实差量时完整读取 [共享澄清 SOP](../nova-development/references/conversation-sop.md)。Architecture 与 Development 必须使用同一提问、委托、确认、中断和恢复逻辑。

从用户已确认目标和项目事实推导技术候选，解释用户可感知的成本、部署、数据、恢复和扩展影响，不要求用户在未知后果下只选择产品名称。至少检查实际涉及的以下边界：

- 语言、框架、运行形态和部署；
- 代码结构、系统分层、目录映射和允许依赖；
- 模块职责、共享能力和跨模块所有权；
- 数据存储、所有权、一致性、迁移和生命周期；
- 公共 API、鉴权、错误语义和兼容策略；
- 事件、异步处理、重试、幂等、恢复与清理；
- 缓存、消息队列、Mock、fixture 和其他必要基础设施；
- 性能、并发、资源上限、安全和可观测性不变量。

没有需要的基础设施写为“不使用”或“不适用”，不创建空目录和占位文档。优先用清晰所有权、版本化接口和必要 Mock 消除并行开发依赖；只有业务顺序不可消除的依赖才保留为串行边界。

用户委托 AI 采用成熟方案时，可免除委托范围内低风险参数的逐项提问，但显著成本、部署边界、数据所有权、公共 API/事件、安全和共享失败语义仍须披露。称为成熟或最佳实践前必须取得与本项目相关的外部证据。

## 架构决定与蓝图影响闭包

Architecture 的核心不是维护导航，而是维护下表中的长期共同选择。每次变更先修改权威章节，再检查所有直接受影响章节；第六章开发导航只做派生路由，不得成为第二个事实来源。

| 架构决定 | 权威章节 | 必须联动检查 |
|----------|----------|--------------|
| 项目对象、核心问题或项目级成功结果 | 1. 项目定位 | 技术栈、模块职责和公共约束是否仍服务同一结果 |
| 语言、框架、运行形态、基础设施或部署 | 2. 技术栈 | 代码结构、模块依赖、运行恢复和开发导航 |
| 顶层目录、系统分层或代码落位 | 3. 代码结构 | 模块职责、允许依赖和开发导航 |
| 模块所有权、对外边界或依赖方向 | 4. 模块职责 | 数据所有权、公共契约、代码落位和开发导航 |
| 数据、接口、事件、安全、资源或恢复不变量 | 5. 公共约束 | 模块职责、详细共享契约、验证入口和开发导航 |
| 已实现共享能力或详细契约的发现入口 | 6. 开发导航 | 对应权威章节、源码、测试和链接仍然有效 |
| 用户明确沉淀的未完成设计 | 7. 待开发工作 | 只维护设计精确链接，不改变架构事实 |

## 蓝图职责与结构

新建时使用 [蓝图模板](assets/PROJECT_BLUEPRINT.template.md)。`.nova/PROJECT_BLUEPRINT.md` 保存长期共同遵守的稳定架构事实、按开发触发条件组织的唯一开发导航，以及用户明确沉淀的未完成工作。

蓝图不得展开单个功能的页面、字段、局部流程、权限、失败分支和故事级验收，也不复制具体函数、SQL、迁移步骤、运维命令和可从代码恢复的实现。当前事实仍以代码、测试、迁移和配置为准。

以下一级章节名称和顺序固定：

1. 项目定位：对象、问题和成功结果；
2. 技术栈：当前事实或已确认硬约束及来源；
3. 代码结构：顶层目录、职责和代码落位；
4. 模块职责：模块所有权、对外边界和允许依赖；
5. 公共约束：全局契约、数据与资源不变量、运行恢复和开发决策边界；
6. 开发导航：已实现共享能力与详细共享契约的按需入口；
7. 待开发工作：仅保存用户明确要求沉淀且尚未完成的设计链接。

## 代码、模块与公共契约

- 代码结构只列稳定区域和落位规则，不复制完整文件树。每个模块给出唯一职责、对外边界和允许依赖；模块业务数据和 Repository 仍由模块所有。
- 公共层只承载连接、事务、迁移、恢复、鉴权等共享机制，不得吸收模块业务语义。新增代码必须映射到既有目录和依赖方向。
- 公共 HTTP API 使用 OpenAPI 3.0.x/3.1.x；异步事件使用 AsyncAPI 2.x/3.x。数据所有权、一致性、资源生命周期和失败恢复使用与项目匹配的表格或专项文档。
- Mock 与 fixture 必须引用被模拟的 API 或事件契约，其声明版本必须与契约的 `info.version` 一致。
- 一个公共事实只保留一个权威位置。蓝图给出摘要和精确链接，详细文件给出完整契约，不在两处重复定义。
- 没有 API、事件、Mock、缓存或消息队列需求时写“不适用”，不创建空目录和占位文件。

## 详细架构、开发导航与待开发工作

只有共享契约无法在蓝图中简洁表达时才创建 `.nova/architecture/<topic>.md`：使用稳定可读的主题名，由蓝图精确链接；只记录长期共享的接口、数据、事件、Mock、运行或恢复边界，不记录具体函数、SQL、迁移步骤或其他可从代码恢复的实现，也不建立额外索引或记录过程状态。修改公共契约时同步更新蓝图导航摘要和直接受影响的链接。

蓝图“开发导航”是唯一发现入口，使用 `开发触发条件 | 名称 | 类别 | 精确入口 | 复用或遵循边界 | 验证入口` 表格。第一列必须让开发者仅凭当前任务判断是否命中；类别只使用“已实现能力”或“详细共享契约”。已实现能力只有通过最低验收后才能登记，并指向源码和测试；详细共享契约指向 `.nova/architecture/<topic>.md`。导航只提供相关性判断所需的一句话边界，不复制实现或契约正文；未命中不证明能力不存在。只有用户显式调用 Architecture 后才修改导航；代码移动、废弃、边界或契约变化时同步更新对应行，没有条目时写“无”。

只有用户明确要求设计、规划或沉淀待办时，才在蓝图“待开发工作”使用 `开发触发条件 | 待开发内容 | 交付结果 | 设计入口` 表格添加条目；设计入口精确链接 `.nova/design/` 对应章节。完成后立即删除对应行，设计文件保留；不记录状态、负责人、优先级、排期、进度、Review 或审计信息，未获授权的后续候选不得自动写入。没有条目时删除表格并写“当前无待开发工作”。

## 写入、验证与完成报告

写入前向用户展示本次架构摘要、取舍、影响和目标文件并取得明确确认。写入后检查：

- 七章完整有序，每项架构决定已更新权威章节并完成联动检查，技术栈、代码落位、模块职责、依赖方向和公共边界足以指导开发；
- 开发导航能按触发条件筛选，只需读取命中的契约、代码和测试；详细架构只通过蓝图精确链接读取，没有第二套索引、设计目录扫描、空目录或占位架构；
- 当前事实、公共约束与局部设计的权威边界清晰；
- 与项目相称的结构、链接和项目验证通过，任务 diff 已核对。

结果保持未提交，不自动启动 Review、Commit、push 或发布。报告只受本提示约束，不生成或校验临时报告。

简单示例：

```text
完成：初始化项目蓝图，确定技术栈、模块职责和公共接口边界。
验证：蓝图七章结构、链接和项目验证通过。
文件：.nova/PROJECT_BLUEPRINT.md
状态：改动未提交；未修改业务代码；未启动 Review。
```
