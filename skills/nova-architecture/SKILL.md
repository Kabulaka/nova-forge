# Nova 架构

维护多人长期并行开发共同遵守的主体技术架构，使互不依赖实时沟通的开发者仍能产出兼容实现。蓝图是架构权威；普通开发不得静默改变架构，唯一开发导航也只保存在蓝图中。不生成独立索引、选型报告、ADR 或过程数据。Architecture 负责一次架构请求的外层生命周期；混合请求中的具体功能可以限域交给 Development 澄清和登记，但必须返回 Architecture 后再继续并完成架构工作。

## 准入与加载

1. 先确定目标仓库并读取项目规则，直接检查固定路径 `.nova/PROJECT_BLUEPRINT.md`。蓝图不存在时负责初始化，不把空白项目直接交给 Development。
2. 蓝图存在后，只有用户本次主动调用本技能或明确要求修改共享架构时才修改；普通开发只读取、复用和遵循现有架构。
3. 蓝图存在时一次读取七章，不按章节制造多次调用。这里的“完整语义审计”只表示逐条判断整份蓝图，不是全仓库审计。用户明确要求升级、迁移或整体精简，或旧蓝图缺少“开发导航”时，才直接检查固定旧入口 `.nova/SHARED_CAPABILITIES.md` 是否存在，并在内存中生成完整语义迁移候选：旧“待开发工作”原样移到新第七章；旧架构链接和旧入口已经明确登记且能用精确路径验证的能力合并为新第六章“开发导航”；其余既有内容只保留通过“架构事实准入”的语义，同义内容合并，过期内容替换，功能实现与通用工程规范移出蓝图。导航迁移不追求穷举现有能力，未登记能力不通过仓库扫描补齐。只有新七章顺序、旧待办的数量与内容、必要事实依据、链接和导航验证通过后，才一次性写回蓝图并移除已存在的旧入口；任一步失败都保留原文件，停止并报告，不得留下部分迁移结果，也不得把无导航解释为无架构或无能力。
4. 升级、迁移或整体精简的默认研究边界是项目规则、整份蓝图、模板和固定旧入口；蓝图中没有直接证据表明失真、冲突或需要改写的普通既有事实，不重新证明。权限与对象隔离、共享数据所有权、蓝图已经精确登记的版本化公共契约，以及当前实际启用的基础设施一旦过期会直接产生不兼容实现，因此迁移中必须各用一次有界关键词查询定位当前权威代码、配置或测试，只读取命中的最小证据，不展开相邻功能；蓝图没有精确契约入口时，不为寻找版本而扫描或把框架生成文档的 `info.version` 当成版本化公共契约。其余只对疑似过期、彼此矛盾、本次新增修改或准备登记导航的事实，沿蓝图已有精确路径做最小核对；蓝图内 Markdown 相对链接必须相对 `.nova/PROJECT_BLUEPRINT.md` 所在的 `.nova/` 目录解析，不得错误地从仓库根解析，链接通常只验证目标和必要锚点或版本存在，不读取整份详细架构、设计或契约。旧台账中的需求链接和需求来源列不属于 Architecture 迁移输入，不检查存在性、不读取内容，迁移时随台账字段移除。禁止为迁移枚举 `.nova`、源码目录或测试目录，禁止主动发现或读取需求文档，也不以“确认完整”为由扫描仓库寻找更多模块、能力、契约或候选导航。用户明确点名某个非需求材料作为本次架构输入时，才读取该精确材料。证据足以决定保留、合并、替换或删除后立即停止研究。
5. 普通架构修改只检查新增或修改内容、同一权威位置中语义重合的内容以及直接关联的导航和契约；先按架构决定映射确定受影响的权威章节，再只沿命中导航的精确入口定向研究代表性代码、配置、部署和测试。能批量读取时使用一个准备批次，不借机审计无关章节、扫描整个仓库或遍历 `.nova/architecture/`、`.nova/design/`。
6. 如果不同选择会使独立开发者产出不兼容实现，或新增、删除项目级模块或技能，改变项目级模块或技能的对外暴露集合、技术栈、运行形态、模块职责、依赖方向、数据所有权、公共接口、安全、失败恢复或部署边界，就属于架构决定；即使改动较小或可逆，也不得降级为普通实现。单一模块内新增普通用户功能且不改变共享边界，或可局部替换且不改变共享边界的内部实现，不属于架构。
7. 既有蓝图和代码已完整约束目标且用户没有要求修改时，只报告复用依据并交回 Development，不创建形式性变更。

## 架构事实准入

只有同时满足以下条件的内容才是蓝图或详细架构中的架构事实：

1. 约束项目整体，或约束两个以上能够独立变化的项目内参与方；参与方可以是模块、运行体，或依赖本项目公共契约的外部调用方。仅由一个模块通过私有适配器调用的上游服务不算第二个架构参与方。技术栈、运行形态和部署边界即使只有一个实现，也因约束整个项目而满足本项。
2. 规定长期共同遵守的所有权、允许依赖、对外接口、数据或资源边界、安全、兼容性或恢复不变量，而不是描述某个功能怎样完成。
3. 任一开发任务都不能在自己的局部实现中单独改变它；改变会造成其他参与方不兼容、共享数据迁移、所有权冲突或项目级运行边界变化。
4. 脱离当前具体开发任务后仍然成立，不以某个功能尚未实现、正在实现或已经完成为存在条件。

单个功能的页面、字段、端到端流程、内部状态机、算法和数据结构、事务步骤、重试顺序、参数、功能验收与测试矩阵都属于 Development。功能同时调用多个模块，或涉及数据库、Redis、并发、安全和失败恢复，不足以把它提升为架构；Architecture 只抽取其中真正满足上述准入条件的共享边界。公共 API 或事件的接口、版本、兼容与跨边界失败语义可以是架构契约，承载该接口的具体用例流程仍是开发内容。单一模块拥有的外部供应商适配、来源优先级、匹配、回退、导入、预览和发布流程仍是 Development；例如价格来源及其回退属于 `pricing` 功能，Architecture 只记录 Pricing 的所有权，以及 Billing 只消费已发布、可冻结的价格版本这一跨模块边界。

空白项目或尚无实现契约的蓝图初始化默认只创建 `.nova/PROJECT_BLUEPRINT.md`。计划中的 Gateway 请求生命周期、跨模块调用编排、预留与结算步骤、Redis 算法、Task/Outbox 消费、幂等与重试、故障恢复矩阵和未来测试清单即使跨越多个模块，也应交给 Development 设计；蓝图只保留运行体定位、模块所有权与依赖、权威数据源、公共接口种类及必须长期成立的一句话不变量。不得为了让第六章有条目而提前创建详细架构文档。

## 轻量写入准入

所有 Architecture 写入都在展示确认摘要前完成一次内存中的语义准入：初始化检查本次候选全部内容；升级、迁移或整体精简检查现有七章；普通架构修改只检查前述受影响范围。不得为此增加独立审计阶段、额外用户往返、持久化报告、版本台账或固定行数预算。

每条准备新增、修改或在迁移中保留的内容，必须有当前依据并通过“架构事实准入”，还必须满足：蓝图中没有另一个同义权威条目；删除该内容后，独立开发者确实可能在所有权、依赖、兼容性、数据、安全、恢复或运行边界上产出不兼容实现；蓝图正文已经压缩为足以指导兼容实现的一句话。相同事实更新原条目，不追加历史版本；无法一句话表达且确有多个独立参与方直接消费的精确公共契约，才使用详细架构并由蓝图提供一句导航摘要。

第 5 章不是资源、失败模式或治理清单。“数据、资源与恢复”只记录两个以上独立参与方必须共同遵守、且不能由所有者模块自行封装的项目级不变量；单模块长任务的领取、迟到结果、重试、摄取恢复和临时文件清理仍属于 Development。这些排除项适用于蓝图所有章节，不得改名或移动到“全局契约”后继续保留。开发决策边界只记录本项目特有且会改变兼容实现的决定，不复述本技能的通用规则；没有合格内容时删除对应小节或表格，不为保持模板外观而填充。模块职责、公共约束和开发导航允许为路由重复名称，不得重复定义同一边界正文。

不通过的候选不写入蓝图：功能流程、页面、字段、内部算法、事务、重试和功能验收交回 Development；通用工程规范留在项目规则、代码或测试；重复内容合并，过期内容替换，证据不足的内容保留为本轮候选而不是既定事实。移出蓝图不等于自动创建设计文档，仍须遵守用户明确授权边界。

## 澄清与决策

出现会改变架构结果的真实差量时完整读取 [共享澄清 SOP](../nova-development/references/conversation-sop.md)。Architecture 与 Development 必须使用同一提问、委托、确认、中断和恢复逻辑。写入前确认是本技能已经定义的固定授权门，不属于架构差量，也不触发读取澄清 SOP；没有真实差量时直接展示摘要并等待确认。

从用户已确认目标和项目事实推导技术候选，解释用户可感知的成本、部署、数据、恢复和扩展影响，不要求用户在未知后果下只选择产品名称。只对当前请求实际产生且通过“架构事实准入”的差量检查以下边界，不为覆盖清单而展开完整功能设计：

- 语言、框架、运行形态和部署；
- 代码结构、系统分层、目录映射和允许依赖；
- 模块职责、共享能力和跨模块所有权；
- 数据存储、所有权、一致性、迁移和生命周期；
- 公共 API、鉴权、错误语义和兼容策略；
- 事件、异步处理、重试、幂等、恢复与清理；
- 缓存、消息队列、Mock、fixture 和其他必要基础设施；
- 项目级性能、并发、资源、安全和可观测性不变量。

没有需要的基础设施写为“不使用”或“不适用”，不创建空目录和占位文档。优先用清晰所有权、版本化接口和必要 Mock 消除并行开发依赖；只有业务顺序不可消除的依赖才保留为串行边界。

用户委托 AI 采用成熟方案时，可免除委托范围内低风险参数的逐项提问，但显著成本、部署边界、数据所有权、公共 API/事件、安全和共享失败语义仍须披露。称为成熟或最佳实践前必须取得与本项目相关的外部证据。

## 混合请求中的开发交接

用户在 Architecture 会话中明确提出需要交付的具体功能时，不得把该功能扩写成架构，也不得因当前技能是 Architecture 而丢弃它。用户本次明确提供并要求作为架构输入的需求文档、功能清单或精确材料，其中写明的待实现功能同样视为用户明确提出，不得只把它们当作架构背景：

1. 先拆分架构差量与开发内容；完成并确认直接相关的架构决定，使后续开发有稳定边界。
2. 明确告知用户哪些内容属于开发需求，并将已确认架构、功能目标、明确排除和未决开发差量限域交给 `nova-development`。交接任务固定为“澄清、设计和登记，不编码”，不得扩展为实现、Review 或提交。
3. 该交接只处理用户明确要求交付的功能；同一材料含有多个功能时按可独立交付的内聚开发任务分组，逐个限域交接，不按页面、字段或技术步骤制造碎片任务。用于解释架构的示例、AI 推导的后续候选和相邻改进不得自动登记。
4. Development 按自身既有规则完成开发澄清，写入 `.nova/design/YYYY-MM-DD_<具体名称>.md`，并在蓝图第七章登记精确设计入口。该限域交接构成明确的设计与待办登记请求，但写入前仍须展示设计摘要、目标文件和蓝图变化并取得用户确认。
5. Development 把已确认架构当作输入，不修改或重开架构决定；若澄清发现疑似架构冲突，只把事实与影响交回 Architecture。Development 的返回只是候选，不构成架构判定；Architecture 必须重新执行“架构事实准入”。未通过时不修改架构、不继续架构提问，直接把该内容连同既有边界退回同一 Development 任务。只有通过时才由 Architecture 澄清和修改共享边界。登记完成或冲突处理后，控制权都回到 Architecture，由 Architecture 继续尚未完成的架构讨论。

Architecture 在限域交接期间仍是外层活动技能；未返回并完成剩余架构工作前，不得宣称本次 Architecture 生命周期完成。本规则不要求修改 Development 的职责或提示词。

架构摘要和写入确认必须同时披露从用户明确材料中识别出的待交接开发任务及后续顺序。允许先确认并写入稳定架构，再逐项交给 Development 登记；但在这些明确功能尚未交接时，不得声称“本次只初始化架构”“不登记开发待办”“当前无待开发工作”或以 Architecture 请求范围为由直接结束。

## 架构决定与蓝图影响闭包

Architecture 的核心不是维护导航，而是维护下表中的长期共同选择。每次变更先修改权威章节，再检查所有直接受影响章节；第六章开发导航只做派生路由，不得成为第二个事实来源。

| 架构决定 | 权威章节 | 必须联动检查 |
|----------|----------|--------------|
| 项目对象、核心问题或项目级成功结果 | 1. 项目定位 | 技术栈、模块职责和公共约束是否仍服务同一结果 |
| 语言、框架、运行形态、基础设施或部署 | 2. 技术栈 | 代码结构、模块依赖、运行恢复和开发导航 |
| 顶层目录、系统分层或代码落位 | 3. 代码结构 | 模块职责、允许依赖和开发导航 |
| 模块所有权、对外边界或依赖方向 | 4. 模块职责 | 数据所有权、公共契约、代码落位和开发导航 |
| 数据、接口、事件、安全、资源或恢复不变量 | 5. 公共约束 | 模块职责、详细共享契约、验证入口和开发导航 |
| 已实现共享能力或详细契约的发现入口 | 6. 开发导航 | 对应权威章节、源码、测试和链接仍然有效 |
| 用户明确沉淀的未完成设计 | 7. 待开发工作 | 只维护设计精确链接，不改变架构事实 |

## 蓝图职责与结构

新建时使用 [蓝图模板](assets/PROJECT_BLUEPRINT.template.md)。`.nova/PROJECT_BLUEPRINT.md` 保存长期共同遵守的稳定架构事实、按开发触发条件组织的唯一开发导航，以及用户明确沉淀的未完成工作。

蓝图不得展开单个功能的页面、字段、局部流程、内部状态机、算法与数据结构、事务或重试步骤、权限与失败分支、功能验收和测试矩阵，也不复制具体函数、SQL、迁移步骤、运维命令和可从代码恢复的实现。当前事实仍以代码、测试、迁移和配置为准。

以下一级章节名称和顺序固定：

1. 项目定位：对象、问题和成功结果；
2. 技术栈：当前事实或已确认硬约束及来源；
3. 代码结构：顶层目录、职责和代码落位；
4. 模块职责：模块所有权、对外边界和允许依赖；
5. 公共约束：跨参与方的全局契约，以及确有必要的数据、资源、恢复或项目特有决策边界；
6. 开发导航：已实现共享能力与详细共享契约的按需入口；
7. 待开发工作：仅保存用户明确要求沉淀且尚未完成的设计链接。

## 代码、模块与公共契约

- 代码结构只列稳定区域和落位规则，不复制完整文件树。每个模块给出唯一职责、对外边界和允许依赖；模块业务数据和 Repository 仍由模块所有。
- 模块名称必须映射到已验证的精确代码目录或运行体，不得用“相关模块”“相关代码”等模糊占位代替实现映射；无法在轻量研究边界内确认细分目录时，合并到已经确认的更大稳定代码区域，不为补全模块表扫描目录。
- 公共层只承载连接、事务、迁移、恢复、鉴权等共享机制，不得吸收模块业务语义。新增代码必须映射到既有目录和依赖方向。
- 公共 HTTP API 使用 OpenAPI 3.0.x/3.1.x；异步事件使用 AsyncAPI 2.x/3.x。数据所有权、一致性、资源生命周期和失败恢复使用与项目匹配的表格或专项文档。
- Mock 与 fixture 必须引用被模拟的 API 或事件契约，其声明版本必须与契约的 `info.version` 一致。
- 一个公共事实只保留一个权威位置。蓝图给出摘要和精确链接，详细文件给出完整契约，不在两处重复定义。
- 没有 API、事件、Mock、缓存或消息队列需求时写“不适用”，不创建空目录和占位文件。

## 详细架构、开发导航与待开发工作

只有已经通过“架构事实准入”、蓝图无法用一句边界简洁表达、且已经存在或本次必须先固定的精确公共接口、数据结构或事件契约被多个独立参与方直接消费时，才创建 `.nova/architecture/<topic>.md`。使用稳定可读的主题名，由蓝图精确链接；正文只记录让参与方兼容所必需的版本化接口、字段、所有权与跨边界失败语义，不记录请求或业务生命周期、跨模块编排、内部算法、事务与重试步骤、恢复场景表、未来测试清单或其他开发设计，也不建立额外索引或记录过程状态。新项目中“将来实现会跨模块”不是创建详细架构的理由；能够直接作为某个功能的实现说明或验收清单的内容必须由 Development 写入 `.nova/design/`。修改公共契约时同步更新蓝图导航摘要和直接受影响的链接。

蓝图“开发导航”是唯一发现入口，使用 `开发触发条件 | 名称 | 类别 | 精确入口 | 复用或遵循边界 | 验证入口` 表格。第一列必须让开发者仅凭当前任务判断是否命中；类别只使用“已实现能力”或“详细共享契约”。已实现能力只有通过最低验收后才能登记，并指向源码和独立测试或校验；实现文件、启动脚本或配置本身不能同时充当验证入口。详细共享契约必须满足上一段严格条件并指向 `.nova/architecture/<topic>.md`，验证入口指向现有契约、Schema 或可执行校验，不得写未来测试清单。升级迁移只迁移旧蓝图或固定旧入口已经明确登记的导航条目；为核对权限、所有权、基础设施或其他高风险事实而找到的代码、配置和测试只是证据，不得自动晋升为新导航。旧版没有合格登记时写“无”，不为了提升可发现性新增条目。导航只提供相关性判断所需的一句话边界，不复制实现或契约正文，不登记开发任务、功能设计或未实现能力说明，也不得用详细共享契约代替第七章待开发工作；空白项目没有合格条目时直接写“无”。未命中不证明能力不存在。只有用户显式调用 Architecture 后才修改导航；代码移动、废弃、边界或契约变化时同步更新对应行。

只有用户明确要求设计、规划或沉淀待办，或在 Architecture 会话中明确提出需交付的具体功能并进入限域 Development 交接时，才在蓝图“待开发工作”使用 `开发触发条件 | 待开发内容 | 交付结果 | 设计入口` 表格添加条目；设计入口精确链接 Development 澄清并确认后的 `.nova/design/` 对应章节。Architecture 不代替 Development 编写功能设计。完成后立即删除对应行，设计文件保留；不记录状态、负责人、优先级、排期、进度、Review 或审计信息，未获授权的后续候选不得自动写入。没有条目时删除表格并写“当前无待开发工作”。

## 写入、验证与完成报告

完成轻量写入准入后，向用户展示本次架构摘要、取舍、影响和目标文件并取得明确确认；摘要同时说明新增、修改、删除或合并的内容，以及因不属于架构而不写入的内容，不增加第二次确认。写入后只做结构与结果验证：

- 七章完整有序，每项架构决定已更新权威章节并完成联动检查，技术栈、代码落位、模块职责、依赖方向和公共边界足以指导开发；
- 模块职责均能映射到精确代码目录或运行体，没有“相关模块”“相关代码”等模糊占位，也没有为补全表格发起目录扫描；
- 写入结果与已确认的语义准入结论一致；空白项目没有为计划中的跨模块功能创建详细架构文档，没有把调用流程、编排、算法、事务、恢复矩阵或未来测试清单包装成共享契约；
- 开发导航能按触发条件筛选，只需读取命中的契约、代码和测试；详细架构只通过蓝图精确链接读取，不替代开发设计或待开发工作，没有第二套索引、设计目录扫描、空目录或占位架构；
- 用户当前表达和明确提供材料中的开发功能已经按内聚任务由 Development 限域澄清和登记；Development 返回的疑似冲突已由 Architecture 重新执行架构事实准入，未通过的已退回 Development，通过的才修改共享边界；交接后 Architecture 已继续完成剩余工作；
- 当前事实、公共约束与局部设计的权威边界清晰；
- 与项目相称的结构、链接和项目验证通过，任务 diff 已核对。

结果保持未提交，不自动启动 Review、Commit、push 或发布。报告只受本提示约束，不生成或校验临时报告。
