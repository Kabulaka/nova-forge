# Nova 本地提交

只有用户明确说“提交”“commit”或主动调用本技能时才执行。Architecture、Development 和 Review 完成不构成提交授权，也不得自动转交本技能。本技能是只消费既有结果的终点动作，不得调用其他 Nova 技能。

## 边界与准入

1. 从用户指定范围或当前会话已固定的任务差异确定提交对象。不同范围会改变提交内容时，只问一个精确范围问题。
2. 用一个只读批次取得仓库根、HEAD、完整 Git 状态、范围内 staged/unstaged diff 和未跟踪文件，并固定候选提交内容标识。标识必须覆盖 HEAD、每个目标路径的最终 mode/blob/object 或删除状态，能够区分 binary、未跟踪文件及同路径内容变化；不得只记录路径集合。不得把工作树中相邻或历史修改自动纳入。
3. 同一文件混有无法可靠分离的用户既有修改时停止，不得覆盖、回退或代替用户选择。
4. 只复用进入本技能之前已经存在、可归属到当前任务且仍有效的验证证据。证据必须能够说明命令与工作目录、覆盖范围、结果以及为何仍覆盖候选提交内容标识对应的当前差异，不能只按路径判断；本技能读取 diff 或运行暂存区检查不构成功能验证。
5. 已有与当前任务无关的 staged 内容时停止。不得重置、取消暂存或改写用户的暂存区。

存在已知失败、阻断问题、未验证改动或验证证据缺失/失效时，当前 Commit 调用立即结束，只报告拒绝原因和需要补齐的 Development 验证。本技能不得自行测试、修复或放宽门禁，不得自动调用 `nova-development`、`nova-review` 或 `nova-architecture`，不得在当前调用中制造证据后继续提交；必须由用户另行发起 Development，并在验证完成后给出新的明确 Commit 请求。

## Conventional Commit

一个内聚任务创建一个提交，不按文件、编辑批次、测试轮次或工具批次拆分。首行使用 `type(scope): 中文结果摘要`；破坏性变更使用 `type(scope)!:`，并在正文使用 `BREAKING CHANGE:` 说明迁移影响。

| type | 使用边界 |
|------|----------|
| `feat` | 新增用户可见能力或既有能力的新行为 |
| `fix` | 有证据的缺陷恢复 |
| `refactor` | 不改变外部行为的代码结构调整 |
| `perf` | 有明确性能目标的优化 |
| `test` | 只增加或修正测试 |
| `docs` | 只修改文档 |
| `build` | 构建系统或依赖变化 |
| `ci` | CI/CD 配置与流程变化 |
| `chore` | 不属于以上类型的例行维护 |
| `revert` | 撤销既有提交 |

`scope` 使用覆盖整个提交的最小稳定能力域、模块或组件，采用小写 kebab-case；不得使用单个文件名、流程阶段或 `all/misc/core` 等无信息名称。中文摘要说明提交后的实际结果，不使用“更新代码”“相关优化”等空话，不以句号结尾。正文只在必要时说明原因、关键边界、迁移影响和验证。Nova 不添加工作项、Review、审计或其他流程 trailers；宿主自身的提交归属信息服从宿主设置，本技能不得为改变它而修改用户或项目配置。

## 执行与结果

1. 根据已检查的完整 diff 生成提交信息和精确路径清单。
2. 用一个失败即停的批次精确暂存目标路径，运行 `git diff --cached --check`，核对 staged 路径与预期完全相等，并逐路径确认最终 staged 内容的 mode/blob/object 或删除状态与候选提交内容标识完全一致，同时确认目标路径没有剩余 unstaged 变化，然后才创建本地提交。即使路径集合不变，只要内容标识变化也必须立即停止且不得提交；禁止 `git add .`、`git add -A` 或范围不受控的通配暂存。
3. 提交后检查 commit hash、主题、提交路径和剩余工作树。任何不一致都如实报告，不创建补救提交。

除非用户本次明确要求，否则不得 amend。不得修改代码或文档、运行测试、启动 Review、调用其他 Nova 技能、生成审计、push、修改远程、发布或提交 SVN。

结果只报告 commit hash、主题、精确提交范围、复用的验证证据和剩余工作树状态。
