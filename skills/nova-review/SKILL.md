# Nova 人工 Review

只在用户明确提出 Review、审查、复审或补审时运行。技能被加载不等于用户已授权启动 Review；普通实现和测试不得自动进入本流程。

## 1. 任务差异基线与审查范围

优先使用用户指定的 commit、SHA range、分支差异、SVN revision 或工作树范围。范围不明确且不同选择会改变审查对象时，完整读取 [共享澄清 SOP](../nova-development/references/conversation-sop.md)，只问一个范围问题。

1. 使用实施阶段首次编辑前固定的仓库类型和根目录、Git/SVN 完整状态、任务路径或模块、既有修改及未跟踪文件基线；不得因压缩、续接、自检或 Review 重建基线。
2. 当前任务差异只包含相对基线由所选 commits、分支差异或本任务尚未提交修改新增、修改或删除的路径与行块。历史未提交内容不得因出现在 diff 或未跟踪列表中自动纳入。
3. 任务开始前相关路径已有修改时，基线必须含足以分离同一文件新旧行块的只读快照或等价补丁；只有文件名或哈希不够。无法可靠分离时停止 Review，请用户选择独立 worktree/checkout、明确扩围或先处理既有变更。
4. Review 输入、内容标识、规模统计、拆分和结论只以当前任务差异为准。Reviewer 可只读查看基线代码和直接调用上下文，但范围外问题不得分级或影响结论；既有问题直接阻止验收时只报告基线风险，由用户决定是否扩围。
5. 选择为空时说明原因，不把空范围当 PASS。用户明确扩围时，在新增范围首次编辑前补充基线、设计依据和验收；不得沿用不完整的内容标识。

## 2. Review 前自检

首次 Review 前，主代理必须：

1. 检查当前任务差异的完整变更；
2. 将固定范围和验收矩阵逐条对应到实现与有效测试证据，包括接口契约、核心不变量、失败语义、蓝图条目和设计依据；
3. 检查空值、非法值、空集合、重复、并发、超时、取消、回滚、兼容、资源释放和重复执行；不适用项说明理由；
4. 检查直接调用方、消费者、恢复/清理路径、各调用边界的契约一致性和所有副作用的失败状态；
5. 修复自检问题；只有修复使测试证据失效时才重跑受影响测试，否则复用已有证据；
6. 向 Reviewer 提供完整任务差异、有效测试证据和未验证事项。

未完成自检，或任一验收项尚未对应实现和有效证据时不得启动 Review。自检不算 Review 轮次。首次 Review 后不得重建验收矩阵，或因重读蓝图和设计扩大范围；Review 问题按已固定范围处置。

## 3. 独立 Reviewer 输入、角色与思考度

主代理每轮必须向独立 Reviewer 提供：

1. 当前任务差异的完整 Git/SVN patch、任务开始基线内容标识及路径/行块清单；
2. 变更意图和摘要；Plan mode 附计划摘要与验收标准；
3. 显式 `reasoning_effort` 参数，不得依赖全局默认；
4. 本轮完整 diff 的内容标识、审查范围、有效测试证据和未验证事项；
5. 复审时附上一轮完整报告及全部 Blocker/Observation-Fix 的修复说明。

Reviewer 是本轮最终独立审查者：

- 只读检查指定范围，完成一次审查后直接输出最终结论，不得边审边改；
- 不得再次启动 Review 子代理、执行 `codex`/`claude` 交叉审查或递归委派；多视角由主代理在父层分别启动；
- 不得运行全量测试、长时间任务或无关命令，除非主代理明确要求；有效测试证据直接复用；
- 一旦产生文件写入、补丁、格式化或其他工作副本变更，本轮立即失效且不得输出结论；该代理转为编码参与者，不得再审查包含其修改的差异，主代理必须改用未参与修改的独立 Reviewer。

思考度规则：

- 默认与主代理当前思考度一致；主代理仍须在 `spawn_agent` 中显式传入；
- 只有审查范围明确且风险集中时，才可比主代理调高一档，并在输入中说明风险理由；
- 更高思考度不替代范围拆分；接近上下文上限时优先减少范围、重复输出和无关上下文。

## 4. 大范围拆分与上下文

1. 先按任务开始基线统计当前任务差异，不得用整个脏工作副本的 diff 统计代替。
2. 当前任务差异超过 10 个文件或新增行超过 1000 行时，按模块和风险拆为多个互斥范围；每个文件只指定一个主 Reviewer，每名 Reviewer 接收其范围的完整差异，主代理汇总结论。
3. 大文件和大 diff 分块读取，优先符号检索后读必要上下文；禁止重复输出大范围重叠片段。
4. 单次输出接近工具上限时继续分块，不得依赖截断结果作结论。

## 5. 七维检查清单

Reviewer 无需主代理逐项提示，也必须检查：

1. **契约一致性**：签名、输入、返回值、错误语义、状态转换和模块边界；
2. **边界/异常路径**：None、空集合、非法值、重复、并发、超时、取消、回滚、资源释放和重复执行；
3. **测试覆盖**：关键正常路径、失败路径、边界条件及跨调用边界等价语义；
4. **架构红线**：是否违反蓝图公共约束、依赖方向或设计范围；
5. **性能审查**：数据读取的内存安全、并发/锁/阻塞路径及可测量退化；
6. **副作用**：意外行为变化、数据污染、补偿/清理缺失或性能退化；
7. **代码风格**：命名、注释、文档字符串和既有约定一致性。

## 6. 问题分级与结论

每条问题必须标注检查维度、严重性、文件/行号、证据和可执行修复方向：

- **Blocker**：必须同时满足“本次任务差异新引入”和“涉及运行时正确性、数据安全或可测量性能退化”；不修复不可通过。既有问题、纯理论低概率边界和风格建议不能定为 Blocker。
- **Observation-Fix**：非 Blocker 但本轮应修复，且不要求跨模块重构。Observation 默认是 Fix。
- **Observation-Defer**：只有逐条满足并引用以下至少一项才成立：①需修改本次未触及模块；②涉及业务接口签名并影响当前范围外下游；③需新依赖或基础设施；④正确性依赖尚未实现功能。不得以“建议以后优化”或“非本次重点”代替理由；未附有效准入理由的 Defer 按 Fix 处理。合法 Defer 不自动等于技术债务，是否登记还必须通过第 9 节准入。

结论只能是：

| 结论 | 判定 | 后续 |
|------|------|------|
| PASS | 无 Blocker、无 Observation | 结束审查，保留当前未提交差异 |
| PASS WITH NOTES | 无 Blocker、无 Observation-Fix，仅有合法 Observation-Defer | 报告延期项；仅将通过第 9 节准入的技术债务登记到待开发工作 |
| REJECT | 有 Blocker 或 Observation-Fix | 主代理统一修复全部必修项后复审 |

Reviewer 必须审查完七个维度并一次性返回“明确结论 + 全部问题列表”，禁止发现一个问题就中断。REJECT 的每条问题须有维度、严重性、描述和文件/行号。

## 7. REJECT 修复与复审

1. 主代理收到完整 REJECT 后逐条分析，统一修复全部 Blocker 和 Observation-Fix；不得只修一部分就复审，也不得借机重构无关代码。
2. Observation-Defer 在中间轮次只保留在 Review 报告中，逐条写明延期准入理由、影响和建议；不扩展当前实现范围，也不在最终结论前创建待办。
3. 只有修复导致证据失效时才重跑受影响测试，其他证据必须复用。测试通过后保留完整 Review 修正 diff，不创建中间提交；需要暂存区固定内容时可暂存，但不得提交。
4. 复审必须用 `followup_task` 复用上一轮 Reviewer，逐条确认旧问题，并只检查修复新增或修改行是否引入新问题；不得在上一轮未指出的区域搜索新问题。
5. 复审新问题只可来自修复直接触及的行，仍按相同规则分级。
6. 同一变更最多三轮（初审 + 两次复审）；第 3 轮仍 REJECT 时停止并报告用户。
7. 每轮只有“主代理提供审查输入 → Reviewer 完整报告”一个来回，不做交互式边审边改；这里的“提供审查输入”不是 Git commit。

仅当原 Reviewer 为 `errored`、`interrupted`、`shutdown`、`not_found` 或因写入失去资格时可更换：

- 生命周期失败：新 Reviewer 收到相同 diff、范围、上轮报告、修复说明和显式思考度，Review 轮次不重置；
- 写入失去资格：原审查无有效结论且不计轮次，新 Reviewer 按当前完整任务差异重新初审。

## 8. 证据、内容标识与复用

1. 每轮记录完整任务 diff 的内容标识和审查范围。相同标识、相同范围已有 PASS 时必须复用，不因压缩、续接、自检、Verify 或重读蓝图再次 Review。
2. 修改只使直接受影响的 Review 范围失效；互斥、未受影响范围的 PASS 继续有效。REJECT 修复按上一节交原 Reviewer 增量复审。
3. Review 分级和处置是后续验收证据；主代理不得在自检或 Verify 中自行重新分级。延期建议不自动进入当前实现范围，只有最终仍成立并通过第 9 节技术债务准入时才登记到蓝图第七章。
4. Review 不使有效测试证据失效；只有内容、环境、覆盖或用户重跑条件变化时才失效。

## 9. 技术债务登记

Reviewer 始终只读，不修改蓝图。只有最终 PASS 或 PASS WITH NOTES 后，主代理才从最终仍成立的 Observation-Defer 中判断是否存在应登记的技术债务；REJECT 中间轮次不登记，因为修复可能消除问题。

一项 Defer 必须同时满足以下条件才是可登记技术债务：

1. 有当前任务差异或 Reviewer 允许读取的直接上下文证据，不是推测、风格偏好或未来可能优化；
2. 不影响本次任务的正确性、数据安全或必要验收，否则必须作为 Blocker 或 Observation-Fix 处理，不能以债务逃避修复；
3. 当前 Review 范围内不能安全修复，且需要形成独立、内聚的后续开发任务；
4. 能写出明确的处理时机和可观察完成结果；
5. 蓝图“待开发工作”中不存在同义条目。

尚未实现功能的自然缺失、范围外普通问题、纯建议、已经修复的问题和无法给出独立交付结果的观察不登记。不是所有合法 Observation-Defer 都是技术债务。

存在合格债务时，主代理才读取一次固定路径 `.nova/PROJECT_BLUEPRINT.md`，在第七章按 `何时处理 | 待开发工作 | 交付结果 | 设计入口` 新增或合并一行，设计入口写“无”。只允许修改该行：不创建设计、不修改系统骨架或已实现可复用能力，不增加来源、严重性、Review 状态、负责人、优先级或进度字段。没有合格债务时不读取或改写蓝图。

这项轻量登记不改变被审查实现，也不触发新的 Reviewer 轮次或业务测试；只对蓝图运行定向格式和 diff 检查。如果主代理修改了第七章债务行之外的任何任务内容，按正常内容变更规则使受影响 Review 证据失效。登记结果保持未提交，并在完成报告中列出。

## 10. 等待、终止与人工中断

主代理不得自行关闭 Reviewer：

1. 禁止为节省等待时间主动中断 Reviewer。等待超时只表示等待窗口结束，不是状态信号；继续等待到 `completed`、`errored`、`interrupted`、`shutdown` 或 `not_found`。
2. 父回合被平台 `turn_aborted` 被动终止属于生命周期失败，不是结论。恢复后先查原 agent：`completed` 则读取报告；其他终态或 `not_found` 用相同 diff、范围和显式思考度重启，生命周期最多重启两次，超过后停止并报告用户。
3. 超时、关闭、空响应、中间消息或“看起来没问题”都不是 PASS。未取得正式结论前不得宣称完成审查。
4. 用户明确要求中断 Review 时，可以停止尚未开始的新轮次，并按用户指令中断正在运行的 Reviewer；中断不是结论。保留已有提交、工作副本和未失效测试证据，恢复时复用中断前已取得的明确结论；无结论的轮次按生命周期规则处理。

## 11. PASS 后边界与报告

PASS 或合法 PASS WITH NOTES 后结束审查。REJECT 产生的修正保持未提交直到复审通过；复审通过后仍保持未提交，不自动启动 Commit。没有修正时不得制造空变更。

Review 结论和流程状态不写入蓝图、设计或其他状态文件；只有第 9 节合格技术债务作为独立待开发工作登记。不得自动 push、修改远程、发布或提交 SVN。

完成报告逐轮列出审查范围与内容标识、明确结论、全部问题及对应修正、复用或重跑的验证证据、实际修改路径、当前提交状态、刻意未改范围、延期项、已登记技术债务和下一步。报告只受提示词约束，不生成或运行报告校验器。
