<a id="shared-context"></a>
## 1. 公共上下文

### 1.1 问题与目标

- 原技能把项目级约束与具体功能设计共同写入蓝图，长期使用会造成蓝图膨胀和开发会话上下文污染。
- 新技能必须通过自然对话完成需求澄清，并把结果分流到项目蓝图、史诗设计文档和待开发工作包索引。
- 已有蓝图需要可识别的格式版本和无损迁移流程；迁移不能替用户补造未确认需求。
- 一个史诗可以包含多个有共同语义的工作包，多个蓝图待办可以引用同一设计文档的不同章节。

### 1.2 明确非目标

- 不保留 `$create-project-blueprint` 兼容入口。
- 不将所有旧待办强制补齐设计文档。
- 不因为待办属于同一模块或优先级就判定可以共同澄清。
- 不增加第三方依赖、远程服务或自动发布能力。

### 1.3 共享模型与不变量

- `PROJECT_BLUEPRINT.md` 只保存所有模块共同理解并长期遵守的项目级事实。
- `docs/design/*.md` 保存史诗公共语义和工作包级行为、权限、失败恢复及验收。
- 蓝图待办使用稳定编号，并以相对路径加显式锚点引用设计章节。
- 未完成澄清的设计依据和未知依赖必须写“待澄清”，不能生成空链接或推断值。
- 共同澄清仍遵守每轮一个信息维度；“共同”只表示共享史诗上下文。
- 结构升级必须保留旧待办名称、优先级、顺序和完成定义。
- 已完成工作包从蓝图删除，设计文档继续保留并更新生命周期状态。

### 1.4 与项目蓝图的关系

- 技能单一源码、发现入口、输出净化和验证失败语义遵守 `PROJECT_BLUEPRINT.md` 的跨模块契约。
- 本文只说明本次技能重构的局部设计，不重复工作区安全和资源红线。

## WP-01 技能重命名

### 状态、范围与非目标

- 状态：已完成
- 范围：唯一技能名、目录名、frontmatter、UI 默认提示和发现入口统一改为 `project-brainstorming`。
- 非目标：不保留旧技能入口、别名或兼容包装层。

### 前置条件、输入与输出

- 输入是当前工作区技能包和个人目录符号链接。
- 输出是工作区唯一实体目录 `project-brainstorming/` 及指向它的个人发现链接。

### 正常行为、权限与状态

- 工作区内完成目录和元数据改名，验证通过后切换个人发现链接。
- 旧入口最终不存在，新入口从工作区路径和发现路径都能通过官方结构验证。

### 边界、失败与恢复

- 新目标已存在且不是期望链接时必须停止，不得覆盖。
- 验证失败时不得声称迁移完成；工作区唯一实体源码必须保留。

### 依赖与影响范围

- 影响技能目录、`SKILL.md`、UI 元数据、根蓝图和个人发现链接。
- 不影响工作区外其他技能。

### 验收标准

- 搜索不到作为入口或契约使用的旧技能名。
- 新名称在目录、frontmatter、默认提示和发现链接中完全一致。
- 旧个人入口不存在，新入口解析到工作区唯一源码。

<a id="wp-02-document-routing"></a>
## WP-02 文档分层与澄清路由

### 状态、范围与非目标

- 状态：已完成
- 范围：定义蓝图、史诗设计和实现事实三层职责，以及已有蓝图迁移和待办共同澄清流程。
- 非目标：不规定具体业务领域的问题顺序，不把共同澄清变成批量提问。

### 前置条件、输入与输出

- 输入是新项目想法、已有蓝图、已有设计文档和用户指定待办。
- 输出是项目级规则、史诗公共章节、独立工作包及蓝图引用之间的可追溯关系。

### 正常行为、权限与状态

- 技能先判断结论属于项目级还是功能级，再写入唯一事实来源。
- 格式不兼容时先报告差异、待办总数和缺少设计引用数量。
- 只有共享用户目标、模型、不变量、状态链、依赖或组合验收的待办才能建议共同澄清。
- 迁移选择必须覆盖全部缺少设计依据的待办；用户不选择全部澄清时直接无损升级。
- 旧蓝图中不能留在新版蓝图的功能细节先逐字归档，归档不作为设计依据，待办仍标记“待澄清”。
- 蓝图结构升级时才一次写入已确认的工作包映射，不向旧表中不存在的列提前写值。

### 边界、失败与恢复

- 迁移无法保留原语义或发现并发修改时停止写入并报告冲突。
- 澄清中断时只保存已确认内容和工作包映射，设计状态保持“澄清中”，旧蓝图保持原样。
- 归档文件已存在或无法验证与原文一致时停止升级，不覆盖既有迁移证据。

### 依赖与影响范围

- 影响技能入口、对话 SOP、迁移 SOP、蓝图规范和设计文档规范。
- 外部参考研究仍使用原证据与 clean-room 契约。

### 验收标准

- 新项目能分别形成项目蓝图和功能设计。
- 旧蓝图拒绝澄清时能只升级结构并保留旧待办语义。
- 旧蓝图含功能级细节时，升级前能逐字归档且新表设计依据仍为“待澄清”。
- 两个关联待办可在单问题对话下共享一份设计文档并引用不同章节。
- 后续指定待办时只询问未确认差量。

<a id="wp-03-validation"></a>
## WP-03 模板与校验

### 状态、范围与非目标

- 状态：已完成
- 范围：提供蓝图规范版本 2 模板、史诗设计模板和只依赖 Python 标准库的校验器。
- 非目标：不实现自动需求推断或自动改写旧蓝图的迁移程序。

### 前置条件、输入与输出

- 输入是蓝图或史诗设计文档路径。
- 输出是确定的成功或非零失败状态，以及可定位的版本、结构、编号、文件或锚点错误。

### 正常行为、权限与状态

- 蓝图校验版本、精确一级结构、五类项目边界、待办表头、唯一编号、合法依赖和非终态设计引用。
- 设计文档校验状态、公共章节、工作包章节、显式锚点、唯一工作包和状态一致性。
- Markdown 结构解析忽略代码围栏中的示例，并正确处理表格单元格中的转义管道符。
- “待澄清”是合法迁移状态，不要求存在空设计文档。

### 边界、失败与恢复

- 缺文件、缺锚点、终态工作包引用、非法或自依赖、重复编号、重复工作包、无效状态、伪造结构和旧格式都必须返回非零状态。
- 校验器只读，不修改输入；读文件失败必须报告原因。

### 依赖与影响范围

- 影响两个模板、校验脚本和黑盒测试。
- 不增加 `pyproject.toml` 或第三方库。

### 验收标准

- 两个待办引用同一设计文档不同锚点时校验通过。
- 已完成工作包的设计文档继续保留，但蓝图仍引用该工作包时校验失败。
- 直接迁移的“待澄清”行校验通过。
- 旧格式、缺文件、缺锚点、非法依赖、重复编号、重复工作包、围栏伪造和无效设计状态分别校验失败。

<a id="wp-04-workspace-migration"></a>
## WP-04 工作区迁移

### 状态、范围与非目标

- 状态：已完成
- 范围：把当前工作区根蓝图升级到规范版本 2，并无损迁移 5 个未设计待办。
- 非目标：不在本次澄清这 5 个待办的功能设计或依赖。

### 前置条件、输入与输出

- 输入是旧根蓝图及其中 5 个原待办。
- 输出是紧凑的项目级蓝图、稳定待办编号，以及明确的“待澄清”设计与依赖状态。

### 正常行为、权限与状态

- 根蓝图按项目定位、技术栈、代码结构、模块架构、跨模块契约、待开发功能和系统架构组织。
- 原待办按原顺序映射为 `PEND-001` 至 `PEND-005`，其名称、优先级和完成定义保持不变。

### 边界、失败与恢复

- 不从待办名称推断设计文档或前置依赖。
- 根蓝图未通过新校验器时迁移不得判为完成。

### 依赖与影响范围

- 影响工作区根蓝图、当前设计文档和发现入口。
- 不修改其他项目蓝图或用户工作区外文件。

### 验收标准

- 根蓝图通过版本 2 校验且 5 个旧待办语义不变。
- 当前设计文档通过设计校验。
- 新技能从工作区和个人发现入口均通过官方结构验证。
