# Nova 实施与交付 SOP

本文件承接旧全局 `AGENTS.md` 中除独立 Review 之外的实施约束。默认流程改为“编码 → 测试 → 本地 commit → 待人工 Review”；此顺序变化不删除任务基线、编码契约、测试证据、plan mode 或完成报告要求。

## 1. 准入、范围与任务差异基线

1. 当前实现事实以代码、测试和配置为准，项目级公共约束以 `PROJECT_BLUEPRINT.md` 为准；开发正式待办时必须读取其“设计依据”引用的工作包，但不得用设计文档证明代码已经实现。
2. 任务开始时，根据用户明确目标、当时蓝图条目及其设计依据固定工作项、范围、验收矩阵和未验证事项。执行期间新增待办、`Review-Defer` 或无关变化不自动纳入；用户扩围时，在新增范围首次编辑前补齐基线、设计依据和验收标准。
3. 标记“待澄清”的待办不得进入实施计划、编码、测试或 Review。只有用户完成澄清，补齐已确认设计依据和可执行验收后才能实施；主代理不得替用户推断、补写或选择结论。
4. 实施前记录仓库类型和根目录、Git/SVN 完整状态、任务声明路径或模块，以及这些范围内既有修改和未跟踪文件的可重建基线。相关路径已有修改时，在源码目录外保存只读内容快照或等价补丁；仅有文件名或哈希不能分离同文件的新旧行块。
5. “当前任务差异”只含相对任务开始基线由本任务新增、修改或删除的路径与行块。历史未提交代码不得因出现在 Git/SVN diff 或未跟踪列表中而纳入。无法可靠分离时停止编辑，请用户选择独立 worktree/checkout、明确扩围或先处理既有变更。
6. 基线保留到最终只读核对和报告内容生成完成；源码目录外的临时快照/补丁在发送报告前清理并报告清理结果。不得因上下文压缩、自检、Review 或续接而重建基线。
7. 实施 `PEND-*` 前运行设计校验并记录其 `Semantic-Fingerprint`。最低验收、提交和待 Review 交接前必须再次比较；只改变设计或工作包状态不得改变指纹。契约、工作包角色/交付/依赖或验收使指纹变化时立即停止，由用户确认设计变化后先更新设计依据和任务基线，并使直接受影响的实现与测试证据失效；不得以继续修改、自动续接或 Review 修复为由静默接受新语义。

## 2. 编码前契约

对 `Review-Policy: required` 的变更，编码前在计划或对话中的结构化变更说明固定：

1. **接口契约**：输入、输出、错误语义、兼容性、状态变化，以及跨调用边界的唯一权威定义与一致性要求；
2. **核心不变量**：必须始终成立的数据、状态、权限、资源或顺序约束；
3. **变更闭包**：修改点、直接调用方、消费者和受影响模块边界；
4. **失败语义**：关键失败点、恢复、重试、回滚、清理和错误传播责任；
5. **资源生命周期**：所有权、并发、取消、超时、释放和重复执行语义；
6. **验收标准**：每条核心契约和不变量对应的可执行验证。

非 plan mode 也必须在编码前输出上述结构；plan mode 写入待审批计划。客观豁免项仍须固定目标、精确范围和最低验收，但不强行为纯文档/格式变更虚构不适用的运行时契约。

## 3. 编码约束

- 正常路径和失败路径同时实现，不得先完成 happy path 再让测试决定异常语义；
- 在输入、接口和资源边界主动保证契约，不依赖调用方自觉传入合法值；
- 同一业务契约在前端、API、服务、任务、持久化等边界保持允许输入、状态转换和错误语义一致；交互层约束不同于业务契约时明确区分并说明理由；
- 上游校验只用于提前反馈，不能替代权威执行层的独立校验；
- 每个副作用都定义失败后的状态、补偿和错误传播；
- 修改接口、状态或资源边界时同步检查直接调用方、消费者及恢复/清理路径；
- 不得通过放宽校验、吞错、静默替换默认值/空值、改变既有语义或削弱断言来适配实现；
- 测试不得反向修改已确认方案来迁就代码；发现设计缺陷时先补全契约与失败语义；
- 同一失败连续修复三次仍未解决时停止，向用户报告证据、三次尝试和阻断点；
- 新依赖必须先声明。Python 依赖通过项目 `pyproject.toml` 安装；其他语言使用项目既有的权威依赖清单，不得绕过依赖管理器。

## 4. 测试与证据复用

1. 测试逐条覆盖固定验收标准的正常和失败路径。同一业务契约以共享用例或等价断言覆盖各调用边界，确认相同输入、状态转换和错误语义不会因层级不同而冲突。
2. 测试发现设计未覆盖的缺陷时，回溯补全契约和失败语义后再修复实现，不得在测试阶段临时决定契约。
3. 首次测试后记录：命令和工作目录、覆盖的验收项、相关代码/测试/配置/依赖及开发环境状态、结果和未验证事项。
4. 只有相关内容或开发环境变化、覆盖不足、结果失败/不完整，或用户明确要求重跑时，证据才失效。上下文压缩、自动续接、自检、Review、Verify、阶段变化及无关文件变化不使结果失效。
5. 证据有效时后续自检、Review 和 Verify 必须复用，不得重复运行。失效时先说明具体原因和影响范围，优先只运行受影响测试；未受影响证据继续有效。仅当验收要求全量或影响无法可靠限定时才全量运行。
6. 设计语义指纹变化属于相关证据失效条件；纯状态变化且指纹不变不使测试失效。

## 5. 提交与待 Review 交接

1. 最低验收通过且无阻断后按子任务创建精确范围本地 Git commit；不得夹带任务差异之外的历史修改，也不得提交未通过测试的代码。
2. 提交分类、稳定工作项、trailers 和客观豁免服从 `nova-review/references/commit-contract.md`。工作项未归档且修正仍属原设计、验收或当前 Review 时沿用相同 ID，追加 commit 和验证证据；可信审计归档后编号永久封存，后续变化重新分类建项。提交前使用仓库感知的 `validate-message --repo <根目录>` 拒绝归档 ID 复用，并校验明确来源 FIX 的 `Related-Work-Item` 指向可信归档 PEND。
3. 只有 `PEND-*` 在最低验收后把既有设计工作包改为 `待Review`，蓝图条目继续保留；`FIX-*`/`MAINT-*` 不创建蓝图条目或工作包。只有 `Review-Policy: required` 的提交由元数据进入待审集合；合法 exempt 的 `MAINT-*` 以豁免证据直接完成。
4. 默认不启动 Review。用户明确要求 Review 时才加载 `nova-review`；Review 中断可返回调试。只有有效 PASS 后才删除正式待办、完成工作包并写审计。
5. 全局治理代表精确范围本地 Git commit 的持续授权；用户明确“不提交”只撤回当次授权。Git push、远程配置和 SVN commit 始终需要针对具体操作的独立授权。

## 6. Plan mode 追加约束

Plan mode 只由用户手动启用，并追加以下约束：

- 走 Research → Create Plan → Obtain Approval → Execute → Verify，不得跳过；方案未经用户审批不得编码；
- Research 先读相关代码、测试、配置，再读蓝图公共约束；开发待办还要读取设计依据引用的工作包；
- Open Questions 至少确认一个会改变实现的决策点；
- 计划包含“关联”章节并列出蓝图模块编号；
- 验收逐条覆盖关键设计及异常/边界路径，多功能点存在数据依赖时列组合验收；
- 涉及持久化时，按项目真实启动方式加载配置并从最终生效配置解析存储路径，不得写死默认配置路径；
- Execute 仍按默认流程测试和提交；仅 required 项标记待 Review，合法 exempt 项直接完成；Plan mode 不自动启动 Review；
- Verify 只读核对固定范围、验收矩阵、有效测试证据、当前工作副本、本地 commit 和已有 Review 状态，不重跑未失效测试、不重新研究需求、不重建矩阵、不扩大范围；
- `required` 项未启动 Review 时 Verify 和完成报告写“未 Review”；合法客观豁免写 `exempt` 并核对 `EX-*` 与完整 diff 证据；两者均无 Review 轮次且不得表述为 PASS；只有已有真实 Review 结论时才按内容标识复用。

## 7. 代码完成报告

所有变更完成后必须使用以下结构。章节不得省略；无内容写“无”。`required` 项未启动人工 Review 时写“未 Review”；合法客观豁免写 `exempt`。两者都不是 Review PASS，也都没有 Review 轮次。

```markdown
## 变更报告

### 概要
- **工作项**: PEND-* / FIX-* / MAINT-*
- **变更分类**: designed / adhoc / maintenance
- **Review 策略**: required / exempt（exempt 必须同时列出客观规则和完整 diff 证据）
- **变更范围**: 一句话说明
- **关联模块**: PROJECT_BLUEPRINT.md 模块编号；不涉及写“无”

### 变更文件

| 文件 | 操作 | 说明 |
|------|------|------|
| path/to/file | 新增 / 修改 / 删除 | 一句话说明 |

### 关键决策
列出非显而易见的技术决策、理由和取舍；无则写“无”。

### 测试结果
- **执行命令与工作目录**: ...
- **结果**: 通过 / 失败（附摘要）
- **证据状态**: 本轮新执行 / 复用既有结果
- **覆盖范围**: 对应验收项
- **相关状态**: 代码/测试/配置/依赖/环境内容标识
- **未验证事项**: ... / 无
- **失效与重跑原因**: 未重跑写“不适用”

### 提交结果
- **本地 commit**: hash 与主题 / 用户当次撤回 / 未提交及原因
- **精确范围**: 本次提交包含的任务差异
- **远程与 SVN**: 未授权未执行 / 用户已明确授权后的结果

### Review 结果
- **状态**: 未 Review / PASS / PASS WITH NOTES / REJECT / exempt
- **轮次**: 未 Review 或 exempt 时写“不适用”；否则第 N 轮
- **内容标识与范围**: 完整任务 diff 标识及审查范围
- **证据状态**: 本轮新 Review / 复用既有结论 / 不适用
- **问题摘要**: 按轮次列出问题及修复/处置；无则写“无”
- **豁免依据**: exempt 时记录客观 `EX-*` 规则及完整 diff 命中证据；其他状态写“不适用”

### PROJECT_BLUEPRINT.md 与设计更新
- **蓝图**: 保留待办 / PASS 后已关闭 / 不适用
- **工作包**: 待Review / 已完成 / 不适用
- **审计**: 未生成 / 已生成路径 / 不适用

### 基线与清理
- **历史工作副本隔离**: 如何排除既有修改
- **临时基线材料**: 已清理及位置 / 未创建

### 遗留事项
本次未解决问题、后续待办或基线风险；无则写“无”。
```

文件路径使用相对项目根目录的路径。“关键决策”不得写“选择了更好的方案”等空泛措辞。每轮 Review 的问题与处理不得合并成无法审计的概括句。
