# 史诗设计文档规范

## 1. 文档职责

`docs/design/YYYY-MM-DD_<具体名称>.md` 保存一个史诗的共享契约和一个或多个相互关联的工作包。日期是文档首次创建当天的项目本地日期，必须是真实日历日期，后续修改不得改变；具体名称必须非空且能区分本次设计。

设计定义待开发目标，不充当当前代码说明书，也不复制蓝图全局规则。

当前实现事实仍以代码、测试、迁移和配置为准。

## 2. 元数据与状态

标题后必须包含：

```text
> 设计规范版本：4
> 设计状态：澄清中
> 演进来源：无
> 工作包：WP-01、WP-02
```

“演进来源”必须为 `无`，或指向同目录中一份已实现/已废弃设计的 Markdown 链接。新需求改变已完成设计所覆盖的原功能时必须填写链接；不得自引用、断链或指向尚未终态的设计。

设计状态只允许：

- `澄清中`：至少一个工作包为“待澄清”或“澄清中”；
- `已确认`：全部工作包已确认，但至少一个尚未完成；
- `已实现`：全部工作包均为“已完成”或“已废弃”，且至少一个已完成；
- `已废弃`：所有工作包均已废弃，并提供 `> 替代来源：[新设计](replacement.md)`。

工作包状态只在工作包地图维护一次，允许 `待澄清`、`澄清中`、`已确认`、`开发中`、`待Review`、`已完成`、`已废弃`。`待Review` 表示实现和最低验收已完成但尚无有效 Review PASS；该状态不是完成或终态。

新建或尚未终态的设计必须使用版本 `4`。版本 `3` 只允许作为 `已实现` 或 `已废弃` 的历史快照继续校验，不得恢复为活动状态或按新需求改写。历史版本 `3` 还必须在同目录 `.v3-legacy-snapshots.json` 中登记原文字节的 SHA-256，且当前文件必须与 Git `HEAD` 中同路径原文完全一致；新建、未登记或内容变化的版本 `3` 文件一律拒绝。

## 3. 共享约束

共享章节使用稳定锚点：

```html
<a id="shared-context"></a>
## 1. 共享约束
```

问题与结果：

```markdown
| 问题 | 成功结果 |
|------|----------|
```

只记录全部工作包共同需要的契约：

```markdown
| 契约 | 语义键 | 唯一规则 |
|------|--------|----------|
```

共享契约编号使用 `S-<编号>`。语义键是文档内唯一、稳定的短名称，推荐使用 `<范围>/<主题>`，例如 `共享/状态模型`。若工作包不共享目标、模型、不变量、依赖或组合验收，应拆成不同设计文档。

### 3.1 语义归一与唯一权威

- 一项会改变实现或验收的规范性语义只能存在于一个共享或工作包契约中；地图、摘要、图和验收只能引用契约 ID 或描述非规范事实，不得用近义句再次定义要求；
- 创建或修改契约前，按同一对象和主题归集用户原话、蓝图约束、代码证据和已有契约。同一语义键只能出现一次；
- 一个契约只表达一个可执行判断。独立改变结果的义务必须拆为不同契约，同一判断的目标值、硬性上下限、默认值、优先级和例外必须在同一契约中明确角色；
- 例如“目标 1 天完成，硬上限 2 天”应写成一个时限契约，不能写成两条可任选要求；若无法确认两句话是目标与上限、覆盖关系还是冲突，保留待确认并询问用户；
- 不得通过选择较宽松、较严格、较新、较靠后或更容易实现的表述消解歧义。只有语义关系唯一时才可归一。

业务关系、业务流程、业务状态或时序确有三个以上节点时可以增加 Mermaid；不得重复工作包地图中的状态、交付和依赖，也不得为了填模板创建空图。

## 4. 工作包地图

```markdown
| 工作包 | 角色 | 状态 | 交付结果 | 前置依赖 | 设计章节 |
|--------|------|------|----------|----------|----------|
```

- 工作包 ID 必须稳定且唯一；
- 角色只允许 `能力` 或 `收口`；单工作包设计只能使用 `能力`；
- 前置依赖只允许当前地图内工作包、`无` 或 `待澄清`；
- 设计章节必须链接到同一文件的显式工作包锚点；
- 地图是工作包状态、交付和依赖的唯一事实来源。

工作包按完整、可观察的功能能力划分，不按前端、后端、API、数据库、任务、测试或其他技术层拆分。一个能力工作包的实现可以同时修改所有相关技术边界。

多工作包设计必须有且仅有一个 `收口` 工作包。它直接依赖其余全部工作包，不重复实现各能力，而是负责共享成功结果、跨包契约和端到端组合验收。若多个工作包不需要共同收口即可分别达到各自目标，应拆成不同设计文档。

一个设计由蓝图中的正式工作项关闭时，可在工作包地图后声明权威关闭映射：

```markdown
### 2.1 工作项关闭映射

| 工作项 | 工作包 |
|--------|--------|
| PEND-001 | WP-01、WP-02 |
```

映射保留已经关闭的历史工作项；其中仍含未完成工作包的工作项集合必须与蓝图中引用该设计的活动 `PEND-*` 条目完全一致，全部工作包均为 `已完成` 的历史映射可以不再出现在蓝图。每个工作包最多归属一个工作项，全部 `待Review` 工作包必须有归属。Review 关闭请求中的 `package_ids` 必须按映射顺序完全一致，不得自行缩减或扩张。没有映射时，只允许该设计恰好对应一个蓝图工作项并关闭其 `Design-Ref` 所属的单个工作包；多个工作项共享设计或一个工作项关闭多个工作包时必须提供映射。

## 5. 工作包契约

每个工作包使用稳定锚点：

```html
<a id="wp-01-example"></a>
## WP-01 示例工作包
```

契约表：

```markdown
| 契约 | 维度 | 语义键 | 唯一规则 |
|------|------|--------|----------|
```

每个工作包必须覆盖以下六个维度；维度是防遗漏的覆盖面，不是固定六行。同一维度可有多个原子契约，但六类首次出现的顺序固定：

1. `交付边界`：本期结果及明确不做；
2. `参与者与权限`；
3. `触发与输入`；
4. `结果、状态与不变量`；
5. `失败与恢复`；
6. `AI 决策边界`：可自行决定和必须再次确认的范围。

契约编号使用 `<工作包 ID>-C<编号>`，例如 `WP-01-C01`。

语义键在共享契约和全部工作包中全局唯一。不得为了满足六维校验把多个规则塞进一行，也不得在不同维度重复同一规则；一个规则涉及多个维度时，选择决定其验收方式的主维度，其他维度通过契约 ID 引用。

业务流程、业务状态或时序复杂时可在契约表后增加 `### 行为图`，使用 Mermaid 表达；工作包依赖仍只保存在地图，简单行为不创建该章节。

验收表：

```markdown
| 覆盖契约 | 场景 | 预期结果 |
|----------|------|----------|
```

每个工作包契约必须至少被一个验收场景覆盖。验收只引用契约 ID 并给出可执行场景与观察结果，不得引入契约中不存在的新义务。

收口工作包必须至少有一个验收场景同时引用其余每个工作包的一项契约，证明端到端组合结果；不得复制一份“组合验收关系”或重新表述各包内部规则。

## 6. 澄清暂存

只有设计状态为“澄清中”时才保留：

```markdown
## 3. 澄清暂存

| 类型 | 内容 | 来源 |
|------|------|------|
| 待确认 | ... | 用户尚未决定 |
```

类型只允许 `证据推断` 或 `待确认`，且至少有一条“待确认”。已确认要求必须进入共享或工作包契约；文档进入“已确认”“已实现”或“已废弃”后删除整个暂存章节，不保留“无”的空章节。

## 7. 锚点、读取与生命周期

- 蓝图只引用显式 HTML 锚点，不引用行号；完成后锚点仍保持稳定；
- 设计文件名始终保留首次创建日期，修改正文、状态或工作包不得重命名为修改日期；
- 开发某个工作包时读取蓝图、设计元数据、共享约束、当前工作包及直接依赖；是否读取其他章节由代码影响分析决定，不在每份设计文档重复声明；
- 工作包进入实施前运行设计校验并记录 `Semantic-Fingerprint`。该指纹覆盖问题与成功结果、演进来源、共享契约、工作包角色/交付/依赖、工作包契约和验收，但排除设计状态与工作包状态；
- `开发中`、`待Review` 或 `已完成` 工作包的设计语义视为冻结。状态推进不得改变指纹；指纹变化必须停止实现，由用户确认语义变化，先更新设计和实施基线，再使直接受影响的实现及测试证据失效；
- 工作包确认后，蓝图待办才链接其锚点；中途停止时蓝图仍写“待澄清”；
- 工作包实现并通过最低验收后进入“待Review”，蓝图继续保留对应待办；只有有效 Review PASS 后才从蓝图删除并将设计地图状态改为“已完成”；
- 全部工作包进入“已完成”或“已废弃”且至少一个已完成后，设计状态改为“已实现”；全部工作包废弃时改为“已废弃”；
- `已实现`和`已废弃`是终态历史快照，不得为后续需求追加工作包、修改已确认契约或改回非终态；后续需求必须新建日期文件，并以“演进来源”链接旧设计；
- 尚未终态的同一史诗只有在共享目标、模型或不变量仍成立时才可追加工作包；否则新建设计；
- 尚未实现的设计被取代时保留旧文档，标记“已废弃”并链接替代来源。

### 7.1 旧式文件名迁移

版本 3 项目的当前待办、当前设计或校验结果出现无创建日期的旧式设计文件名时，只迁移设计路径及其引用，不升级蓝图七章结构：

1. 先列出旧路径、新路径、日期证据和全部已知引用，取得用户确认后再写文件；
2. 日期优先取文档中可验证的首次创建记录；没有记录时，取当前文件连续版本控制谱系的首次加入日期，并转换为项目本地日期；
3. 文件曾删除后重建时，只有历史和内容能证明仍是同一设计谱系才沿用原日期；无法证明、没有版本历史或不同证据冲突时停止迁移，只询问首次创建日期，不得使用迁移当天日期；
4. 重命名时保留标题、契约和稳定锚点，只补充当前规范必需的元数据，并在同一变更中更新蓝图、设计及项目内已知引用；
5. 任一引用无法安全更新、源文件在迁移中变化或迁移后校验失败时停止，不形成部分迁移结果。

## 8. 完成检查

- 新建或活动设计规范版本为 `4`；终态版本 `3` 只作已登记且与 Git `HEAD` 原文一致的历史快照；文档状态与工作包地图一致；
- 文件名符合 `YYYY-MM-DD_具体名称.md`，日期有效且具体名称非空；
- 演进来源为“无”或指向同目录终态设计；新需求没有复用终态文档；
- 共享契约和工作包契约编号唯一；
- 每个工作包只有一处状态和依赖；
- 语义键全局唯一，一项规范性语义只有一个权威契约；六类工作包契约按首次出现顺序覆盖且允许重复维度，验收逐条引用覆盖；
- 单工作包设计没有收口包；多工作包设计有且仅有一个收口包，直接依赖其余全部包并具有覆盖全部前置包的组合验收；
- 锚点、地图链接和蓝图引用可解析；
- 非澄清状态没有证据推断、待确认或空占位章节；
- 没有复制蓝图全局规则或代码可恢复细节。
