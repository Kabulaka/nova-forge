# 项目头脑风暴与设计收敛

让用户按自己的思路描述。AI 在后台维护关系、证据和影响范围，前台只呈现当前结论和一个最小问题。

## 不可违反

1. 每轮最多一个问题，只确认一个信息维度；用户应能用短语或一句话回答。
2. 能从代码、配置、测试、运行契约或指定参考源查明的事实先研究，不让用户代替检索。
3. 区分“已确认”“证据推断”“待确认”，未经用户接受的推断不得写成正式要求。
4. 蓝图只保存所有模块长期共用的事实；史诗与工作包设计进入 `docs/design/*.md`；当前实现以代码、测试、迁移和配置为准。
5. 一个史诗可含多个相关工作包，蓝图待办可引用同一设计的不同稳定章节；没有共享语义时拆分设计。
6. 用户可见回复必须移除推理草稿、规则自检、代理身份、工具过程、孤立人名和无上下文英文；写正式要求或扩大范围前必须取得确认。
7. 每次取得有效答案后重新计算待确认差量和研究任务；任一未清空时不得宣称话题收敛，已确定下一动作时不得只报告“下一步”而不执行。文本与原生提问工具适用同一状态语义。

## 1. 先定位项目，再加载上下文

先从用户明确路径、当前请求指向的仓库或已确认会话状态确定目标项目。只因当前目录存在蓝图，不得把它当成目标项目。未能安全确定且不同路径会改变结果时，只问项目位置。

会话内维护：目标根目录绝对路径、蓝图绝对路径、规范版本、蓝图 SHA-256、已加载的项目指令，以及访谈 SOP SHA-256。用户无需管理这些状态。

### 实施请求前置路由

用户明确要求实施某个编号时，此路由优先于下述首次进入和蓝图版本路由。先读取目标项目指令并检查精确蓝图路径，再以编号或稳定锚点定向读取目标条目；不得在确认交接资格前把蓝图全文展开到模型上下文。条目具有已确认设计依据和可执行验收标准时，再定向读取所引工作包、直接依赖和本任务实际涉及的公共约束，并按“已确认工作包的实施交接”执行。目标条目无法定位、仍为“待澄清”、设计依据缺失、验收不可执行或契约冲突时，退出实施路由并转入单问题澄清；只有无法通过定向读取判断阻断原因时，才按首次进入和版本路由补读必要范围。

### 首次进入或状态失效

未命中实施请求前置路由且发生任一情况时，先读取目标项目指令并检查精确蓝图路径是否存在。蓝图不存在时记录“无蓝图”，不得对不存在的文件计算 SHA-256 或要求全文；蓝图存在时，从同一份稳定快照取得全文、版本与 SHA-256：

- 新会话首次进入目标项目；
- 切换项目或蓝图路径；
- 没有可信的会话内理解；
- 当前 SHA-256 与记录不同。

对已存在蓝图，在读取前后分别计算 SHA-256；两次不一致时丢弃正文并重新读取，连续变化无法取得稳定快照时停止并报告，不绑定旧理解与新哈希。首次向用户提问前，完整读取一次 [访谈 SOP](references/conversation-sop.md) 并记录其 SHA-256。除已保存实施交接且其列明的失效条件均未发生外，上下文丢失时按首次进入处理，不猜测旧状态。

### 同一会话续问

每次继续访谈前，先用不向模型上下文展开正文的方式计算当前蓝图与访谈 SOP SHA-256。项目、路径、蓝图指纹和 SOP 指纹均未变化时，复用已有理解，只读取当前待办、相关蓝图章节、设计元数据、当前工作包及其直接依赖；不要重读完整蓝图或访谈 SOP。代码影响分析表明范围扩大时，再补读受影响部分。

蓝图指纹变化时立即废弃旧理解并完整重读；SOP 指纹未记录或发生变化时只完整重读访谈 SOP，保留已确认的项目理解。任一文件读取前后指纹不一致时重新读取，连续变化则停止并报告。不得跨会话或跨项目复用缓存。

## 2. 按蓝图版本路由

未命中实施请求前置路由时，首次进入或缓存失效必须先完成上一节的文件存在性检查；蓝图存在时再完成稳定快照全文读取并按已读版本分流，不得用单独读取版本标记替代首次完整读取。同会话缓存有效时使用已记录版本：

- 不存在蓝图：按新项目推进，不加载迁移 SOP。
- 明确为版本 3：正常澄清和只读分析不加载迁移 SOP；用户明确要求迁移审计时例外。当前待办、当前设计或校验结果出现旧式设计文件名时，只读取设计规范并执行其中的“旧式文件名迁移”，不进入七章蓝图迁移决策门。
- 已存在蓝图但版本标记缺失、版本不是 3，或用户明确要求迁移审计：完整读取 [迁移 SOP](references/blueprint-migration-sop.md)，进入迁移决策门。

旧版蓝图不得套模板覆盖。迁移决策门必须先完成迁移报告：逐项列明新版七章职责，并按原标题或摘要列出每段待归档局部内容，不得用概括句替代证据清单；然后只询问“先澄清后升级、立即升级、暂不升级”这个三选一决定。用户明确选择前，禁止追问待办功能、加载蓝图规范、创建或修改文档、运行校验器；不得替用户决定“本轮不迁移”。选择后的处理严格按迁移 SOP，且每轮仍只询问一个差量。

## 3. 研究与澄清

已有代码库时，围绕当前主题研究入口、模块边界、直接调用关系、权限、存储、失败恢复和测试；冲突标为待确认。

用户指定外部产品、功能或 GitHub 项目时，完整读取 [参考研究 SOP](references/reference-research-sop.md)。范围明确且支持子代理时，启动一个或多个只读探索子代理；主代理只向用户输出参考事实、适配建议、不建议照搬之处和一个确认问题。宽泛的“类似某产品”先问一个范围问题。

沿当前语境选择影响最大且证据不足的一个差量。用户谈 A 时涉及 B，只有 B 会改变 A 的当前含义才立即问，否则暂存。逐轮闭环目标、参与者、触发、结果、权限、状态、边界、失败恢复、明确不做和验收证据；不要按文档章节审问用户。

架构讨论来自已确认场景、失败语义和非功能要求。必须澄清代码结构、系统分层及其目录映射；内部实现细节可由开发时分析，不用提前写成长说明。

### 已确认工作包的实施交接

任何 `PEND-*`、`FIX-*` 或 `MAINT-*` 实施开始前，完整读取 [实施与交付 SOP](references/implementation-sop.md)。本节只定义与需求/设计状态衔接的增量规则，不替代其中的任务差异基线、编码契约、测试证据、提交、plan mode 或完成报告约束。

用户明确要求实施某个编号，且蓝图条目具有已确认设计依据和可执行验收标准时，进入实施交接，不重新运行需求访谈。只读取该条目、所引工作包、直接依赖和本任务实际涉及的公共约束；复用当前可信的项目、路径和指纹状态，不重读完整蓝图、访谈 SOP 或已闭环关系。本技能负责固定最小上下文、快速实现、最低验收和待 Review 交接；用户明确启动 Review 时再转交 `nova-review`。

本轮从需求澄清新建正式 `PEND-*` 时，只要用户未把任务限定为仅头脑风暴、澄清、规划、蓝图、设计或文档，当前不处于尚待方案批准的 Plan mode，且工作包已确认、蓝图引用与可执行验收完整、蓝图和设计校验通过，就自动进入同一实施交接；不要求用户在原始请求中再次说“实施”或报出新编号。不得以仅交付文档的回复结束当前执行周期，也不得再次询问是否开始编码；立即完整读取实施 SOP、固定任务差异基线并按默认实施流程推进。用户明确暂停或取消、上述范围限制、待确认差量、研究证据不足、文档校验失败、契约冲突或无法安全隔离既有工作副本变化时停止；Plan mode 继续服从其方案审批门禁。

交接时固定任务编号、范围、设计依据、验收标准和未验证事项。上下文压缩、自检、显式 Review 或继续修改不使交接失效；只有目标路径、蓝图或设计指纹变化，用户明确扩围，或实现证据暴露契约冲突时，才重读受影响部分并重新计算差量。条目仍为“待澄清”、设计依据缺失、验收不可执行或契约相互冲突时，不得实施；退出交接并按单问题规则只确认一个差量。

创建新工作项时，先按提交契约确定分类，再调用 `nova-review/scripts/nova_review.py new-id --class <分类>` 生成一次 UUIDv7 编号；既有数字编号继续沿用。编号一经进入蓝图或提交即固定，后续开发和 Review 不得重新生成或替换。

默认实施流程是编码、最低验收、记录有效测试证据和本地 Git commit。只有 `PEND-*` 的设计工作包在最低验收后更新为 `待Review`；`FIX-*`、`MAINT-*` 不创建蓝图条目或工作包。`Review-Policy: required` 的提交进入待审集合，合法 exempt 的 `MAINT-*` 以客观豁免证据直接完成。全局治理中的持续授权使精确范围本地 commit 无需逐次询问，用户明确要求不提交时只撤回当次授权。不得自动启动 Review。正式 `PEND-*` 在 Review PASS 前继续保留于蓝图，提交使用 `Change-Class: designed`、相同 `Work-Item` 和设计引用；用户测试后要求继续修改时沿用同一编号并追加 commit 与验证证据。push 和 SVN commit 必须另行授权。

用户明确要求 Review 时才加载 `nova-review`。Review 中断则保留 `待Review` 并返回调试；PASS 后由 `nova-review` 完成蓝图删除、设计终态和审计归档。Review-Defer、新增待办及无关蓝图变化不自动进入当前范围。

## 4. 形成文档

讨论结论满足任一条件时，提炼后写入蓝图：影响多个模块、模块职责或依赖方向、全局权限/安全/数据生命周期、公共外部契约、项目级非功能指标，或所有后续功能必须遵守。其余局部交互、流程、状态、失败恢复和验收只进入设计。

创建或升级蓝图前，读取 [蓝图规范](references/blueprint-standard.md)；新建时使用 [蓝图模板](assets/PROJECT_BLUEPRINT.template.md)。创建或更新设计前，读取 [设计规范](references/design-document-standard.md)；新建时使用 [设计模板](assets/DESIGN.template.md)，文件必须命名为 `YYYY-MM-DD_具体名称.md`。首次创建相应文档类型时，再读取 [完整示例](references/examples/equipment-borrowing/PROJECT_BLUEPRINT.md) 及其关联设计；模板不替代示例。

`已实现`、`已废弃`设计是终态历史快照。新需求即使基于原功能，也不得向终态文档追加工作包或改回非终态；必须用创建当天日期新建设计，并通过“演进来源”链接旧设计。只有同一史诗尚未终态时，关联工作包才可继续共用原文档。

一个工作包只有完成澄清后才能成为蓝图中的有效设计链接。中断时可保留“澄清中”设计，但蓝图仍写“待澄清”。写文件前展示自然语言摘要、目标文件和待办引用变化，取得用户确认后再写。

`PEND-*` 工作包完成最低验收后标记为 `待Review`，正式待办继续留在蓝图；`FIX-*`、`MAINT-*` 不创建工作包。只有 `nova-review` 记录有效 PASS 后才从蓝图删除对应条目并把工作包标记为“已完成”；设计文档和稳定锚点始终保留。全部工作包完成或废弃且至少一个完成时，设计标记“已实现”；全部废弃或被整体替代时标记“已废弃”并链接替代来源。

## 5. 校验触发

以下操作完成后运行对应校验器：创建、修改或迁移蓝图/设计；改变待办引用、工作包状态或文档生命周期；交付本轮已变更文档前。

```bash
python3 scripts/validate_blueprint.py /absolute/path/to/PROJECT_BLUEPRINT.md
python3 scripts/validate_blueprint.py --design /absolute/path/to/docs/design/2026-08-26_example.md
```

纯头脑风暴、继续提问、解释规则、读取项目和只读分析不运行校验器。校验不代替项目要求的测试、显式 Review 或提交门禁。
