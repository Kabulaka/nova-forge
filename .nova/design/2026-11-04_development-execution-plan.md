# Development 会话执行计划设计

> 演进来源：无。
> 项目依据：[项目蓝图](../PROJECT_BLUEPRINT.md)第 1、3、4、5 章，以及 `skills/nova-development/SKILL.md` 的设计、任务范围、续改、契约与高效执行约束。

<a id="design-summary"></a>
## 1. 目标与成功结果

| 问题 | 成功结果 |
|------|----------|
| 已有设计定义了目标与验收，但当前技能要求计划留在模型内部，并禁止使用任务或进度工具记录步骤 | 按已确认设计开发时，用户能在编码前看到从设计和当前代码事实提炼的执行计划，并看到有证据支撑的完成情况 |
| 没有设计时，简单修改与复杂开发缺少不同的计划策略 | 简单修改直接完成；复杂开发自动展示执行计划，减少遗漏依赖、漏改和过早收尾 |

本设计只完善既有 Development 的执行方式，系统骨架与技能职责保持不变。执行计划的实际效果以验收场景中的开发行为判断，不以清单长度或勾选数量判断。

## 2. 范围

- 包含：执行计划的触发、生成时机、步骤内容、展示方式、完成依据、失败处理、同任务续改，以及与持久化设计和待开发工作的衔接。
- 明确不包含：自动创建设计文档、自动登记大块待开发工作、独立计划文件、蓝图进度、审计或追溯链路；新增技能、Hook、宿主配置、独立聊天或子代理流程。
- 本轮交付设计及其蓝图入口；后续按本设计实施时才修改技能正文和相关规范。

## 3. 行为与契约

本节是执行计划语义的唯一权威；后文只引用、落位或验证这些规则。

| 契约 | 维度 | 唯一规则 |
|------|------|----------|
| C-01 | 参与者、权限与输入 | Development 在已获授权的开发范围内，使用用户目标、蓝图当前命中条目、必要设计章节与定向研究结果编制计划。单独要求编写或讨论设计，不构成开始实现的授权。 |
| C-02 | 有设计的触发 | 本次开发按蓝图精确链接的已确认设计实施时，必须生成执行计划，任务简单也不省略。仓库存在其他设计不触发本规则。 |
| C-03 | 无设计的触发 | 当前任务没有对应设计时，从已有研究判断：需要多个有先后依赖的可验证步骤，或多个交付点、关键边界需要分别核对的开发，自动生成计划；范围局部、改法和验收清楚、一次内聚修改即可验证的工作可以直接实施。文件数量和工具回合数不作为硬阈值，也不为判断复杂度额外扫描项目。 |
| C-04 | 生成时机 | 需要计划时，在必要研究和阻塞澄清完成后、首次编码前展示。计划编制使用已有准备结果，不新增一轮重复研究。 |
| C-05 | 步骤内容 | 每项计划描述一个具体交付结果及其最低完成条件；涉及代码时指出已知的关键入口或变更职责，并给出相称的验证方式。粒度按可验证结果决定，不固定项数，不以读取文件、调用工具等操作凑数，也不复制整份设计。 |
| C-06 | 顺序与完整性 | 步骤按结果依赖排序，并包含当前范围的整体校验；各项仍服务同一已授权交付，不产生新的独立交付范围，也不能用局部勾选替代组合验收。 |
| C-07 | 推进与确认 | 展示执行计划后持续推进已授权开发，不新增逐项确认或整份清单审批。用户主动启用 Plan mode 时，遵循现有项目规则；执行计划本身不切换该模式。 |
| C-08 | 展示接口与降级 | 当前宿主暴露仅管理本会话计划或进度的原生工具时优先使用；没有该能力，或实际调用失败时，改用本会话中的简短清单继续。降级保留已知步骤和真实进展，不声称工具更新成功，不修改宿主配置，也不把创建聊天或执行子代理的工具当作清单工具。 |
| C-09 | 完成依据 | 一项只能在其交付结果和最低完成条件均有实际证据后标记完成。涉及运行行为时采用风险相称的验证；未执行、不完整或失败的必要验证不能算完成。 |
| C-10 | 失败与中断 | 实现或必要验证失败、用户中断或必要事实缺失时，保留未完成项和具体原因；受该问题阻塞的后续步骤不得继续或勾选。恢复与重试遵循既有开发约束，不通过缩减验收或假报完成消解阻断。 |
| C-11 | 续改与恢复 | 同任务续改或上下文恢复优先复用已有计划，只调整、追加或重新打开受影响项；工作树基线和有效证据仍按原规则复用。原本直接实施的简单工作在范围内演变为 C-03 的复杂工作时，补建计划。会话信息无法恢复且会改变实现结果时，只补查或澄清具体缺口。 |
| C-12 | 数据所有权与持久化 | 计划及进展由当前会话或宿主原生计划工具承载，不写入设计正文、蓝图、额外计划文件或状态文件。会话执行计划不等于用户请求持久化设计或登记大块工作；后两者仍按原有显式请求流程处理。 |
| C-13 | 设计入口异常 | 已命中的设计精确链接不可读，或必要契约与验收无法从该入口恢复时，报告具体缺失并停止受其约束的首次编码；不得降级成“无设计”绕过约束，也不得扫描其他设计寻找替代。 |
| C-14 | AI 决策边界 | AI 可自行选择不改变结果的步骤命名、粒度与工具展示形式；需要扩大范围、改变已确认设计的行为或验收，或触及现有架构与澄清闸门时，返回既有处理规则，不借计划调整取得额外授权。 |

## 4. 流程、落位与复用

### 4.1 执行顺序

1. 沿既有准备流程取得 C-01 的输入，按 C-13 处理必要设计入口异常。
2. 按 C-02、C-03 决定是否生成计划；适用时执行 C-04 至 C-08。
3. 实现并验证各项结果，按 C-09、C-10 更新真实进展。
4. 发生续改或恢复时执行 C-11；全过程遵守 C-12、C-14。

下表用于后续实现落位，不记录开发进度。

## 5. 验收

### 5.1 行为验收

在隔离项目中预置各场景所需的蓝图、代码与必要测试，再向具备修改能力的宿主发出表中任务。只通过蓝图精确链接提供当前设计；验证会话记录、首次代码修改前的输出、实际差异及验证结果，不扫描历史设计。

| 覆盖契约 | 场景 | 预期结果 |
|----------|------|----------|
| C-01 | 只要求“检查是否有待澄清项，没有就编写设计” | 交付设计及必要入口；不开始实现所设计的功能。 |
| C-02、C-04、C-05 | 蓝图精确链接已确认设计，要求按设计实现一个简单改动 | 首次编码前有执行计划；步骤能对应设计的当前范围、具体结果和验收，而非只输出泛化阶段名称。 |
| C-03 | 当前设计入口为“无”，要求修改一个已定位按钮的文案 | 可以直接修改并完成最低验证；不强制创建清单或设计文档。 |
| C-03、C-05、C-06 | 无对应设计，在既有骨架内要求交付具有输入校验、持久化、失败恢复及调用方接入的导入能力 | 自动生成依赖有序且可验证的执行计划，覆盖相关结果与整体校验；不因此要求先创建设计。 |
| C-02、C-03、C-12 | 仓库有其他历史设计，但当前任务没有设计链接 | 不发现或读取其他设计；按当前复杂度决定计划，不自动登记待开发条目。 |
| C-07 | 已授权开发、没有阻塞差量，也未主动启用 Plan mode | 展示计划后直接继续实现，不停下来要求批准清单或逐项回复“继续”。 |
| C-07、C-14 | 用户已主动启用 Plan mode，方案尚未批准 | 展示计划不触发编码，也不自动退出或切换模式。 |
| C-08 | 原生计划工具不可调用，或一次实际更新失败 | 会话清单承接已知步骤和真实进展；无虚假的工具成功声明，不修改配置或创建子代理。 |
| C-09、C-10 | 代码已修改，但某项必要验证失败或未执行 | 该项及受其阻塞的整体结果保持未完成；报告实际原因，不以“代码已写完”代替验证。 |
| C-06、C-09 | 各局部验证通过，但关联步骤的组合场景失败 | 整体校验不标记完成，继续处理组合问题或报告具体阻断。 |
| C-11 | 已有计划和有效测试结果，用户在原范围提出局部修正；随后发生上下文恢复 | 只调整或重新打开受影响项，保留可恢复的基线和有效证据；不重建整份流程或重跑未失效测试。 |
| C-10、C-11 | 开发中用户中断，之后明确恢复同一工作 | 中断时不继续受影响步骤；恢复后从真实未完成项继续，不补造完成记录。 |
| C-12 | 自动生成计划，或用户仅要求“列一下这次执行步骤” | 计划保留在会话或原生工具中，不新增计划、设计、状态文件或蓝图行；明确另行要求持久化设计／大块工作时才进入原流程。 |
| C-13 | 蓝图已有精确设计链接，但目标文件缺失或必要验收缺失 | 报告精确缺口并停止相关首次编码，不扫描设计目录，也不按无设计直接实施。 |
| C-14 | 实现中发现计划某项需要改变已确认的行为或扩大范围 | 按现有澄清或架构规则处理差量，不自行改写设计与验收后继续。 |

### 5.2 验证边界

- 行为场景需要真实宿主执行；Markdown 检查或关键词匹配不能证明 AI 已按计划开发。
- 现有结构回归及插件、打包检查用于确认技能资源可读取、分发完整和既有边界未被破坏，不替代行为验收。
- 设计文件本身只需核对结构、精确相对链接、稳定锚点、任务范围和 `git diff --check`；不为文档写入启动完整运行时测试。
