# AI Skills 工作区 — 产品需求

> 需求规范版本：1
> 产品版本：v4
> 文档定位：总体业务流程、业务模块与需求块索引的长期契约。

## 1. 产品定位

| 对象 | 核心问题 | 成功结果 |
|------|----------|----------|
| AI 技能使用者与维护者 | 访谈可能把完整性误解为逐项提问，用户委托 AI 采用成熟方案后又无法看到 AI 的具体决定和依据 | 需求、架构和开发访谈只询问真正改变交付结果的事项，AI 的代决策有证据、完整披露、可修正并由用户最终确认 |
| Codex 与 Claude Code 使用者和插件维护者 | 手工链接规则与技能不便安装和升级，长会话压缩后还可能丢失已确认决定与当前交付状态 | 使用者通过有明确版本的插件获得一致的 Nova 能力，并在同一会话压缩或恢复后自动延续有效任务状态 |
| Codex 与 Claude Code 用户 | 长任务经过上下文压缩后可能遗漏用户决定、当前范围、控制约束或下一动作，依靠反复加载完整技能与规范恢复又持续消耗上下文 | 两个宿主通过同一份轻量全局规则提高压缩信息完整性，既有决定不被无故重问，未变化控制文档不因恢复而重复全文加载 |
| Nova 需求方与交付维护者 | 已确认需求可能长期停留在未提交工作树，任务类型、蓝图状态、完成报告和提交边界又容易因自然语言规则分散而失真 | 每版需求确认后立即形成不可变本地检查点；按 REQ、ARCH、FEAT、PATCH、FIX、MAINT 的真实语义分类交付，并以最少状态、清晰报告和确定性校验保持闭环 |

## 2. 端到端业务流程

| 步骤 | 参与者 | 业务输入 | 业务结果 |
|------|--------|----------|----------|
| 1. 表达目标与委托 | 用户 | 业务目标、参考对象或采用成熟方案的授权 | 明确当前阶段目标、委托范围和用户保留的决策权 |
| 2. 研究并形成候选 | AI | 当前项目事实、外部标准和可验证参考资料 | 分离参考事实与适配判断，形成具体 AI 候选决定 |
| 3. 披露与修正 | AI 与用户 | 候选决定、依据、影响、不采用内容和证据边界 | 用户能够理解并修正与预期不一致的决定 |
| 4. 整体确认与分层交付 | 用户与 AI | 无待确认差量的整份摘要 | 用户确认正式契约，随后按需求、架构和开发的权威边界继续交付 |
| 5. 固化需求基线 | AI | 用户明确确认且通过校验的完整需求版本 | 需求文档立即形成独立本地检查点，下游只绑定该提交中的版本和内容指纹 |
| 6. 判断架构差量并建立交付台账 | AI 与用户 | 已提交需求、当前共享契约和需求级交付拆分 | 无架构差量时不创建架构成果；有差量时形成 ARCH。首个开发切片前一次性登记全部稳定 FEAT、依赖、完成定义和需求引用，需求进入开发中 |
| 7. 分类交付、报告并跟踪 | AI 与用户 | 完整台账、当前任务、既有契约及其详细设计 | FEAT、PATCH、FIX、MAINT 各守边界，完成报告直述结果和待 Review 状态；正式 Review 的拒绝修正在同一任务中收敛，PASS 后只形成一次闭环提交 |
| 8. 安装轻量全局规则 | 用户 | Nova Forge 工作区及 Codex、Claude Code 的用户级规则入口 | 通过统一安装脚本为两个宿主启用同一份压缩保留规则，并安全处理已有入口 |
| 9. 获取并启用插件 | 用户与插件维护者 | 已明确发布的插件版本、宿主和信任选择 | Codex 与 Claude Code 使用者获得一致的 Nova 规则和技能，默认不再维护个人软链接 |
| 10. 自动保存会话状态 | AI 与宿主 | 用户确认、范围变化、提交、Review 等语义边界 | 当前目标、决定、证据和下一动作形成与当前会话绑定的有效检查点 |
| 11. 压缩、恢复与异常处理 | AI 与宿主 | 同一会话发生压缩、恢复或继续，或插件与检查点异常 | 恢复静态规则和最近有效检查点；异常时明确提示并阻止不安全推进，必要时使用兼容入口 |

## 3. 业务模块

| 业务模块 | 职责 | 边界 |
|----------|------|------|
| 访谈治理 | 负责三阶段问题选择、委托决策、外部参考研究、候选披露、修正和最终确认 | 不负责替用户确认业务或公共契约，不负责自动实施或启动 Review |
| 插件分发与会话续接 | 负责 Codex 与 Claude Code 的统一插件交付、版本发布、同会话自动检查点及压缩恢复 | 不负责跨会话、跨宿主、跨设备或团队状态同步，不替代宿主的插件信任与权限控制 |
| 会话连续性 | 负责为 Codex 与 Claude Code 提供同一份轻量压缩保留规则和安全安装入口 | 不建设独立状态系统，不保证宿主压缩绝不遗漏，不让新会话自动继承旧任务 |
| 交付治理 | 负责确认需求的独立基线提交、架构零差量判定、任务分类、完整切片台账、最小状态、阶段报告、提交边界和整体进度展示 | 不为每个请求制造需求或架构成果，不替代单项实现、测试或人工 Review，不用额外状态和文件掩盖语义问题 |

## 5. 范围边界

| 边界 | 内容 |
|------|------|
| 本期范围 | 需求、架构和开发访谈中的问题价值判断、委托决策、外部证据综合、候选披露、用户修正和整份摘要确认；确认需求的独立提交与下游绑定；REQ、ARCH、FEAT、PATCH、FIX、MAINT 分类；完整切片台账、最小状态、阶段报告、提交边界、代码化校验和进度展示；Codex 与 Claude Code 共用的轻量压缩保留规则、安全安装、版本化插件分发、同一会话本机自动检查点、压缩恢复及兼容安装入口 |
| 明确不做 | 复制参考项目全部功能、代码、界面或资产；用用户沉默代替确认；为完成流程制造形式性问题或架构成果；让需求或交付计划检查点进入人工 Review；把后续切片只保存在会话；按文件或 Review 轮次制造碎片提交；自动启动 Review；为每个状态或报告增加独立文件；跨会话、跨宿主、跨设备或团队状态同步；凭据落盘 |
| 后续候选 | 申请宿主官方公共目录；在独立确认身份、权限、冲突与隐私边界后评估跨会话或跨设备连续性 |
