# Codex与Claude Code插件分发及同会话压缩续接

> 需求块规范版本：1
> Requirement-Key：REQ-01a06524-60ee-7d61-a9f1-c588cd2bfdff
> 需求版本：v1
> 所属模块：插件分发与会话续接

## 1. 目标

| 业务问题 | 成功结果 |
|----------|----------|
| Codex 与 Claude Code 使用者需要手工维护规则和技能链接，升级不便；长会话压缩后还可能遗失已确认决定、活动范围和下一动作 | 使用者通过明确版本的插件获得一致的 Nova 能力，并在同一宿主、同一会话的压缩或恢复后自动延续最近有效任务状态，无需手工保存 |

## 2. 参与者与业务流程

| 步骤 | 参与者 | 触发与输入 | 业务结果 |
|------|--------|------------|----------|
| 1. 发布插件版本 | 插件维护者 | 通过验收并被明确标记为正式版本的 Nova 能力 | GitHub 分发入口提供版本可识别、可安装的 Codex 与 Claude Code 插件 |
| 2. 安装并启用 | 用户 | 选择目标宿主、插件版本并完成宿主要求的信任操作 | 当前宿主获得与该版本一致的 Nova 规则和技能，插件成为默认入口 |
| 3. 开始或恢复会话 | 用户与 AI | 新建会话，或继续同一宿主中的既有会话 | 静态治理规则生效；恢复同一会话时同时取得最近有效检查点 |
| 4. 自动形成检查点 | AI | 用户确认、范围变化、提交、Review 或其他改变任务权威状态的语义边界 | 目标、阶段、确认项、排除项、当前问题、范围、证据和下一动作自动保存，用户无需额外操作 |
| 5. 压缩并续接 | AI 与宿主 | 当前会话发生自动或手动压缩 | 压缩前冻结有效状态，压缩后先恢复规则和检查点，再从原任务的下一动作继续 |
| 6. 处理异常或兼容宿主 | 用户与 AI | 检查点不可用、插件未启用，或宿主不能加载插件 | 明确说明不可恢复的边界；必要时阻止不安全推进，并允许使用兼容安装入口 |

## 3. 业务规则

| 规则 | 唯一定义 |
|------|----------|
| R-01 | Codex 与 Claude Code 必须分别提供可安装的插件入口，并向使用者呈现同一版本的 Nova 核心规则与技能能力。 |
| R-02 | 插件是支持插件宿主的默认安装和升级入口；使用者无需为正常安装手工创建或刷新规则与技能软链接。 |
| R-03 | 每个正式发布必须具有唯一、可比较的版本；主分支变更不自动成为正式更新，只有维护者明确标记的版本才可供正式安装或升级。 |
| R-04 | 首版状态连续性只覆盖同一宿主、同一会话和同一设备上的压缩、恢复与继续，不允许新会话、另一宿主或另一设备自动继承。 |
| R-05 | 检查点必须在确认、范围变化、提交、Review 等改变任务权威状态的语义边界自动更新，不能要求用户手工保存。 |
| R-06 | 有效检查点至少保留当前目标与阶段、用户已确认决定、明确排除、委托范围、当前问题、活动交付范围、有效证据、文件与提交状态、下一动作，以及已加载控制文档的位置和内容指纹。 |
| R-07 | 同一会话压缩或恢复后，AI 必须先恢复静态规则和最近有效检查点；不得把已确认事项重置为待确认、把候选提升为正式决定或把暂存范围提升为当前范围。 |
| R-08 | 检查点保存失败必须立即显式提示；没有有效检查点时必须阻止压缩或恢复流程继续宣称安全，不能静默降级为可能丢失状态的推进。 |
| R-09 | 检查点缺失、损坏、过期或相互冲突时，只能从当前会话和工作区事实定向恢复缺失差量；仍无法确认时只询问具体差量，不得猜测或从头重放任务。 |
| R-10 | 会话状态必须按宿主和会话隔离地保存在本机插件私有范围，不得保存密码、访问令牌或其他秘密，也不得用于跨会话或跨端同步。 |
| R-11 | 现有软链接安装方式必须保留为 Codex IDE、旧版宿主和故障恢复的兼容入口，但不得覆盖用户已有普通文件或真实目录，也不得作为支持插件宿主的默认路径。 |
| R-12 | 首版只通过项目维护的 GitHub 分发入口提供，不申请 Codex 或 Claude Code 官方公共目录；未启用或未信任插件生命周期能力时，系统不得宣称自动检查点与恢复已经生效。 |

## 4. 边界与异常

| 场景 | 业务结果或恢复 |
|------|----------------|
| 新会话首次启动且没有当前会话检查点 | 只加载静态规则并从用户当前输入开始，不读取其他会话状态。 |
| 同一会话发生压缩或恢复 | 加载最近有效检查点并核对当前宿主、会话和版本范围，然后从记录的下一动作继续。 |
| 自动检查点无法保存 | 立即提示保存失败；在取得有效检查点前阻止压缩或恢复流程继续宣称安全。 |
| 检查点损坏、过期、版本不兼容或存在冲突 | 保留可验证事实，拒绝载入不可信部分，定向恢复或只询问仍缺失的具体差量。 |
| 插件未启用、未获信任或宿主不支持插件 | 明确说明自动注入和恢复未生效；支持的旧入口可按兼容流程安装，不静默修改用户配置。 |
| 兼容安装目标已有普通文件或真实目录 | 整次兼容安装不写入并报告冲突，不覆盖用户内容。 |
| 用户尝试让新会话、另一宿主或另一设备继承状态 | 首版明确拒绝自动继承，并说明该能力不在当前范围。 |
| 正式版本以外的主分支变更 | 只作为验证中的候选，不被正式安装入口视为新版本。 |

## 5. 独立交付边界

| 交付结果 | 共享业务输入输出 | 架构前置 | 硬依赖 | 明确不做 |
|----------|------------------|----------|--------|----------|
| 一名全栈工程师可独立交付双宿主插件入口、版本发布、自动会话检查点、压缩恢复、失败保护、兼容安装及完整验收 | 输入为当前 Nova 规则、技能、用户确认和宿主会话事件；输出为可安装版本、同会话有效检查点、恢复结果和可观察失败状态 | 需要先确认双宿主插件生命周期、持久状态隔离、版本发布和真实宿主验收契约 | 无 | 官方公共目录发布；跨会话、跨宿主、跨设备或团队同步；远程状态服务；秘密持久化；每轮重复注入完整规则 |

## 6. 验收

| 覆盖规则 | 场景 | 预期结果 |
|----------|------|----------|
| R-01 R-02 | 用户分别从正式分发入口安装 Codex 与 Claude Code 插件 | 两端都能发现同版本 Nova 规则与技能，正常安装不要求用户创建软链接。 |
| R-03 | 主分支合并变更但没有明确发布新版本 | 正式安装入口保持原版本；创建与内容一致的新版本标记并通过验收后才出现可升级版本。 |
| R-04 | 用户在同一会话恢复以及新会话、另一宿主、另一设备中分别尝试续接 | 只有同一宿主、同一会话、本机恢复成功，其他场景不自动继承。 |
| R-05 R-06 | 用户依次确认范围、完成提交并进入 Review 前后检查状态 | 无需手工保存，每个语义边界后的有效检查点均包含规则规定的完整权威状态。 |
| R-07 | Codex 与 Claude Code 分别触发真实自动压缩后继续 | 两端都先恢复静态规则和最近检查点，确认项、排除项、当前范围与下一动作不发生语义倒退。 |
| R-08 | 在没有有效检查点时模拟保存失败并触发压缩或恢复 | 用户收到明确失败提示，流程被阻止，系统不宣称状态已安全保存或恢复。 |
| R-09 | 提供损坏、过期、版本不兼容或冲突的检查点 | 不可信内容不进入权威状态；系统只恢复可验证差量，无法确认时只询问具体缺口。 |
| R-10 | 检查不同宿主、会话和敏感输入对应的本机状态 | 状态严格隔离，不发生跨会话继承，持久内容不包含密码、令牌或其他秘密。 |
| R-11 | 在兼容安装目标分别为空、已有软链接、已有普通文件和已有真实目录时执行安装 | 缺失或链接目标可安全安装或刷新；普通文件和真实目录保持不变，冲突时整次操作不写入。 |
| R-12 | 通过 GitHub 分发入口安装，并分别测试已信任、未信任和禁用状态 | 首版无需官方公共目录；只有启用并信任后才声明自动检查点与恢复生效。 |
