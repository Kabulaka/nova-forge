# AI委托决策与外部参考研究闭环

> 需求块规范版本：1
> Requirement-Key：REQ-01a05ba8-f944-7de8-83ba-599a04745d83
> 需求版本：v2
> 所属模块：访谈治理

## 1. 目标

| 业务问题 | 成功结果 |
|----------|----------|
| 访谈可能连续询问可由 AI 研究和决定的常规参数，阶段切换后又把上游结论与本阶段新增决定混在一起，使用户看不出本阶段实际澄清了什么 | 一次访谈能够识别真正需要用户决定的差量，继承上游已确认契约，完成必要研究，分开展示本阶段事实、AI 候选决定和未决差量并允许修正，最终由用户确认完整契约 |

## 2. 参与者与业务流程

| 步骤 | 参与者 | 触发与输入 | 业务结果 |
|------|--------|------------|----------|
| 1. 确定当前阶段和委托边界 | 用户与 AI | 用户提出需求、架构或开发目标，并可能带入上游已确认契约、参考对象、成熟方案或由 AI 决定 | 明确当前阶段权威、继承内容、AI 可代决策范围和仍需用户确认的事项 |
| 2. 判断研究与提问 | AI | 当前项目证据、委托表达、风险和剩余差量 | 可查事实进入研究，显式参考或高风险委托触发深度研究，只保留真正改变结果的问题 |
| 3. 形成并披露候选 | AI | 上游已确认契约、已验证参考事实、当前项目约束和证据边界 | 分开展示继承契约、本阶段查明事实、本阶段新增候选决定及未决差量，并说明依据、影响、不采用内容和未验证事项 |
| 4. 修正和重新收敛 | 用户与 AI | 用户对任一候选决定的纠正或补充 | 最新明确意见覆盖候选，只重新计算受影响差量，不重启整个访谈 |
| 5. 整体确认 | 用户 | 待确认差量清零后的整份摘要 | 用户明确确认后形成正式契约，并按阶段边界继续后续交付 |

## 3. 业务规则

| 规则 | 唯一定义 |
|------|----------|
| R-01 | 需求、架构和开发访谈共享单问题、答案合并、中断恢复、候选披露和整份摘要确认语义，但各阶段只处理自身权威范围 |
| R-02 | 用户明确提到参考、类似、成熟平台、行业标准、最佳实践或指定产品、仓库时必须启动外部参考研究；未显式提及时，安全、身份、公共契约等高风险委托也必须研究，普通低风险内部决定不启动深度研究 |
| R-03 | 委托范围已确认只表示 AI 获得限定决策权；外部或当前项目事实记为证据已查明；AI 的适配结果记为 AI 候选决定；只有用户明确确认整份摘要后才成为正式契约 |
| R-04 | 用户授权 AI 采用成熟方案后，可以免除委托范围内常规参数的逐项提问，但不得免除研究、具体决定披露、用户修正机会和最终确认 |
| R-05 | 外部研究必须记录参考范围、版本、日期、来源和证据边界；闭源产品只能依据官方资料、公开接口和可验证行为，开源实现还必须核对实际实现、测试和许可证；安全主题不能只模仿产品行为 |
| R-06 | 用户可见综合结果必须分开呈现参考事实、AI 采用的具体候选决定、适配理由和影响、不建议照搬或明确未采用内容、证据冲突与未验证事项，不得只写“按行业标准处理” |
| R-07 | 能由代码、配置、测试或指定资料查明的事实不得转问用户；已回答事项不得重问，只有新证据形成具体冲突时才可说明差异并重开一个冲突差量 |
| R-08 | 需求阶段保留业务目标、角色、流程、权限、状态、规则、范围和验收的确认权；架构阶段保留显著成本、部署、数据所有权、公共契约和共享失败语义的确认权；开发阶段只询问会改变功能行为、外部契约、安全边界或数据语义的差量 |
| R-09 | 用户修正 AI 候选决定时，最新明确意见覆盖该候选，只失效直接依赖该决定的推断和差量，其他已确认内容与无冲突候选保持有效 |
| R-10 | 没有剩余行为改变型差量时直接形成整份候选摘要，不得制造形式性问题；取消、空答案和未提交选择不得视为确认或研究成功，也不得自动实施或启动 Review |
| R-11 | 进入架构或开发阶段时必须继承上游已确认契约且不得重新询问；本阶段用户可见摘要必须分开标明“继承契约”“本阶段查明事实”“本阶段新增 AI 候选决定”和“本阶段未决差量”，不得用整份内容平铺掩盖阶段新增决定 |
| R-12 | 本阶段没有未决差量时必须明确显示未决差量为零，并说明相关事项已由既有确认、证据或授权范围内的 AI 候选决定消解；零差量不等于零工作，也不得为证明发生过澄清而制造问题 |
| R-13 | 阶段最终确认仍覆盖该阶段形成的整份候选契约，而非只确认差量；摘要必须突出本阶段新增候选及其影响，使用户能够修正，同时不得要求用户重新批准没有冲突的继承契约 |
| R-14 | 需求阶段只确认更换技术实现后仍必须成立的业务行为和用户明确指定的产品验收；可替换的页面布局、组件组织、数据结构、算法落位和其他实现方案默认属于开发候选，显著成本、部署、数据所有权、公共契约和共享失败语义仍属于架构阶段 |

## 4. 边界与异常

| 场景 | 业务结果或恢复 |
|------|----------------|
| 用户只说“像某产品”，未说明参考功能 | 保留委托意图，只询问一个最影响结果的参考范围问题 |
| 用户指定成熟项目管理平台的账号安全，功能范围已明确 | AI 自行选择有代表性的正式标准和产品资料直接研究，不要求用户描述公开事实或逐项决定常规参数 |
| 参考对象不可访问、版本不明、证据冲突或研究超时 | 只报告已验证事实和缺口，撤回依赖缺失证据的候选决定并标明证据不足 |
| 用户要求参考闭源产品的“内部实现” | 说明内部实现不可验证，只提炼公开行为和契约；需要代码级证据时另选合适开源来源且披露差异 |
| 用户纠正一项候选决定 | 保留其他无冲突决定，只重新研究和确认受影响范围 |
| 原问题未提交、取消或呈现状态不明 | 保持未回答，不合并、不推进；恢复时完整重现原问题和选项 |
| 需求已经确认，开发研究没有发现新的行为改变型差量 | 明确显示开发阶段未决差量为零，同时披露代码事实和新增实现候选，再等待整份设计确认，不重复需求问题 |
| 上游要求包含可替换的展示建议，但用户没有把它指定为产品验收 | 保留上游业务结果，将具体展示方式标为开发阶段 AI 候选并说明用户可感知影响 |

## 5. 独立交付边界

| 交付结果 | 共享业务输入输出 | 架构前置 | 硬依赖 | 明确不做 |
|----------|------------------|----------|--------|----------|
| 一名全栈工程师可独立交付三阶段访谈的委托决策和参考研究闭环及其验收 | 输入用户目标、委托范围和当前阶段事实；输出参考事实、AI 候选决定、用户修正和最终确认状态 | 统一访谈状态、研究结果和三阶段权威边界需由架构阶段冻结 | 无 | 宿主级持久化、参考项目复制、自动 Review 和与本需求无关的访谈重构 |

## 6. 验收

| 覆盖规则 | 场景 | 预期结果 |
|----------|------|----------|
| R-01、R-08 | 同一用户分别在需求、架构和开发阶段委托 AI 采用成熟方案 | 三阶段使用相同交互与确认语义，同时只询问各自权威范围内会改变结果的差量 |
| R-02、R-04 | 用户说“常规安全和账号规则按成熟项目管理平台的标准方案设计，不需要逐项问我” | 直接启动安全标准、成熟平台行为和当前项目约束研究，不再逐项询问密码等常规参数 |
| R-03、R-06 | 研究完成并形成账号安全方案 | 用户看到参考事实、具体规则、依据、影响、不采用内容和证据缺口；这些内容保持 AI 候选状态 |
| R-05 | 用户要求参考 Jira 内部实现，并同时提供一个开源项目 | Jira 只使用公开可验证资料，开源项目追踪实际实现和测试并披露版本及许可证，不混淆证据强度 |
| R-07 | 用户已回答账号停用规则，随后出现无冲突的相邻问题 | 不重复账号停用问题；可查事实由 AI 研究，只有具体冲突才说明原因并重开一个差量 |
| R-09 | 用户只把候选锁定时长从 15 分钟改为 30 分钟 | 更新该决定及直接依赖的验收，其他已确认内容和无冲突候选保持不变 |
| R-10 | 所有行为改变型差量已清零，或原生问题返回空答案 | 前者直接展示整份候选摘要并等待明确确认；后者保持未回答且不推进、不自动实施或 Review |
| R-11 | 已确认账户负载需求后进入开发，代码研究形成同步、存储和失败隔离方案 | 摘要分别展示继承的指标口径、代码查明事实、开发阶段新增候选及未决差量，用户能直接识别本阶段新增内容 |
| R-12 | 开发研究能够从代码查明全部事实且内部方案均在授权范围内 | 明确显示“本阶段未决差量：0”及消解依据，不增加形式性问题，仍完整披露开发工作和候选决定 |
| R-13 | 开发摘要含四项继承需求和三项新增实现候选 | 用户确认覆盖整份设计；用户可以只修正一项新增候选，未冲突的继承需求不重新审批也不失效 |
| R-14 | 需求提出“能够查看账户负载趋势”但未指定图表结构，开发需要在单图切换和多图展示间选择 | 趋势能力保留为需求，具体图表结构作为开发候选披露；若用户明确指定图表结构为验收要求，则由需求阶段确认 |
