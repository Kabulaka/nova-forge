# 需求基线与完整切片跟踪

> 需求块规范版本：1
> Requirement-Key：REQ-01a06a50-2732-704d-97d0-7a98b205a4ea
> 需求版本：v1
> 所属模块：交付治理

## 1. 目标

| 业务问题 | 成功结果 |
|----------|----------|
| 已确认需求可能等待后续开发才被提交，大需求又只逐次创建当前任务，导致基线、完整范围和总体进度无法可靠恢复 | 每版需求确认后立即形成独立、不可变的本地检查点；首个开发切片前完整登记交付台账，此后任何会话都能从项目证据恢复整体范围和进度 |

## 2. 参与者与业务流程

| 步骤 | 参与者 | 触发与输入 | 业务结果 |
|------|--------|------------|----------|
| 1. 确认需求版本 | 用户与 AI | 用户明确确认整份需求，需求索引与需求块校验通过 | 当前 `REQ-...@vN` 成为唯一可提交的确认候选 |
| 2. 提交需求检查点 | AI | 已确认需求版本、需求块内容指纹和精确文件范围 | 立即形成独立本地提交；不等待架构或开发，不进入人工 Review |
| 3. 判断架构门禁 | AI | 已提交需求与当前共享边界 | 只有共享工程骨架、数据所有权、公共 API、事件或 Mock 发生变化才进入架构；进入后必须 Review PASS |
| 4. 建立完整台账 | AI | 需求检查点、已就绪架构和完整需求级交付拆分 | 首个开发切片前一次性登记全部 PEND、依赖、完成定义和 Requirement-Ref，需求转为开发中 |
| 5. 激活并交付切片 | AI 与用户 | 台账中满足依赖的下一 PEND | 一次只激活一个 PEND；激活时再完成详细设计、实现、测试、本地提交和按策略 Review |
| 6. 聚合进度 | AI | 台账、蓝图与可信 Review 审计 | 固定展示总数、已完成、当前、剩余和阻塞；单片完成不提前关闭整项需求 |
| 7. 调整计划或完成需求 | 用户与 AI | 新证据、阻塞、范围变化或全部有效 PEND PASS | 调整留下稳定身份与原因；减少业务验收范围时升级需求版本；全部有效切片 PASS 后需求才已实现 |

## 3. 业务规则

| 规则 | 唯一定义 |
|------|----------|
| R-01 | 每个经用户明确确认且校验通过的 `REQ-...@vN` 必须立即形成独立本地需求检查点，不得等待架构、开发或 Review 后夹带提交。 |
| R-02 | 需求检查点必须绑定 Requirement-Ref、需求块路径、内容 SHA-256 和不可变 commit；架构、交付台账和开发只能引用该已提交版本，不得引用未提交工作树。 |
| R-03 | 需求检查点是用户已确认业务契约的保存动作，不是 PEND/FIX/MAINT，不进入人工 Review 选择，也不产生功能完成审计。 |
| R-04 | 架构阶段只在共享工程骨架、数据所有权、公共 API、事件或 Mock 边界变化时进入；一旦进入，对应架构 PEND 必须 Review PASS 后才能启动受其约束的开发。 |
| R-05 | 首个开发切片启动前，当前需求版本必须有一份持久化完整交付台账；台账一次性列出全部 `PEND-*`、依赖、完成定义和逐字一致的 Requirement-Ref。 |
| R-06 | 台账提交表示需求已认领且需求级交付设计已完成，需求状态从待实现转为开发中；各 PEND 的详细实现设计允许在该项激活时再完成。 |
| R-07 | 同一需求版本默认一次只激活一个 PEND；未激活项仍须保留在项目台账和蓝图投影，不得只存在于会话胶囊、计划文本或模型记忆。 |
| R-08 | 单个 PEND 只有可信 Review PASS 后才计入已完成；任意一个 PEND PASS 不得直接把整项需求标为已实现。 |
| R-09 | 只有当前需求版本台账中全部有效 PEND 均有可信 Review PASS，且没有当前或阻塞项时，需求才转为已实现并保存全部实现依据。 |
| R-10 | 已登记切片不得静默删除或复用身份；拆分、合并、替代、取消、重排或新增必须递增计划版本，保留原切片、替代关系、原因和时间顺序。 |
| R-11 | 计划调整不得减少已确认业务验收范围；确需减少、撤销或改变业务结果时必须返回需求阶段，升级同一 REQ 的需求版本并重新确认、提交和规划。 |
| R-12 | 每次进入、继续、提交、Review 或查询当前需求时，进度必须从持久化台账与可信审计派生，并固定展示总数、已完成、当前、剩余和阻塞。 |
| R-13 | 需求检查点与交付计划检查点必须和普通 Work-Item/Audit commit 明确分型；Review 发现逻辑只选择声明需要 Review 的 PEND/FIX/MAINT。 |
| R-14 | 校验、提交或台账投影失败时保持上一份有效需求与计划，不得进入开发中、激活切片或宣称进度已安全保存。 |
| R-15 | 本需求自身是旧提交规则下唯一一次 bootstrap：它以合法架构 PEND 携带需求和完整未来切片登记，保持待实现直至新机制落地；该例外不得推广到后续需求。 |

## 4. 边界与异常

| 场景 | 业务结果或恢复 |
|------|----------------|
| 需求确认后会话中断，尚未进入架构或开发 | 从独立需求检查点恢复 `REQ@版本`、内容指纹和 commit，不重新依赖会话记忆。 |
| 需求不改变任何共享架构边界 | 跳过架构阶段，直接建立完整交付台账；不得为了流程形式制造架构 PEND。 |
| 需求需要共享架构变化 | 先形成架构 PEND 并完成 Review；Review PASS 前台账可以规划但不得激活受影响开发切片。 |
| 后续切片尚未完成详细设计 | 台账与蓝图保留稳定 PEND、依赖、完成定义和 Requirement-Ref，设计依据显示待澄清。 |
| 当前切片阻塞或失败 | 保留当前与阻塞原因；不丢弃剩余切片，不把下一项静默提升为当前。 |
| 计划需要拆分、合并或替代切片 | 原身份保留为非有效终态，新身份和替代关系追加到新计划版本，总体业务验收保持不减。 |
| 发现必须减少或改变业务验收 | 停止开发计划调整，返回需求阶段创建并确认新版本，再基于新检查点重建台账。 |
| 需求或计划提交失败 | 工作树不得被当作已提交基线；恢复上一有效检查点并明确报告失败。 |

## 5. 独立交付边界

| 交付结果 | 共享业务输入输出 | 架构前置 | 硬依赖 | 明确不做 |
|----------|------------------|----------|--------|----------|
| 一名全栈工程师可独立交付需求检查点提交类型、完整交付台账、状态聚合、Review 选择隔离、计划变更留痕和进度查询 | 输入为已确认需求版本、必要架构、PEND 生命周期和可信 Review 审计；输出为不可变需求基线、版本化台账、蓝图投影及五项进度 | 需要先冻结提交分型、台账 schema、状态聚合、变更和失败恢复契约 | 无 | 替代单项详细设计或代码 Review；自动 Review；把计划或进度只存入会话；远程提交或团队项目管理系统 |

## 6. 验收

| 覆盖规则 | 场景 | 预期结果 |
|----------|------|----------|
| R-01 R-02 R-03 R-13 | 确认并校验一个新需求后停止，不进入架构或开发，再从新会话恢复并查询 Review 候选 | Git 中存在独立需求检查点，能恢复精确版本、路径、内容指纹和 commit；Review 候选不包含该检查点。 |
| R-04 | 分别处理不改变共享边界和改变数据所有权的两个需求 | 前者跳过架构直接规划；后者的开发在架构 Review PASS 前被阻止，PASS 后才可激活。 |
| R-05 R-06 R-07 | 将一个大需求拆成三个切片并准备启动第一项 | 首项启动前已一次性持久化三个稳定 PEND、依赖、完成定义和 Requirement-Ref；需求显示开发中，仅第一项为当前。 |
| R-08 R-09 | 三个切片依次 Review PASS | 前两次只增加已完成数且需求仍开发中；第三次 PASS 后无剩余与阻塞，需求才已实现并列出全部依据。 |
| R-10 R-11 | 先技术拆分一个切片，再尝试取消一项业务验收 | 技术拆分保留原身份、原因和替代关系；取消业务验收被阻止并要求升级需求版本。 |
| R-12 | 在切片激活、提交、Review PASS、阻塞和跨会话继续时查询进度 | 每次都从项目证据展示总数、已完成、当前、剩余和阻塞，结果与台账和审计一致。 |
| R-14 | 模拟需求提交、计划写入、蓝图投影和审计读取失败 | 保留上一有效状态，不进入开发中、不激活新 PEND，也不宣称提交或进度更新成功。 |
| R-15 | 检查本需求 bootstrap 与下一项新需求 | 本需求只由一次合法架构 PEND 引导；新需求严格在确认后先形成独立需求检查点，不再夹带到 PEND。 |
