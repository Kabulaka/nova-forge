# 需求基线与完整切片跟踪

> 需求块规范版本：1
> Requirement-Key：REQ-01a06a50-2732-704d-97d0-7a98b205a4ea
> 需求版本：v3
> 所属模块：交付治理

## 1. 目标

| 业务问题 | 成功结果 |
|----------|----------|
| 已确认需求可能等待后续开发才被提交，任务分类、架构产出、蓝图状态、完成报告和提交边界又可能因分散的自然语言规则发生偏移 | 每版需求立即形成独立检查点；按真实语义区分 REQ、ARCH、FEAT、PATCH、FIX、MAINT，无差量阶段不制造成果，工作项保持完整边界，并由统一校验和阶段报告持续暴露交付与 Review 状态 |

## 2. 参与者与业务流程

| 步骤 | 参与者 | 触发与输入 | 业务结果 |
|------|--------|------------|----------|
| 1. 确认需求版本 | 用户与 AI | 用户明确确认整份需求，需求索引与需求块校验通过 | 当前 `REQ-...@vN` 成为唯一可提交的确认候选 |
| 2. 提交需求检查点 | AI | 已确认需求版本、需求块内容指纹和精确文件范围 | 立即形成独立本地提交；不等待架构或开发，不进入人工 Review |
| 3. 判断架构差量 | AI | 已提交需求与当前共享边界 | 无共享架构差量时明确依据并零产物通过；只有共享工程骨架、数据所有权、公共 API、事件或 Mock 实际变化时才形成 ARCH |
| 4. 建立完整台账 | AI | 需求检查点、必要且就绪的 ARCH 和完整需求级任务拆分 | 首个开发任务前一次性登记全部独立 FEAT、内部里程碑、依赖、完成定义和 Requirement-Ref，需求转为开发中 |
| 5. 分类并交付任务 | AI 与用户 | 台账中的下一 FEAT，或既有契约内新发现的局部工作 | 新能力使用 FEAT，主动局部调整使用 PATCH，恢复偏离契约的缺陷使用 FIX，非产品行为维护使用 MAINT；默认按一个完整阶段结果提交 |
| 6. 报告并人工 Review | AI 与用户 | 已完成实现、验证证据和 Review 策略 | 阶段报告先说明实际结果；required 项明确显示待Review。Review 拒绝轮次在同一任务中修正，最终 PASS 后只产生一次闭环提交 |
| 7. 聚合进度或调整计划 | 用户与 AI | 台账、蓝图、提交、可信 Review 审计及新证据 | 固定展示总数、已完成、当前、剩余和阻塞；调整保留身份与原因，全部有效 FEAT PASS 后需求才已实现 |

## 3. 业务规则

| 规则 | 唯一定义 |
|------|----------|
| R-01 | 每个经用户明确确认且校验通过的 `REQ-...@vN` 必须立即形成独立本地需求检查点，不得等待架构、开发或 Review 后夹带提交。 |
| R-02 | 需求检查点必须绑定 Requirement-Ref、需求块路径、内容 SHA-256 和不可变 commit；架构、交付台账和开发只能引用该已提交版本，不得引用未提交工作树。 |
| R-03 | 需求检查点是用户已确认业务契约的保存动作，不是 ARCH/FEAT/PATCH/FIX/MAINT，不进入人工 Review 选择，也不产生功能完成审计。 |
| R-04 | 架构判定不等于架构交付。只有共享工程骨架、数据所有权、公共 API、事件或 Mock 实际变化时才创建 `ARCH-*`；无差量时不创建编号、不修改架构文件、不提交或 Review，只报告判断依据。 |
| R-05 | 首个开发任务启动前，当前需求版本必须有一份持久化完整交付台账；台账一次性列出全部独立 `FEAT-*`、各任务内部里程碑、依赖、完成定义和逐字一致的 Requirement-Ref。 |
| R-06 | 台账提交表示需求已认领且需求级交付设计已完成，需求状态从待实现转为开发中；各 FEAT 的详细实现设计允许在该项激活时再完成。 |
| R-07 | 同一需求版本默认一次只激活一个 FEAT；未激活任务仍须保留在项目台账和蓝图投影，当前任务的未完成内部里程碑仍须保留在台账，不得只存在于会话胶囊、计划文本或模型记忆。 |
| R-08 | 单个 FEAT 只有可信 Review PASS 后才计入已完成；任意一个 FEAT PASS 不得直接把整项需求标为已实现。 |
| R-09 | 只有当前需求版本台账中全部有效 FEAT 均有可信 Review PASS，且没有当前或阻塞项时，需求才转为已实现并保存全部实现依据。 |
| R-10 | 已登记任务和内部里程碑不得静默删除；工作项的拆分、合并、替代、取消、重排或新增必须递增计划版本并保留原身份、关系、原因和时间顺序，里程碑调整也必须留痕但不得据此制造新 FEAT。 |
| R-11 | 计划调整不得减少已确认业务验收范围；确需减少、撤销或改变业务结果时必须返回需求阶段，升级同一 REQ 的需求版本并重新确认、提交和规划。 |
| R-12 | 每次进入、继续、提交、Review 或查询当前需求时，进度必须从持久化台账与可信审计派生，并固定展示总数、已完成、当前、剩余和阻塞。 |
| R-13 | 需求检查点、ARCH 结果、交付计划、普通工作项与 Review 闭环提交必须明确分型；Review 发现逻辑只选择声明需要 Review 的 ARCH/FEAT/PATCH/FIX/MAINT。 |
| R-14 | 校验、提交或台账投影失败时保持上一份有效需求与计划，不得进入开发中、激活切片或宣称进度已安全保存。 |
| R-15 | 已有 `PEND-*` 是历史兼容身份，保持原编号、引用和审计，不得批量改写；新规则启用后禁止创建新的 PEND，后续完整功能交付统一使用 FEAT。 |
| R-16 | 工作项只能沿独立、内聚、可控的交付边界拆分：每项必须有完整结果和验收，可独立排期、暂停、恢复、Review 或取消；不能因需求、架构、编码、测试等流程阶段，或文件、模块、技能、代理、提交批次不同而拆项。 |
| R-17 | 多个步骤若只有共同完成才具备交付价值，或共同修改同一项规模可控的能力，必须保留为一个 FEAT，并以内部里程碑跟踪；只有需求过大且能沿稳定能力边界切成满足 R-16 的任务时，才建立多个 FEAT。 |
| R-18 | 新编号按语义固定为 `REQ-*`、`ARCH-*`、`FEAT-*`、`PATCH-*`、`FIX-*`、`MAINT-*`。Review 是绑定目标工作项与提交范围的审查批次，不另造交付工作项编号。 |
| R-19 | PATCH 只表示既有能力内不属于缺陷的主动局部调整；FIX 必须能以既有需求、设计、协议、测试或运行证据证明实际行为偏离预期。新增能力、业务语义或公共契约变化不得降级为 PATCH/FIX。 |
| R-20 | 蓝图活动投影只使用 `待澄清 / 待开发 / 待Review` 三个常态状态；开发开始不为显示“进行中”制造额外文档提交，required 项完成实现提交后必须显示待Review，PASS 后才从活动投影移除。 |
| R-21 | 设计依据和前置依赖不得只写无上下文的“待澄清”；依赖只允许无、可点击稳定编号或带具体问题的待确认说明。需求引用必须使用可校验的 `REQ-...@vN` 超链接，无引用时说明客观原因。 |
| R-22 | 需求、架构、FEAT、PATCH、FIX、MAINT、Review 分别使用能体现本阶段含义的完成报告；报告首先说明实际结果和明确未改范围，再列验证、提交、Review 状态、遗留边界与下一步，不能以文件和命令堆砌代替结果说明。 |
| R-23 | 开发完成但未正式 Review 时只能报告“未 Review / 待Review”。同一 Review 的 REJECT 轮次只累积发现、修正和复验，不逐轮提交；最终 PASS 后仅形成一个包含全部 Review 修正和审计闭环的提交。 |
| R-24 | 受控提交首行使用 `type(scope): 中文结果摘要`；type 表示变更性质，scope 表示稳定能力区域并来自项目白名单，摘要至少包含中文结果描述。禁止用任务编号、状态、文件名或 all/misc/core/governance 等无区分度词作为 scope。 |
| R-25 | 一个工作项默认形成一个完整实现结果提交；只有真正可恢复、可验证的内部里程碑才允许沿用同一编号追加提交，不得按文件、代码/测试/文档或 Review 拒绝轮次制造碎片提交。 |
| R-26 | 开发准入必须证明需求版本、可执行验收、设计依据和依赖足以实施。开发发现歧义时先区分需求、架构和局部实现来源，只把会改变结果且无法由证据消解的一个差量返回相应上游，不重复询问已有答案或制造形式性问题。 |
| R-27 | 编号、分类映射、scope、中文首行、trailers、引用、蓝图状态、Review 闭环和阶段报告必填内容必须由统一只读校验入口确定性检查并失败封闭；工作项独立性、PATCH/FIX 业务语义和架构合理性仍由确认与 Review 负责，不以增加状态或文件冒充语义验证。 |

## 4. 边界与异常

| 场景 | 业务结果或恢复 |
|------|----------------|
| 需求确认后会话中断，尚未进入架构或开发 | 从独立需求检查点恢复 `REQ@版本`、内容指纹和 commit，不重新依赖会话记忆。 |
| 需求不改变任何共享架构边界 | 记录零差量依据后直接建立完整交付台账；不创建 ARCH、架构文件、提交或 Review。 |
| 需求需要共享架构变化 | 形成可追溯 ARCH 并在蓝图架构区域管理，不把 ARCH 写成待开发功能；架构结果再产生一个或多个 FEAT。 |
| 后续切片尚未完成详细设计 | 台账与蓝图保留稳定 FEAT、依赖、完成定义和 Requirement-Ref，状态为待澄清并说明具体缺失项。 |
| 当前切片阻塞或失败 | 保留当前与阻塞原因；不丢弃剩余切片，不把下一项静默提升为当前。 |
| 计划需要拆分、合并或替代任务 | 先按独立、内聚、可控边界校验；成立时原身份保留为非有效终态，新身份和替代关系追加到新计划版本，总体业务验收保持不减；仅调整内部步骤时只更新里程碑。 |
| 发现必须减少或改变业务验收 | 停止开发计划调整，返回需求阶段创建并确认新版本，再基于新检查点重建台账。 |
| 需求或计划提交失败 | 工作树不得被当作已提交基线；恢复上一有效检查点并明确报告失败。 |

## 5. 独立交付边界

| 交付结果 | 共享业务输入输出 | 架构前置 | 硬依赖 | 明确不做 |
|----------|------------------|----------|--------|----------|
| 一名全栈工程师可独立交付需求检查点、ARCH/FEAT/PATCH/FIX/MAINT 分类、完整交付台账、最小状态、阶段报告、提交边界、Review 闭环和统一校验 | 输入为已确认需求版本、实际架构差量、工作项证据和可信 Review 审计；输出为不可变需求基线、版本化台账、清晰蓝图投影、可读报告及可验证提交 | 需要先冻结编号、提交分型、scope、台账投影、报告字段和失败恢复契约 | 无 | 替代单项详细设计或代码 Review；自动 Review；为流程制造成果；把计划或进度只存入会话；远程提交或团队项目管理系统 |

## 6. 验收

| 覆盖规则 | 场景 | 预期结果 |
|----------|------|----------|
| R-01 R-02 R-03 R-13 | 确认并校验一个新需求后停止，不进入架构或开发，再从新会话恢复并查询 Review 候选 | Git 中存在独立需求检查点，能恢复精确版本、路径、内容指纹和 commit；Review 候选不包含该检查点。 |
| R-04 R-18 | 分别处理不改变共享边界和改变数据所有权的两个需求 | 前者以零产物架构判定直接规划；后者建立 ARCH 且不进入待开发功能表，架构结果就绪后才激活 FEAT。 |
| R-05 R-06 R-07 R-16 R-17 | 将一个大需求沿三个独立能力边界拆成开发任务并准备启动第一项 | 首项启动前已一次性持久化三个稳定 FEAT、各自内部里程碑、依赖、完成定义和 Requirement-Ref；需求显示开发中，仅第一项为当前。 |
| R-08 R-09 | 三个独立 FEAT 依次 Review PASS | 前两次只增加已完成数且需求仍开发中；第三次 PASS 后无剩余与阻塞，需求才已实现并列出全部依据。 |
| R-10 R-11 | 先技术拆分一个切片，再尝试取消一项业务验收 | 技术拆分保留原身份、原因和替代关系；取消业务验收被阻止并要求升级需求版本。 |
| R-12 | 在切片激活、提交、Review PASS、阻塞和跨会话继续时查询进度 | 每次都从项目证据展示总数、已完成、当前、剩余和阻塞，结果与台账和审计一致。 |
| R-14 | 模拟需求提交、计划写入、蓝图投影和审计读取失败 | 保留上一有效状态，不进入开发中、不激活新 PEND，也不宣称提交或进度更新成功。 |
| R-15 R-16 R-17 | 读取历史 PEND，再为一个小需求和一个真正包含多个独立能力的大需求规划新任务 | 历史 PEND 及审计保持不变；小需求只建立一个 FEAT 和内部里程碑，大需求可沿独立能力边界建立多个 FEAT；任何入口都不能再创建新 PEND。 |
| R-18 R-19 R-24 R-25 | 分别提交新能力、主动局部调整、缺陷恢复和维护任务，并尝试使用宽泛 scope、英文摘要及按文件拆分提交 | 分别得到 FEAT/PATCH/FIX/MAINT；scope 和中文首行可校验，宽泛 scope、英文摘要与碎片提交被拒绝。 |
| R-20 R-21 | 登记待澄清、待开发和已完成待审的三个任务 | 状态只使用三个常态值；设计依据、依赖和需求引用均可理解且可点击，完成实现的 required 项显示待Review。 |
| R-22 R-23 | 完成一个 FEAT 后执行两轮 REJECT 和最终 PASS 的 Review | 开发报告先说明实际结果并显示待Review；拒绝轮次无 commit，最终报告列明审查对象、各轮发现和全部修改，只形成一个闭环提交。 |
| R-26 R-27 | 开发遇到已有答案、真实需求冲突和局部实现选择，并故意构造编号、引用、状态、提交与报告不一致 | 已有答案不重问，真实冲突返回来源阶段，局部选择在当前任务解决；所有可确定矛盾由统一校验入口失败封闭。 |
